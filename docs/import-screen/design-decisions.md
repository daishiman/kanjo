## 3. agent 推定の値

## 4. 本文の上限(OI-02 / P03)

- 本文の上限 = 合計の上限 30MB + 64KiB(multipart の境界とヘッダの枠)。`importBodyLimitBytes()` が core の値から導く。
- `bodyLimit` は Content-Length があれば本文を読む前に比べ、無ければ読みながら数える。どちらの経路も 413 `payload_too_large` になることを統合テストで固定した。
- 本文を読んだ直後・パースの前に、ファイル数 → 1 ファイル → 合計 の順で `importLimitViolation` を掛ける。合計 30MB+1 byte は検査も仮置きも作らずに止まる。

## 5. 関数と経路の境界(P02)

| 経路 | 役割 |
|---|---|
| `POST /imports/inspections` | 検査。原本を R2 に仮置きし、結果を `import_inspections` / `import_inspection_files` に置く。明細の表は書かない |
| `POST /imports/inspections/:id/files`、`DELETE …/files/:fileId` | 同じ検査 ID の上での追加と削除。期限は延ばさない。累計で上限を判定する |
| `POST /imports/runs` | 確定。検査 ID と選んだファイル ID だけを受ける。1 要求 1 ファイル(§6) |
| `GET /imports/runs`、`GET /imports/runs/:id` | 履歴(取込 1 回 = 1 行)と詳細 |
| `POST /imports/runs/:id/reimport`、`…/undo/preflight`、`…/undo`、`POST /imports/runs/hide` | 置換・取り消し・一括の非表示 |
| `POST /imports`(旧来) | API 互換とローカル seed のため残す。新しい取込画面は呼ばず、確定を `POST /imports/runs` に一本化する。本文・ファイル数・合計サイズの上限、Origin 検査、利用者単位の確定 5 回/分制限は新経路と揃える |

- `import_runs.id` を取込 1 回の ID にする。検査 ID は `import_inspections.id` で、確定後も期限まで残す。確定済み項目は R2 の仮置き原本を消し、`summary_json` の最小結果と `error_kind='committed'` を再送 receipt として残す。2 本目以降の run は `parent_run_id` で最初の run に結び、履歴に単独では出さない。
- `keepOnShrink`(行が減ったときに前回データを残すかの判断)は画面から外した。「前回データを残す」と意味が重なり、利用者が区別できないため。
- `IMPORT_LIMITS` は取込の上限だけを持つ。`IMPORT_RATE_STALE_MS`(24 時間を過ぎたレート制限の枠を消す)は片づけの都合なので `import-rate-limit.ts` に置き、上限の一覧の対象外にした。

## 6. 確定を 1 要求 1 ファイルにした理由

D1 は 1 invocation あたりの query 数に上限がある。10 ファイルを 1 要求で確定すると、明細の書き込み・重複の確認・run の更新でこの予算を超える。そこで確定は 1 要求 1 ファイルにし、画面が続きの要求を順に送る。

- 履歴を 1 行に保つため、2 本目以降の run は最初の run の子にする(`parent_run_id`)。
- レート制限は取込 1 回で 1 回だけ数える。続きの要求(`run_id` が付いた検査)は数えない(P10 の中1)。
- 1 ファイルの確定の query 数は 49/50 で、余裕が小さい(P10 の低)。

## 7. 重複の監査(P08)

- web と api の取込経路に、上限の数値リテラルは 0 件(`import-limits-literal.test.ts` が 10 ファイルを読む)。
- `packages/web/src/pages/import/view-model.ts` は core が導いた状態を数えるだけで、状態を導き直していない。受入の最終監査で、送信の失敗だけは `importItemStatus` が core より先に `failed` を返していたことが見つかった。この分岐は core の `importFileState` へ移した(入力 `uploadError`)。web に残るのは、core が理由を持たない「確定の失敗」に、確定の応答で受け取った理由を添えることだけ。
- web と api で結果・状態の文字列を直接比べている箇所は、core が導いた状態を数える・出し分けるもの、応答の値を型で確かめるもの(`routes/imports.ts` の `isRunResult`)、確定の応答のファイル状態を数えるもの(`ImportHistory.tsx`)だけ。判定を作り直している箇所は 0 件。
- `packages/web/src/pages/Import.tsx` は新しい画面を再 export する 5 行だけになった。
- 選択バーの errors は取込不可と失敗を数え、要約の `errorCount` は取込不可だけを数える。選択バーは「今ある問題」、要約は「検査で見つかった問題」を表すので、別の値のままにした。

## 8. xlsx 展開時のメモリ(OI-03 / P09)

Node v22.21.1 で、架空のデータの xlsx を `parseUpload` にかけて測った。Workers の実行環境ではないので、傾向の目安として読む。

| 行数・メモ | ファイル | 展開後 | heap の増分 | 時間 |
|---|---|---|---|---|
| 20,000・短い | 2.6MB | 8.4MB | 52.0MB | 531ms |
| 20,000・乱数 | 3.7MB | 9.3MB | 55.8MB | — |
| 40,000・短い | 5.1MB | 16.9MB | 115.9MB | 1,105ms |
| 60,000・短い | 7.7MB | 25.4MB | 151.4MB | — |
| 140,000・短い | 17.9MB | 59.8MB | 419.3MB | 4,135ms |
| 128,000・乱数 | 23.9MB | 60.7MB | 297.7MB | 3,801ms |

- Workers のメモリ 128MB に収まるのは、展開後およそ 15MB(約 35,000 行)まで。
- 25MB の xlsx は、ほとんどが展開後 60MB を超える。上限 (下記の結論で 15MB) を超えるものは `zipCentralDirectoryStats` の事前判定で、展開する前に止まる。
- 展開後 15MB〜60MB の xlsx は、当初の上限 60MB の内側でもメモリ不足で落ちうる。CSV は行ごとに読むので、この問題はない。

### 結論(利用者の判断・A案)

後退策のうち **A案(xlsx だけ展開後の上限を下げる)** を採り、`IMPORT_LIMITS.maxExpandedBytes` を 60MB から **15MB** へ下げた。実測で 128MB に収まる限界がそこだから。

B案(xlsx は 1 要求 1 ファイルに限る)は採らなかった。上の表のとおり heap の増分は**同時に何ファイル展開するか**ではなく **1 ファイルの展開後サイズ**でほぼ決まり、単独で送っても展開後 60MB なら約 300MB に達する。ファイル数を絞っても 128MB は超えるので、根本の解決にならない。

副作用として、展開後 15MB(約 35,000 行)を超える xlsx は取込不可になる。その場合は `zipCentralDirectoryStats` の事前判定で展開する前に止まり、理由は「展開後 15MB 超」と出る。要求全体は拒否せず、他のファイルの検査は続く。分割して送れば取り込める。
