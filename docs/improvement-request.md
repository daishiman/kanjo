# 改善リクエスト

画面の不具合や「ここが使いにくい」を、そのときの画面と技術的な記録つきで送るための機能です。

## 1. 利用者向け

### 1.1 送り方

1. 困った画面で **改善を送る** を押します。スマートフォンやタブレットを含め、画面幅に応じた入口から撮影を始められます。
2. 画面の右下に **画面をキャプチャ** のパネルが開きます。**キャプチャする** で画面全体を、**範囲を選択する** で一部だけを撮れます。範囲はドラッグか矢印キーで動かし（Shift と矢印キーで大きさを変える）、**この範囲を撮影** か Enter で撮ります。Escape で取り消せます。
3. 撮影用の複製では、金額・取引先名・名義・口座などをできる限り伏字にします。パネルと送信ボタン自身は写りません。自動判定では画像内の機密情報を完全には検出できないため、送る前に縮小画像を確認してください。
4. 撮り終えると **改善リクエスト** の画面（`/improvement`）へ移り、作成フォームに縮小画像・関連ページ・技術的な記録が入った状態になります。画像・記録はメモリ上で受け渡すだけで、端末には保存しません。
5. **どのような改善を希望しますか？** に内容（どう操作して、何を期待して、何が起きたか）を書きます。1000 字までです。件名の欄はありません（一覧には本文の最初の行が概要として出ます）。
6. **プライバシーに関する確認** の 2 つのチェックを入れて、**改善リクエストを送信** を押します。どちらかが空いていると送れず、理由がボタンの近くに出ます。

撮影に失敗しても作成フォームは使えます。その場合は文章だけで送れます。端末の画像ファイルを選んで添付することはできません（撮影用の複製で掛ける伏字を通らないため）。画像を替えたいときは **キャプチャを撮り直す** で関連ページへ戻って撮り直し、要らなければ **画像を削除** を押します。

### 1.1.0 一覧・詳細・状態・削除

- 送った依頼は、同じ画面の一覧に `IMP-001` のような番号つきで並びます（新しい順・10 件ずつ）。番号は削除しても詰めません。
- 一覧の上の検索欄は、本文・番号（`IMP-024`・`024`・`24` のどれでも）・関連ページ名で絞ります。タブは **すべて / 受付 / 対応中 / 完了 / 再確認** で、件数は検索で絞った後の数です。一覧は画面上部の期間では絞りません。
- 番号を押すと右側に詳細が開きます。本文・添付画像（押すと拡大）・診断情報の要約・アクティビティ（作成・状態の変更・再発行・削除・復元の履歴。コピー日時は依頼本体に記録）・同じページの関連する依頼（最大 3 件）が出ます。詳細を読み込めないときは理由と再試行の入口が出ます。
- **ステータスを変更** で状態を動かせます。移れる先は **受付 → 対応中・完了**、**対応中 → 受付・再確認・完了**、**再確認 → 対応中・完了**、**完了 → 対応中・再確認** です。旧版の「対応しない」は **完了** にまとめました（移行時に履歴へ理由が残ります）。
- **このリクエストを削除** は確認の画面を出さずに一覧から消し、右下の知らせの **元に戻す** で同じ番号のまま戻せます。戻さなかった依頼は、削除から **30 日後** に画像・履歴ごと完全に消えます。
- 一覧で選んだ依頼は、画面の下の **選択中** のバーからもコピーできます（コピー先は Claude Code / Codex を切り替えられます）。

### 1.1.1 画像に書き込む

作成フォームに画像があると、画像の上に **書き込みの道具**（**枠**・**ペン**・**文字**・**マスク**・**移動**）と **色**（赤・青・緑・橙・黒）が最初から並びます。道具と色を選び、画像の上をドラッグして書き込みます。「ここがおかしい」は文章より枠や線のほうが速く伝わります。

| 道具 | できること |
|---|---|
| 枠 | ドラッグした範囲を、選んだ色の四角で囲む |
| ペン | なぞった形のまま、選んだ色の線を書く（丸で囲む・矢印を描くなど） |
| 文字 | 押した場所に入力欄が出る。打ち込んで **Enter**（または入力欄の外を押す）で、選んだ色の文字として置く。**Esc** でやめる。1つにつき 40 文字まで。改行は空白になる |
| マスク | ドラッグした範囲を不透明の墨色で塗りつぶす。自動の伏字が届かない画像内の名前や金額を、自分で隠すときに使う |
| 移動 | 書いた枠・線・文字・マスクを掴んでドラッグし、場所を動かす。大きさ・形・色・文字はそのまま。画像の外へははみ出さない |

- 色は何も選ばなければ赤です。色を選び替えても、それまでに書いたものの色は変わりません。複数の場所を指すときに「赤がここ、青があそこ」と分けられます。マスクは常に墨色で、マスクを選んでいる間は色を選べません。
- 移動では、重なっているときはあとから書いたものを掴みます。枠は線の近くを押すと、枠の中に書いた線や文字より先に掴めます。枠の中の何も無いところを押しても枠を掴めます。移動している間は色を選べません（色を変えたいときは書き直してください）。
- 直前の操作を取り消したいときは **1つ戻す**、やり直したいときは **全部消す** を押します。1つ戻すは、書いた操作なら書いたものを消し、動かした操作なら動かす前の位置へ戻します。全部消した直後に押せば、消す前の書き込みが戻ります。
- 縮小画像では細かい場所を塗りにくいときは **拡大して書き込む** を押します。画面いっぱいに画像が開き、同じ道具で書き込めます。**書き込みを終える**（または Esc）で閉じると、書いたものはフォームの縮小画像にもそのまま残ります。
- 短く押しただけでは書き込みになりません（誤って点が増えないようにしています）。
- 書き込みは**送信するときに画像へ焼き込まれます**。書き込みが1つも無ければ、撮った画像はそのまま送られます。
- 枠・ペン・文字だけなら、焼き込みに失敗しても元の画像で送信を続けます。**マスクを含むときは送信を止めます**。元の画像を送ると、隠したはずの文字が届いてしまうためです。その場合は画像を削除するか撮り直してから送ってください。

### 1.1.2 一緒に送られる情報を送信前に確かめる

作成フォームの **自動マスキングの対象** の **詳細を確認する** を開くと、一緒に送られる情報と送られない情報が読めます。送った後は、詳細の **診断情報（マスク済み）** に次の要約が出ます。

- **ブラウザ**：OS とブラウザの種類（版は伏せます）
- **画面サイズ**：ウィンドウの大きさ（拡大率は落とします）
- **利用環境**：どの環境（ローカル・本番など）から送ったか
- **セッションID**：末尾 4 桁だけ
- **気になっている点**：記録のうち先に見るべき数件（最大3件）を、折りたたみを開かなくても読める位置に出します。重い種類（処理が止まった例外 → 通信の失敗 → エラー → 警告）を上に、同じ重さなら新しいほうを上に並べ、同じ内容が繰り返されている場合は1件に畳んで「N回起きています」と添えます
- **画面の裏で起きていた記録 N 件**：折りたたみを開くと、記録の1件ずつ（種類と要約）がそのまま読めます

この「気になっている点」と同じ数件が、Claude Code / Codex 用の指示文にも **先に見るべき記録** として載ります。送った人と直す人が同じところを見ることになります。

伏せ字の扱いは 1.3 と同じです。読んで「これは送りたくない」と思ったら、**画像を削除** を押すか、送らずに画面を離れてください。

### 1.2 送ったあとに出るもの

詳細の **Claude Code用のプロンプトをコピー** と **Codex用のプロンプトをコピー** のボタンを押すと、その要望を調べるための指示文がクリップボードに入ります。これを Claude Code や Codex に貼り付けると、要望の本文・そのとき起きていた不具合の記録・撮った画面を、AI が自分で取りに行って調査を始めます。

指示文の中には使い捨ての合言葉（トークン）が入っています。**合言葉の原文を画面が覚えているのは、送信直後か再発行の直後だけ**です。後日開いた依頼でコピーを押すと、コピーの前に自動で再発行します。画面にはこの動きと、前に配った指示文が失効することをボタンを押す前に示します。**このリクエストを再発行** を押しても同じです。どちらの場合も、**前に配った指示文はその時点で使えなくなります**。

削除した依頼の合言葉は、AI から取りに行っても「見つからない」になります（**元に戻す** で戻すと、同じ合言葉が再び使えます）。

合言葉には次の制限があります。

- 発行から **24時間** で切れます
- 取得できるのは **20回** までです

### 1.3 送られる技術的な記録について

要望には、そのとき画面の裏で起きていた失敗の記録が自動で添えられます。中身は「エラーの1行要約」「失敗した通信の宛先と結果」「起きた時刻」だけで、通信の中身（金額や明細）は最初から記録していません。

次の情報は伏せ字（`***`）に置き換えられます。

- 口座番号（「口座」に続く数字）・カード番号などの 10 桁以上の数字の並び
- 取引先名（登録済みの取引先の名前）
- 金額（`12,345円`・`¥12,345`・`12,345` のような 3 桁区切り）
- 個人名（口座の名義など登録済みの名前）
- メールアドレス
- 電話番号（`03-123-4567` のような区切り付きの形も）
- 住所（都道府県名に市区町村が続く形を番地まで。都道府県名だけの言及は残す）
- パスワード・ログインの合言葉などの秘匿値

ブラウザ側では、撮影用の複製で金額などの表示をできる限り伏字にし、本文と記録には辞書を使わない規則だけを掛けます。取引先名・個人名の辞書はブラウザへ渡さず、サーバが本文・関連ページ・診断を保存するたびに辞書を含む同じ規則を掛け直します。直接投稿された文章にも同じ規則が掛かります。画像のバイト列はサーバで再マスクしないため、送信前にプレビューを確認してください。

記録は直近 60 件・合計 32KB までです。それを超えた分は古いものから捨てられ、捨てた件数が画面に「上限を超えた N 件は省略されています」と出ます。

### 1.4 添付と依頼はいつ消えるか

依頼を **完了** にすると、そこから **30日後** に、その要望のスクリーンショットと技術的な記録が自動で消えます。

消えるのは添付だけです。**本文・状態・番号・アクティビティは残ります。** 何をいつ直したかの履歴は失われません。

完了にしていない依頼の添付は消えません（調査中に証拠が消えると本末転倒なため）。

**削除** した依頼は別の扱いです。削除から **30 日** を過ぎると、画像・本文・履歴を含めて依頼そのものが完全に消えます。30 日以内なら **元に戻す** で戻せますが、知らせを閉じた後に戻す画面はありません。

## 2. 運用向け

### 2.1 削除ジョブの相乗り先

改善リクエストの添付削除と、論理削除から 30 日を過ぎた依頼の完全消去には、**専用の Cron はありません**。既存の夜間メンテナンス（`packages/api/wrangler.jsonc` の `triggers.crons`、JST 03:00 の1本）から呼ばれる `scheduledMaintenance` の `Promise.allSettled` 配下に `runImprovementRetention` として相乗りしています。

Cron の設定・実行の全体像は `docs/ci-cd-operations.md` が正本です。ここではこのジョブに固有の点だけを書きます。

- 1 回の実行は D1 を **4 本** だけ使います（`scheduled-maintenance-budget.ts` の `improvement_retention: 4`）。内訳は、対象の検索 1 本（完了から 30 日の添付と、削除から 30 日の依頼を 1 つの `UNION ALL` で最大 500 件）、添付の失効の集合 UPDATE 1 本、完全消去の DELETE 1 本、孤児照合 1 本です。
- 夜間全体の予算は `PLAN_MAX = 49`（Free の 50 に 1 本の余白）で、`scheduled-maintenance-budget.test.ts` が `total === PLAN_MAX` を固定しています。完全消去の 1 本を足すため、`audit_header_retention` を 3 本から 2 本に減らしました。削除前にバイト数を読む問い合わせをやめ、`DELETE … RETURNING` で消した行のバイト数を受け取って、削除前の値を「削除後 + 消した分」で復元します。記録される値は変わりません。
- 完全消去は、R2 の画像を先に消し、消せた依頼だけを D1 から消します。DELETE の条件に `deleted_at IS NOT NULL AND deleted_at <= 期限` を残すので、検索の後に **元に戻す** が入った依頼は消しません。アクティビティは外部キーの `ON DELETE CASCADE` で一緒に消えます。R2 の削除に失敗した依頼は D1 に残り、翌晩にもう一度対象になります。消した件数は `RETURNING` で数えます（D1 の `meta.changes` は CASCADE で消えた履歴まで数えるため）。
- 削除中の依頼は、完了から 30 日の添付失効の対象にしません（完全消去がまとめて消すため）。孤児照合は削除中の依頼も照合に含めます（画像を持っているので、外すと孤児と誤って消してしまうため）。
- R2の個別削除失敗は件数`failed`として返し、成功したIDだけを1本の集合UPDATEで失効させます。
  個別失敗行、または集合UPDATE自体が失敗した全行は`purged_at`がNULLのまま残り、翌日に冪等再試行されます。
  これは処理済みの件数結果であって、job-level rejectではありません。
- D1障害や孤児照合payload guardなどでjob自体がrejectした場合、backupを先に確定した後の残る7 jobは
  `Promise.allSettled`で最後まで実行・記録されます。その後`scheduledMaintenance`が内容を含まない
  `scheduled_maintenance_failed`をthrowし、Cron全体を失敗として観測可能にします。
- 改善要望のテーブルは `packages/api/src/store.ts` の `BACKUP_SNAPSHOT_SQL` に**含めません**。会計の正本ではないため、夜間バックアップの対象外です（`packages/api/src/improvement-backup-exclusion.test.ts` が固定しています）。
- 孤児照合はR2から最大300 keyだけを先に取得し、そのexact keyだけをJSON 1 bindでD1に照合します。
  300件は最大1024-byte keyが全て6倍へJSON escapeされても1,844,101 bytesで、D1の2,000,000-byte
  string上限を下回ります。実UTF-8 byte guardもbind前に行い、超過時はR2を削除せずjob-level rejectにします。
- R2の続きがある場合はopaque cursorだけを`improvements/`外のversion付きcheckpointへ保存し、
  次の夜間実行で次pageを1枚進めます。D1照合またはR2削除の失敗時はcheckpointを進めず同じpageを再試行し、
  末尾pageでcheckpointを消して次回は先頭に戻ります。cursorやR2 keyはログに出しません。

### 2.2 実行結果の確認手順

Worker のログに、このjobについて1回の実行につき1行だけ JSON が出ます。

```bash
pnpm --filter @kanjo/api exec wrangler tail --format json
```

```json
{ "level": "info", "job": "improvement_retention", "selected": 4, "purged": 3, "erased": 1, "failed": 0, "orphans": 0, "orphanScanned": 300, "orphanDeferredRecent": 0, "orphanHasMore": true, "orphanCycleCompleted": false }
```

| 項目 | 意味 | 異常のサイン |
| --- | --- | --- |
| `selected` | この実行で対象になった要望の件数 | 毎晩ゼロでない状態が続く＝削除が進んでいない |
| `purged` | 添付を消せた件数（完了から 30 日） | `purged + erased + failed` が `selected` と一致しない |
| `erased` | 依頼ごと完全に消した件数（削除から 30 日） | 削除した依頼があるのに 30 日を過ぎても 0 のまま |
| `failed` | R2 か D1 で落ちた件数 | 同じ件数が何日も続く（一時障害なら翌日ゼロに戻る） |
| `orphans` | D1 に対応する行が無い R2 オブジェクトを消した件数 | 継続して増える＝投稿処理が途中で落ちている |
| `orphanScanned` | 今回照合したR2 object数（最大300） | 孤児候補があるのに継続して0 |
| `orphanDeferredRecent` | 投稿途中を避ける5分猶予で今回は保留し、先頭に戻った次の巡回cycleで再訪する件数 | 同じ件数が長期間減らない |
| `orphanHasMore` | 次pageがあるか | `true`のまま長期間変化しない |
| `orphanCycleCompleted` | 末尾pageへ到達し、次回は先頭に戻るか | 長期間`true`にならない |

ジョブ自体が例外で落ちた場合は `{"level":"error","job":"improvement_retention","name":"..."}` が出ます。
backupは先に確定し、他の6つを含む残り7 jobも独立に完走します。全jobの結果を記録してからCronは
`scheduled_maintenance_failed`で失敗し、内部message・利用者情報・金融内容・R2 keyはログへ出しません。

### 2.3 失敗が続くときの切り分け

1. `failed` が続く場合、まず D1 側で対象が残っているかを見ます。

   ```bash
   pnpm --filter @kanjo/api exec wrangler d1 execute kanjo-db --remote \
     --command "SELECT COUNT(*) FROM improvement_requests WHERE deleted_at IS NULL AND status='done' AND purged_at IS NULL AND done_at < datetime('now','-30 days')"
   pnpm --filter @kanjo/api exec wrangler d1 execute kanjo-db --remote \
     --command "SELECT COUNT(*) FROM improvement_requests WHERE deleted_at IS NOT NULL AND deleted_at < datetime('now','-30 days')"
   ```

2. 件数が残っていれば R2 側の削除権限を疑います。`FILES` バインディングは `packages/api/wrangler.jsonc` にあります。
3. `orphans` が増え続ける場合は、投稿経路（R2 へ put → D1 へ insert）の途中で落ちています。`improvement_requests` への insert が失敗するログを探します。孤児は配置から5分が経過した後、夜間巡回がそのpageへ到達した際に自動で消えるため、手動削除は不要です。

本番 D1 への手動 `UPDATE` / `DELETE` は通常運用に含めません（`docs/ci-cd-operations.md` 10章と同じ扱い）。

### 2.4 配信と巻き戻し

migration `0057_improvement_request_screen.sql` は表を作り直し、状態の CHECK を `wontfix` から `reconfirm` へ張り替え、`seq`（番号）と `deleted_at`（論理削除）を足します。巻き戻しは対称ではありません。

- **配信の順序**: 夜間の Cron は schema guard の外で動くので、**Migrate → Deploy** の順で適用します。適用の前後で `SELECT count(*), count(screenshot_key), count(token_hash) FROM improvement_requests` を取り、件数・画像のキー・トークンの数が一致することを確かめます。
- **コードだけを戻したとき**: schema guard は「適用済みの番号が期待より新しい」ときも通すので、0056 前提の Worker は 0057 の表をそのまま使います。そのとき、(1) 作成は `seq` を渡さないので失敗し、(2) 削除中の依頼が一覧に戻って見え、完全消去も止まり、(3) 再確認の依頼は旧画面の知らない状態として出て、(4) 「対応しない」への変更は CHECK で失敗します。
- **戻す前に確かめること**: `SELECT status, deleted_at IS NOT NULL AS deleted, count(*) FROM improvement_requests GROUP BY 1, 2` で、再確認の依頼と削除中の依頼の件数を確かめます。0 件でなければ、上の表示の乱れを承知のうえでコードだけを戻すか、`docs/runbooks/prod-d1-schema-recovery.md` の手順（Time Travel の復元地点へ戻し、0056 前提の版をデプロイ）で表ごと戻します。表は手で 0053 の形へ戻しません。
- 画面・規則・判断の記録は `docs/improvement-screen/`（`design-decisions.md`・`rules.md`・`evidence.md`）にあります。
