# runbook: 総収支の『元に戻す』が効かないとき

対象: `/analysis/total-cashflow` で『元に戻す』を押したのに操作が戻らない、
または エラーが出る。

規則の正本は `docs/total-cashflow-screen.md` の BR-008。

## まず確認すること

エラーの文言で原因が分かれる。**文言が違えば対処も違う。**

| 画面に出た文言 | HTTP | code | 意味 |
|---|---|---|---|
| この操作は見つかりませんでした | 404 | `not_found` | その id の操作が自分の履歴に無い |
| この操作はすでに元に戻されています | 409 | `already_undone` | 二重送信。1 回分は戻っている |
| 取り消しそのものは元に戻せません | 409 | `not_undoable` | 『元に戻す』自体を戻そうとした |
| 別の更新と重なりました。もう一度お試しください | 409 | `stale_operation` | 直前の操作が入れ替わった |

## ケース 1: `already_undone` (二重送信)

### 何が起きているか

同じ操作 id を 2 回送った。回線が遅いときにボタンを 2 度押すと起きる。

### 対処

**何もしなくてよい。** 1 回分だけ戻っており、総額も件数も正しい。
画面を再読込すると導線が消える (戻せる操作がもう無い)。

### 確認

操作前の総額と、現在の総額が一致していること。
一致していなければケース 4 へ。

## ケース 2: `not_found` (古い表示から押した)

### 何が起きているか

画面を開いたまま別のタブや端末で操作すると、開いている画面が持っている操作 id が
すでに履歴の中で意味を失っていることがある。
これは**安全側の拒否**で、昔の操作を今になって戻してしまう事故を防いでいる。

### 対処

1. 画面を再読込する
2. 戻したい操作をもう一度、最新の状態から行う

再読込後は『元に戻す』の導線が消える (仕様どおり)。
戻したい判断がある場合は、その明細を開いて判定し直す。

## ケース 3: `stale_operation` (別の更新と重なった)

### 何が起きているか

『元に戻す』は**直前の 1 件**しか戻せない。
押そうとした操作より後に別の操作が入ると、その操作はもう「直前」ではなくなる。

別タブ、別端末、あるいは同じ画面で連続して判定したときに起きる。

### 対処

1. 画面を再読込する (**この code のときだけ再読込が必要**)
2. 履歴の一番新しい操作から順に戻す

### 確認

再読込後、『元に戻す』が指している操作が、戻したいものと同じか確かめる。
違うなら、それより新しい操作を先に戻す。

## ケース 4: 総額が合わない

上の 3 ケースに当てはまらず、総額が操作前と違う。

### 切り分け

1. **除外が原因か** — freee 除外一覧を開き、意図しない行が入っていないか見る。
   入っていれば復元する (復元も操作履歴に残る)。
2. **判定が原因か** — 判定は総額を変えない (BR-009)。判定だけが違っている場合、
   総額のずれは別の原因。
3. **取込が原因か** — 期間中に再取込していないか確認する。
   再取込後も判断は再適用されるが、明細そのものが増減していれば総額は変わる。

### 検算

API を直接叩けるなら:

```
GET /api/total-cashflow?from=YYYY-MM&to=YYYY-MM
```

`coverage` が次を満たしていること。

```
matched + freeeOnly + excluded === freeeTotal
```

満たしていなければデータ側の問題。`docs/runbooks/prod-d1-schema-recovery.md` へ。

## ケース 5: 復元の後で古い操作 id が残っている

### 何が起きているか

バックアップから復元すると `total_cashflow_operations` も復元時点へ戻る。
復元前に開いていた画面は、もう存在しない操作 id を持っている。

### 対処

復元したら**開いている画面をすべて再読込する**。
再読込しないまま押すと `not_found` (ケース 2) になる。データは壊れない。

## 仕組みの補足 (保守者向け)

### 「直前」の決め方

```sql
ORDER BY created_at DESC, id DESC
```

`id` を第二鍵に置いているのは、同じミリ秒に 2 行入ったときに
どちらが直前かが実行ごとに変わらないようにするため。

### 取消も 1 行として残す

取消は履歴から操作を消すのではなく、`undone_at` を立てたうえで
`kind = 'undo'` の行を足す。消す作りだと「なぜ値が戻ったか」が後から読めない。

その `undo` 行自体は取り消せない (`not_undoable`)。

### 判定の順序

`undoOperation` は「存在 → 取消済み → 取消行 → 最新か」の 4 段で判定する。
段ごとに画面へ出す言葉が違うため、まとめていない。

固定しているテスト: `packages/api/test/total-cashflow-operations.integration.test.ts`。
