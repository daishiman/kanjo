# T0. 30思考法レビュー — 照合作業場の改善

**実施日**: 2026-09-16 / **前提**: 既存成果物は削除せず、従来案を正解とみなさない状態から再評価した。

## 思考リセット後の第一印象

問題の中心は装飾不足ではなく、対応対象が0件のときに選択行まで消える状態設計、全件を再掲する下段、画面ごとに異なる件数定義、期間を先に切る照合順序だった。目標画像は会計ルールの正本ではなく、KPI・絞り込み・一覧・詳細・補助情報を一画面で結ぶ情報設計の基準として扱った。

## 30思考法の適用結果

| # | 思考法 | 検証結果 | 改善への反映 |
|---:|---|---|---|
| 1 | 批判的思考 | 目標画像の「MF未計上」をそのまま現仕様へ戻す前提を棄却 | MFのみは対応不要という現行会計ルールを維持 |
| 2 | 演繹思考 | 対応必要は未処理または要確認である | `actionRequiredCount = unprocessed + review` をcoreの正本化 |
| 3 | 帰納的思考 | 空の詳細・長大な下段・件数差は別々でなく同じ状態分散から発生 | 行・KPI・キューを同じreportから描画 |
| 4 | アブダクション | 右側が空く最善説明は「pending行だけをactiveにする」こと | 表示中の先頭行を安定した既定選択にした |
| 5 | 垂直思考 | 表面の余白問題から件数契約と期間境界まで掘り下げた | UIだけでなくcore/API/consumerを同時修正 |
| 6 | 要素分解 | 契約・期間・状態・選択・操作・応答・レスポンシブへ分解 | feature-localな8部品とAPI/modelへ分割 |
| 7 | MECE | 5状態と、理想/空/読込/部分/失敗/低速の6表示状態を網羅 | DOM/API/実描画テストへ各状態を固定 |
| 8 | 2軸思考 | 「freee候補の有無」と「対応状態」は別軸 | 排他的な候補有無絞り込みとstatus絞り込みを分離 |
| 9 | プロセス思考 | 絞る→選ぶ→根拠を見る→判断→結果/取消が最短 | 3列マスタ詳細と同一文脈のUndoに集約 |
| 10 | メタ思考 | スクリーンショット一致が目的化していた | 正しさを守ったうえで情報階層と密度を合わせた |
| 11 | 抽象化思考 | 本質は「照合表」ではなく「判断ワークスペース」 | KPI、master、detail、補助previewの4層に整理 |
| 12 | ダブル・ループ思考 | MFのみを要対応とする前提そのものを再検討 | 対応不要だが確認可能な情報として独立表示 |
| 13 | ブレインストーミング | 別画面化、巨大表、drawer、3列を比較 | 往復と重複が最小の3列を採用 |
| 14 | 水平思考 | 対応対象がなくても一致済み行は閲覧価値がある | pending 0件でも一覧・詳細を維持 |
| 15 | 逆説思考 | 全件を見せるほど全体を把握しにくい | 下段を3件previewに制限し、主一覧へ導線を置いた |
| 16 | 類推思考 | 審査キューやメール受信箱のmaster-detailに類似 | 左キュー・中央一覧・右判断の責務を固定 |
| 17 | if思考 | 空、部分、旧Worker、月境界、狭幅、低速を仮定 | fallback、全期間照合後の投影、レスポンシブ状態を追加 |
| 18 | 素人思考 | 「MFのみ」だけでは放置してよい理由が分からない | 「対応不要」と総収支へ計上済みの理由を併記 |
| 19 | システム思考 | 照合件数はハブ、サイドバー、月次クローズへ波及 | consumer全体を同一契約へ接続 |
| 20 | 因果関係分析 | 期間を先に切る→月境界候補消失→誤って未照合 | 全期間で照合してから選択期間へ投影 |
| 21 | 因果ループ | 判断保存→件数減少→進捗更新→次の判断という循環 | query invalidationとUndoを同じ操作系へ統合 |
| 22 | トレードオン思考 | 情報密度と可読性を同時に高められる | desktopは3列、狭幅は副次列を詳細へ段階開示 |
| 23 | プラスサム思考 | 一つの件数正本で利用者の信頼と保守性を同時改善 | web側の再計算を除去しAPI投影を再利用 |
| 24 | 価値提案思考 | 価値は見栄えより「迷わず1件を判断できる」こと | 根拠・一致度・主要操作を詳細に集約 |
| 25 | 戦略的思考 | 視覚修正より意味契約を先に直す方が手戻りが少ない | core→API→consumer→UIの順で実装 |
| 26 | why思考 | 空白を5回掘るとactive選択とpending定義の結合へ到達 | 選択状態を対応状態から分離 |
| 27 | 改善思考 | 1044行の単一画面は変更影響を読みにくい | Page/KPI/Workspace/Detail/Summary/Action/Feedbackへ分割 |
| 28 | 仮説思考 | 3列と短いpreviewなら判断時間と空白が減る | 5幅の実描画と主要ジャーニーDOMで検証 |
| 29 | 論点思考 | 真の論点は「信頼できる対応キュー」 | status、actionability、件数、期間の契約を優先 |
| 30 | KJ法 | 指摘を意味契約・情報設計・操作安全・品質ゲートへ集約 | 4群ごとに実装し最後に横断検証 |

## 検証4条件

| 条件 | 判定 | 根拠 |
|---|---|---|
| 矛盾なし | PASS | 5状態、MFのみ対応不要、件数定義を仕様/core/API/webで統一 |
| 漏れなし | PASS | 6表示状態、単件/一括/Undo、5幅、期間境界、旧応答fallbackを試験 |
| 整合性あり | PASS | `actionRequiredCount`、feature-local API/model、デザイントークンを正本化 |
| 依存関係整合 | PASS | core→API→hub/close status→各consumer→UIの順で契約試験を通過 |
