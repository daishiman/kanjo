# 体験設計メモ

## データ取込（代表画面）

- 使われる場面: ひとりの運用者が月次の収支ファイルをPCで数件まとめて取り込み、直近の結果と失敗だけを確認する。
- 中心対象: 取込ファイル。最頻操作は「ファイルを選ぶ」「失敗を見つけて再試行する」「不要な取込だけ安全に取り消す」。
- 成功時の感情: 何が反映され、何を直す必要があるかが一目で分かり、安心して画面を閉じられる。
- 起きてはいけないミス: 同月データの意図しない洗い替え、手修正の消失、対象を誤った一括削除。

### 情報設計

1. 取込作業を主役にし、`ファイルを選ぶ → 必要なら差分を見る → 取り込む` を先頭に置く。
2. 取込結果と履歴は、ファイル名・状態・行数を第一階層、期間・種別・日時を副情報にした、単一の面と境界線によるリストにする。件数内訳と失敗理由は開示し、再試行は常時見せる。
3. ファイルの取得方法は補助情報として畳む。期間を指定する低頻度の削除は履歴の後ろに畳んで置く。
4. 全件の入れ替えは新規取込と連続する別目的のため、取込枠の上部に「データを入れ替える」の独立dialog入口を1か所だけ置く。下部に全件削除の二重入口を作らない。
5. 削除を開いた後は、対象指定・事前確認・実行／取り消しの3段階を順に見せる。
6. 履歴行の `取り消す` は反映済みデータを消す操作、`履歴を削除` は失敗・重複の記録と不要原本だけを破棄する操作として、文言と確認内容を分ける。
7. 取込履歴からの取り消し確認は行の中に展開せず、独立したモーダルで行う。削除期間・種別を変更したら事前確認を破棄し、現在の条件での再確認を必須にする。

表示形式の6軸は、主目的=`探す・状態把握・件ごとに操作`、情報量=`4〜8項目`、件数=`〜100`、識別=`ファイル名と時刻`、関係=`時間順と状態遷移`、操作=`再試行・取り消し`。このため横長テーブルではなく、要対応を先頭にした境界線リストを採用する。表は同じ列を高速比較する場面ではなく、独立カードは件数が増えるほど境界が過剰になるため却下した。

### 状態と操作

- 理想: 要対応の取込が上に並び、状態・対象月・件数・次の操作が同じ位置で読める。
- 空: ファイル選択を1つの主要操作として提示し、履歴には次に起きることを1文で示す。
- ローディング: 履歴の面積を予約したスケルトンを出す。
- 部分: 1件でも間延びしない単一の履歴面にする。
- エラー: 失敗理由と「やり直す」を同じカードに置き、選択済みファイルは保持する。
- オフライン／低速: 読み込み失敗を明示し、再読み込みの操作を残す。
- hover/pressed/focus: 操作可能な要素だけに短い面・罫線・押下反応を付け、フォーカスは即時表示する。
- 展開: 取得方法・詳細件数・削除領域だけを標準の `details` で開示する。装飾目的の入場モーションは増やさない。
- 入れ替え: all preflight のMF明細・freee仕訳・MF資産残高の件数とサーバ導出期間を示し、「入れ替える」と入力するまで実行しない。freee/MF側の元データ・手入力現金/負債・設定は残し、取込履歴と削除記録も監査/undoのため残すと明記する。履歴の空/取得失敗に関係なく入口は常に表示し、成功後はファイル選択と30日undoを同じ場所に出す。
- 帳簿取消: `committed` かつサーバが active ownership または canonical 行参照を検出した履歴にだけ「取り消す」を出す。更新済み表示でも参照が残る場合は隠さない。
- 履歴破棄: `failed` / `duplicate` で、active・canonical・undo退避から参照されない履歴にだけ入口を出し、確認文で「帳簿データは変わらない」「共有中の原本は残す」を示す。`committed`（更新済みを含む）は provenance を完全に証明できる仕組みが入るまで対象外とする。処理後はその行を一覧から除く。
- やり直し中: 履歴から原本を取込枠へ戻した後は、同じ行の操作を「やり直しをやめる」に変える。その履歴を削除した場合は、実行待ちの原本もブラウザ上の選択から外す。
- 確認モーダル: 開いたら最初の操作へフォーカスを移し、`Escape` と「やめる」のどちらでも閉じる。閉じた時点で事前確認状態も破棄する。
- 処理中／完了／失敗: 対象の近くで文言と状態バッジを更新する。色だけでは伝えない。

### データライフサイクル

- 取込値と手修正は別枠のまま保持し、再取込でも明細IDが一致する手修正を上書きしない。
- 確定済み期間をマスタ変更で黙って再計算しない。取込前差分は強い変更だけを選択対象にする。
- 突合は正規化キー、画面のファイル名・取引先名は原本表記を使う。

### 要件フラグ

| フラグ | 判定 | 今回の差分 |
|---|---|---|
| 認証あり | ON | 既存認証を変更しない |
| AI機能あり | OFF | 追加なし |
| リアルタイム同期あり | OFF | 追加なし |
| メール送信あり | OFF | 追加なし |
| 公開フォームあり | OFF | 追加なし |

カラーは既存アプリの意味契約を継承し、操作色・成功・警告・危険を役割どおりに限定する。色の追加ではなく、順序・余白・タイポグラフィ・段階的開示で改善する。

## 支出照合（代表画面）

- 使われる場面: ひとりの運用者が月次取込後にPCで数分間、freeeとMoney Forwardの支出が二重になっていないか、帳簿へ未記帳の事業支出があるかを見る。
- 中心対象: 実際の支出。最頻操作は「帳簿と実態の差を見る」「未記帳のMF明細を仕分ける」「要確認の照合候補を原本で確かめる」。
- 成功時の感情: 税務の正本と現実の支出を混同せず、今やる一手が分かる。
- 起きてはいけないミス: 同一支出の二重計上、曖昧一致の勝手な統合、MFの未記帳額をfreee確定額と呼ぶこと、freeeの個人支出（事業主貸）を経費へ混ぜること。

### 情報設計

1. 月別の「帳簿確定」「未記帳」「実質支出」を同じ行で比較し、原本別の単純合算は出さない。
2. 帳簿確定はfreeeの事業経費のみ。未記帳は「MFで事業」かつfreeeと厳密一致しない支出。実質支出は両者の合計とする。
3. 厳密一致は「支出・用途・日付・金額・厳格正規化した支払先」が同じで1対1、かつMFの安定IDがある場合のみ自動照合する。
4. 複数候補、金額のみ、日付ずれ、支払先不明、用途の不一致、MF分割明細、不安定IDは統合せず「要確認」へ残す。この間は過少計上を避けるためMF側も実質支出に含める。
5. 照合結果はcanonicalを書き換えず毎回導出する。そのため取込の取消、30日undo、期間・種別削除、全件入れ替えの結果に自動追従する。
6. 明細の修正・個別削除・リセットは既存の「公私仕分け」、取込単位の取消は「データ取込」へ接続し、照合画面に第二の削除実装を作らない。

表示形式の6軸は、主目的=`突き合わせる・比較する`、情報量=`月1行に4値`、件数=`月数分`、識別=`月と金額`、関係=`同一支出の状態遷移`、操作=`絞り込み・修正先へ移動`。主骨格は数値KPI3つ+月別比較表、要確認は一覧では事実3項目までとし詳細で展開する。独立カード列は同じ数字の縦比較が遅くなるため却下する。

### 状態と操作

- 理想: 実質支出が二重なしで見え、未記帳か要確認の件数から次の画面へ一手で進める。
- 空: freee/MFのどちらが足りないかと「データ取込へ」を出す。
- ローディング: 月別表の面積を予約する。
- エラー: 読み込み直しを残し、数字を0と表示しない。
- 要確認: 金額・日付の事実と、自動照合しなかった理由を一組で示す。「公私仕分けで直す」と「取込を取り消す」を詳細内の導線にする。
- サブスク: 実質支出だけから毎回導出し、登録支払先・候補ともfreee/MFを同じ照合ルールで扱う。
