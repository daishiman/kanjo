# 体験設計メモ

## 全画面共通シェルと全体期間

- 使われる場面: ひとりの運用者が月次作業中にPCとタブレットを往復し、取込・整理・確認・計画の20画面を同じ期間のまま移動する。
- 中心対象: 月次クローズの現在地。最頻操作は「次の画面へ移る」「1・2・3年の比較期間を変える」「未記録とデータ鮮度を確かめる」。
- 成功時の感情: どの画面でも同じ位置を見れば現在地・期間・データ状態・次の移動先が分かり、安心して作業を続けられる。
- 起きてはいけないミス: 画面遷移で対象期間が外れる、別期間の数字だと気づかず判断する、ログイン前に業務ナビが操作できるように見える。

### 情報設計

1. サイドバーはルートの種類ではなく、月次業務の順序 `取込 → 整える → 確認 → 計画`で束ねる。支出分析の5切口は親の直下に置き、名前から直接移動できる状態を保つ。
2. 固定ヘッダーは `現在地 / 全体期間 / データ状態 / 共通操作` の4群とする。PCは64pxの1行、狭幅は優先度の低い詳細をサイドバーへ重ねて本文の高さを守る。
3. 期間は `1年 / 2年 / 3年` を一手で選び、全期間・年指定・開始終了月は `任意` で開示する。現在の `localStorage` 保持とAPIクエリ契約は変えない。
4. 月次進捗は保存済みを推測しない。ルートから決まる現在ステップと、APIが返す未記録月数・取込履歴の最新時刻だけを表示する。
5. ログイン前は同じ骨格を出すが、業務ナビと期間・検索・出力はロック表示にし、リンクや擬似ボタンにしない。
6. 共通フッターは「外部送信なし / 税務上の正本はfreee / 毎晩バックアップ」を反復し、出典と復元画面だけを操作導線にする。

表示形式の6軸は、主目的=`移動・状態把握`、情報量=`1項目あたり1〜3`、件数=`20画面`、識別=`業務名と位置`、関係=`月次の順序と親子階層`、操作=`画面移動・期間切替`。このためPCは階層リストの220pxサイドバー、タブレットは68pxレール、モバイルは下部タブ+ドロワーを採用する。上部ナビは20画面を群と階層のまま描けず、ページ固有ナビは期間とデータ状態を画面ごとに覚え直させるため却下した。

### 共通状態と見た目

- 全画面の対象は固定ヘッダーと固定サイドバー。ページ本文の主要操作は画面ごとに異なるため、共通フッターに重複させない。
- カラーは正式デザインのブランド上書き。`primary=#14353D`を骨格と操作、`accent=#087F78`を選択と実行中の状態、アンバー/赤/緑を注意/危険/成功に限定する。ブランド色を本文全体へ敷かない。
- ロゴ原本は無いためテキストロゴ `Focus Ledger`を採用。Light固定の既存テーマを維持し、今回はテーマ機能を追加しない。
- hoverは操作できる要素の面と罫線だけを90〜140msで変える。pressedは90ms、focusは即時の2pxリング、popoverは140ms、ページ入場は200ms。`prefers-reduced-motion` で全装飾動作を停止する。
- 読込中は同面積のプレースホルダ、取込が無い場合は `未取込`、取得失敗は `確認できません`と再読込を表示し、0と未取得を同じ表示にしない。

### 入力作法

- ページ固有のフォーム契約は既存のまま。共通期間は選択即時反映、`1/2/3年` は1操作、任意の開始/終了月は入力中も保持し、始点が終点より後の間はAPIに無効値を送らない。

### 要件フラグ

| フラグ | 判定 | 今回の差分 |
|---|---|---|
| 認証あり | ON | 既存のパスワード / Cloudflare Access認証は変更せず、ログイン前シェルの表示だけを追加 |
| AI機能あり | OFF | AI分析画面の機能・API・コストは変更しない |
| リアルタイム同期あり | OFF | 追加なし |
| メール送信あり | OFF | 追加なし |
| 公開フォームあり | OFF | 追加なし |

## サブスク詳細 — 取引履歴と統合先登録

- 使われる場面: 一覧で見直し候補を開いた運用者が、元取引の表記と金額を確認し、未登録候補を既存または新規の統合先へ結び付ける。
- 中心対象: 選択中サブスクの判断根拠。最頻操作は「利用期間と支払規模をつかむ」「全履歴を確認する」「統合先を選ぶ」。
- 成功時の感情: 一覧の文脈を失わず、取引名を最後まで読んで統合先をその場で確定できる。
- 起きてはいけないミス: 省略記号だけで異なる取引を同一視する、新規登録後に別の統合先を選ぶ、重複した統合先を増やす。

### 情報設計

1. 狭い詳細railは直近3件の日付・取引名・ソース・金額を要約し、全文が必要な全件履歴は同じ画面上の広いdialogへ段階的に開示する。
2. dialogは先に `確認できる利用期間 / 支払い実績 / 合計支払額 / 支払い月あたり平均` の4項目を見せ、その下で取引明細を確認できる構造にする。同じ金額になりやすい1回平均は置かない。
3. 利用要約は対象期間内の全履歴から画面側で算出する。利用期間は最古日〜最新日、支払い実績の月数は支払いがあった年月の重複なし件数、月平均の分母もその支払い月数とする。契約開始・終了・連続利用とは断定しない。
4. dialogのPC表示は4列の比較表、モバイル表示は1取引1行の縦リストにする。取引名は省略せず折り返し、日付・ソース・金額も同じ取引の中で読める状態を保つ。
5. 未登録候補の `統合先` 直下に `新しい統合先を登録` を置く。名称は必須・120文字以内、既存重複は登録せず上の選択肢へ案内する。
6. 作成経路は既存の「候補として採用」と同じ `POST /sub-vendors` に集約する。成功時は候補一覧の再取得完了後、返却されたIDを統合先として自動選択する。

表示形式の6軸は、主目的=`根拠を読む・統合先を確定する`、情報量=`1取引4項目`、件数=`直近3件〜期間内全件`、識別=`取引名・日付・ソース`、関係=`選択中候補に属する時系列`、操作=`全件表示・既存選択・新規登録`。このため常設railの拡幅や別ページ遷移ではなく、要約rail+広いdialogを採用する。常設拡幅は一覧比較領域を奪い、別ページは候補選択の文脈と戻り位置を失うため却下した。

### 状態と操作

- dialog: 開いたら見出しへフォーカスを移し、`Escape` または「閉じる」で閉じ、入口へフォーカスを戻す。背景はnative dialogのmodal状態で操作対象外にする。
- 新規登録: 入口から入力欄へフォーカスを移す。「やめる」で入力を閉じ、再生成された入口へフォーカスを戻す。
- 処理中: 登録ボタンを無効にして「登録中…」と表示する。成功は選択完了を近接表示し、失敗時は入力値を保持する。
- 重複: 409を入力直下へ表示し、登録済み候補を上のselectから選ぶよう案内する。
- 空: 取引が無い場合は全件dialog入口を出さず、「期間内の取引はありません」と明示する。
- 1件: 利用期間はその1日、支払い実績は1か月・1件、合計と支払い月あたり平均は同額として表示する。

## 支出分析ハブ

- 使われる場面: 月次確認を行う一人の運用者が、5つの分析から先に見る場所をPCまたはタブレットで決める。
- 中心対象: 現在の収支と、5つの分析ルートの状態・優先度。最頻操作は「説明を選ぶ」「詳細を開く」「ブラウザの戻るで比較に戻る」。
- 成功時の感情: 数字をすべて読まなくても、今見る一手とその理由が分かる。
- 起きてはいけないミス: 説明を選んだだけで遷移したと誤解する、データ未取得を0円と解釈する、保存後も古い要確認件数が残る。

### 情報設計

1. 上から `判断の問い → 5視点 → 3 KPI+純収支説明 → ルート比較+選択説明 → 5段の読み順 → 主要CTA` の順に読む。ページの `h1` は問いを1件だけ置き、「支出分析」と二重にしない。
2. ルート比較はPCで `段階 / 分析の視点 / 目的 / 現在の状態 / 優先度 / 次の操作` の6列表。狭幅は同じ項目をカードで上から読み、ページ全体は横スクロールしない。
3. 「説明を見る」は同じページの選択、「○○を開く」は詳細ページへの遷移とし、文言・見た目・ARIAを分ける。主要CTAは1クリックで選択中の詳細へ進む。
4. `ANALYSIS_TABS` をタブ・ルート表・説明パネル・読み順・CTAの共通メタデータとし、同じ説明の別定義を作らない。

### 状態と遷移

- ローディング: KPI領域の面積を保ち、各ルートに「集計中」を出す。
- 取得失敗: 数値を0にせず、「取得できません」と局所の「もう一度読み込む」を出す。詳細へのリンクは残す。
- 空: KPIを0円と表示せず、「データを取り込む」を出す。
- 成功: 3 KPI、前期間比、各ルートの状態と優先度をAPIの値で表示する。
- 遷移: PUSHは先頭へスクロールし、描画後の見出しへフォーカスを移す。Back / Forwardはスクロール復元を上書きせず、deep linkとリロードで同じ詳細を再現する。

## データ取込（代表画面）

- 使われる場面: ひとりの運用者が月次の収支ファイルをPCで数件まとめて取り込み、直近の結果と失敗だけを確認する。
- 中心対象: 取込ファイル。最頻操作は「ファイルを選ぶ」「失敗を見つけて再試行する」「不要な取込だけ安全に取り消す」。
- 成功時の感情: 何が反映され、何を直す必要があるかが一目で分かり、安心して画面を閉じられる。
- 起きてはいけないミス: 同月データの意図しない洗い替え、手修正の消失、対象を誤った一括削除。

### 情報設計

1. 取込作業を主役にし、`ファイルを選ぶ → 必要なら差分を見る → 取り込む` を先頭に置く。
2. 取込結果と履歴は、ファイル名・状態・行数を第一階層、期間・種別・日時を副情報にした、単一の面と境界線によるリストにする。件数内訳と失敗理由は開示し、再試行は常時見せる。
3. ファイルの取得方法は補助情報として畳む。期間を指定する低頻度の削除は履歴の後ろに畳んで置く。
4. 全件の入れ替えは新規取込と連続する別目的のため、取込枠の上部に「データを入れ替える」の独立dialog入口を1か所だけ置く。下部に全件削除の二重入口を作らない。
5. 削除を開いた後は、対象指定・事前確認・実行／取り消しの3段階を順に見せる。
6. 履歴行の `取り消す` は反映済みデータを消す操作、`履歴を削除` は失敗・重複の記録と不要原本だけを破棄する操作として、文言と確認内容を分ける。
7. 取込履歴からの取り消し確認は行の中に展開せず、独立したモーダルで行う。削除期間・種別を変更したら事前確認を破棄し、現在の条件での再確認を必須にする。

表示形式の6軸は、主目的=`探す・状態把握・件ごとに操作`、情報量=`4〜8項目`、件数=`〜100`、識別=`ファイル名と時刻`、関係=`時間順と状態遷移`、操作=`再試行・取り消し`。このため横長テーブルではなく、要対応を先頭にした境界線リストを採用する。表は同じ列を高速比較する場面ではなく、独立カードは件数が増えるほど境界が過剰になるため却下した。

### 状態と操作

- 理想: 要対応の取込が上に並び、状態・対象月・件数・次の操作が同じ位置で読める。
- 空: ファイル選択を1つの主要操作として提示し、履歴には次に起きることを1文で示す。
- ローディング: 履歴の面積を予約したスケルトンを出す。
- 部分: 1件でも間延びしない単一の履歴面にする。
- エラー: 失敗理由と「やり直す」を同じカードに置き、選択済みファイルは保持する。
- オフライン／低速: 読み込み失敗を明示し、再読み込みの操作を残す。
- hover/pressed/focus: 操作可能な要素だけに短い面・罫線・押下反応を付け、フォーカスは即時表示する。
- 展開: 取得方法・詳細件数・削除領域だけを標準の `details` で開示する。装飾目的の入場モーションは増やさない。
- 入れ替え: all preflight のMF明細・freee仕訳・MF資産残高の件数とサーバ導出期間を示し、「入れ替える」と入力するまで実行しない。freee/MF側の元データ・手入力現金/負債・設定は残し、取込履歴と削除記録も監査/undoのため残すと明記する。履歴の空/取得失敗に関係なく入口は常に表示し、成功後はファイル選択と30日undoを同じ場所に出す。
- 帳簿取消: `committed` かつサーバが active ownership または canonical 行参照を検出した履歴にだけ「取り消す」を出す。更新済み表示でも参照が残る場合は隠さない。
- 履歴破棄: `failed` / `duplicate` で、active・canonical・undo退避から参照されない履歴にだけ入口を出し、確認文で「帳簿データは変わらない」「共有中の原本は残す」を示す。`committed`（更新済みを含む）は provenance を完全に証明できる仕組みが入るまで対象外とする。処理後はその行を一覧から除く。
- やり直し中: 履歴から原本を取込枠へ戻した後は、同じ行の操作を「やり直しをやめる」に変える。その履歴を削除した場合は、実行待ちの原本もブラウザ上の選択から外す。
- 確認モーダル: 開いたら最初の操作へフォーカスを移し、`Escape` と「やめる」のどちらでも閉じる。閉じた時点で事前確認状態も破棄する。
- 処理中／完了／失敗: 対象の近くで文言と状態バッジを更新する。色だけでは伝えない。

### データライフサイクル

- 取込値と手修正は別枠のまま保持し、再取込でも明細IDが一致する手修正を上書きしない。
- 確定済み期間をマスタ変更で黙って再計算しない。取込前差分は強い変更だけを選択対象にする。
- 突合は正規化キー、画面のファイル名・取引先名は原本表記を使う。

| メール送信あり | OFF | 追加なし |

## 支出照合（代表画面）

- 使われる場面: ひとりの運用者が月次取込後にPCで数分間、freeeとMoney Forwardの支出が二重になっていないか、帳簿へ未記帳の事業支出があるかを見る。
- 中心対象: 実際の支出。最頻操作は「帳簿と実態の差を見る」「未記帳のMF明細を仕分ける」「要確認の照合候補を原本で確かめる」。
- 成功時の感情: 税務の正本と現実の支出を混同せず、今やる一手が分かる。
- 起きてはいけないミス: 同一支出の二重計上、曖昧一致の勝手な統合、MFの未記帳額をfreee確定額と呼ぶこと、freeeの個人支出（事業主貸）を経費へ混ぜること。

### 情報設計

1. 月別の「帳簿確定」「未記帳」「実質支出」を同じ行で比較し、原本別の単純合算は出さない。
2. 帳簿確定はfreeeの事業経費のみ。未記帳は「MFで事業」かつfreeeと厳密一致しない支出。実質支出は両者の合計とする。
3. 厳密一致は「支出・用途・日付・金額・厳格正規化した支払先」が同じで1対1、かつMFの安定IDがある場合のみ自動照合する。
4. 複数候補、金額のみ、日付ずれ、支払先不明、用途の不一致、MF分割明細、不安定IDは統合せず「要確認」へ残す。この間は過少計上を避けるためMF側も実質支出に含める。
5. 照合結果はcanonicalを書き換えず毎回導出する。そのため取込の取消、30日undo、期間・種別削除、全件入れ替えの結果に自動追従する。
6. 明細の修正・個別削除・リセットは既存の「公私仕分け」、取込単位の取消は「データ取込」へ接続し、照合画面に第二の削除実装を作らない。

表示形式の6軸は、主目的=`突き合わせる・比較する`、情報量=`月1行に4値`、件数=`月数分`、識別=`月と金額`、関係=`同一支出の状態遷移`、操作=`絞り込み・修正先へ移動`。主骨格は数値KPI3つ+月別比較表、要確認は一覧では事実3項目までとし詳細で展開する。独立カード列は同じ数字の縦比較が遅くなるため却下する。

### 状態と操作

- 理想: 実質支出が二重なしで見え、未記帳か要確認の件数から次の画面へ一手で進める。
- 空: freee/MFのどちらが足りないかと「データ取込へ」を出す。
- ローディング: 月別表の面積を予約する。
- エラー: 読み込み直しを残し、数字を0と表示しない。
- 要確認: 金額・日付の事実と、自動照合しなかった理由を一組で示す。「公私仕分けで直す」と「取込を取り消す」を詳細内の導線にする。
- サブスク: 実質支出だけから毎回導出し、登録支払先・候補ともfreee/MFを同じ照合ルールで扱う。
