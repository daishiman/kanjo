統合で消えた画面の`taskDetail`(色の凡例、判定基準など)は`ANALYSIS_TABS`へそのまま移し、タブごとの折りたたみ説明として表示している。用語ホバーの総数は`route-task-detail.test.tsx`が`APP_ROUTES + ANALYSIS_TABS`で数える。**画面を減らすときに説明文ごと捨てない**、というのがこの検査の意味である。

## 決定の更新(2026-08-30 / feat-transaction-split-readability)

明細の分割記帳で**科目が読めない・選べない**という指摘を受けた判断。ここでも過去の行は消さない。

| 更新した判断 | これまで | 2026-08-30の決定 | 変更した理由 |
|---|---|---|---|
| 分割エディタの科目パネル | `CategoryPicker`の`.cat-panel`を`position: absolute`で浮かせる(全画面共通) | **分割エディタの中だけ`position: static`にして、その場に開く** | 浮かせた要素は「一番近いスクロール祖先」で切られる。分割の表は`.scroll-x`(内側)と`.card.scroll-x.classify-table-card`(外側)に二重で囲われていたため、460pxのパネルが2〜3行ぶんの小窓に押し込まれ、その中をスクロールして選ぶ状態になっていた |
| 分割の表の囲い | `.scroll-x`(`overflow: auto` + `max-height`) | `.split-lines`(スクロール枠を作らない) | 分割エディタは元の明細表(`min-width: 1160px`)の中に展開される。横幅はすでに確保されており、内側でもう一度スクロール枠を作る必要がない。枠を作る代わりに、パネルが切れないほうを取った |
| 科目列の幅 | 内容なり(閉じているとき約150px) | 開く前から`480px`で固定確保 | 開いた瞬間に列が伸びると、隣の金額欄が動いて押し間違える。`.cat-detail { min-height: 72px }`(触れた科目の説明で高さを固定する)と同じ考え方を、縦だけでなく横へも適用した |

### 浮かせるのをやめた代わりに失ったもの

パネルを開くと**行の高さが伸び、下の行が下がる**。`.cat-picker`のコメントが元々警告していた挙動そのものである。分割エディタでは、下の行が動くことより「何を選んでいるか読めない」ことのほうが致命的だと判断して、この副作用を受け入れた。他の画面(仕分け一覧・設定)のピッカーは浮かせたままにしてある。

### この決定を古びさせないために

`packages/web/scripts/check-mobile-layout.mjs`の不変条件9に、**開いた分割パネルが分割エディタ内部の`overflow`で切られていないこと**を実描画で固定した。外側の明細一覧は意図したスクロール領域なので検出対象から外し、以前パネルを小窓にしていた内側だけを見る。将来ここへ`overflow`を足すと、実ブラウザ検査が落ちる。

- `staleTime`はアプリ共通値と同じ30秒。分類・分割・予算は`invalidateAnalysisDerived`、総収支の判定・freee除外は`invalidateAnalysisHub`を成功時に呼び、保存後は期間別の`['analysis-hub']`全てを古い状態にしない。

### この決定を古びさせないために

- `analysis-hub.dom.test.tsx`「ハブ表示中は集約 API 1 本だけを呼び、5 タブの API を呼ばない」が、集約APIの呼出し1回と5タブAPIの呼出し0回を固定する。queryKeyを分ける、ハブからタブAPIを呼ぶ、のどちらでも落ちる。
- 同ファイルの「サイドバーの要確認バッジ」2件が、件数の一致・0件で出さないこと・リンク名がタブ名のままであることを固定する。0件でも出す/全視点に出す/件数を固定、の3変異で落ちることは実測してある。

### 保存と状態遷移

- **下書き**: 入力が止まってから 800ms 後に端末へ残す(v1、30 日で消える)。再読込すると戻る。保存済みの値に戻したとき、保存に成功したとき、リセットを確定したとき、ログアウトしたときに消す。
- **保存バー**: 画面の下端に sticky で置く。変更があるときは『未保存 N項目』と『変更した設定を保存してください。』、無いときは『未保存の変更はありません。』を出す。件数はフィールド単位で数え、行の追加・削除は 1 行で 1 項目、並べ替えは動いた行ごとに 1 項目。入力に誤りがあると『入力内容を確認してください。』を出し、保存を止める。ボタンは『変更をリセット』『設定を保存』(送信中は『保存中…』)。成功したら『設定を保存しました。』を出す。
- **1 回の保存**: `PUT /api/settings/screen` を 1 回送る。本文には `baseSavedAt` と、変更した節だけを入れる。
- **409**: 他で更新されていたら『他の画面で更新されました』を出して取り直す。400 は『設定を保存できませんでした。入力内容を確認してください。』、413 は『保存する内容が大きすぎます。』を出す。この 2 つと競合には『再試行』を出さない。それ以外の失敗は『設定を保存できませんでした。時間をおいてもう一度お試しください。』と『再試行』を出す。
- **リセット**: 確認『未保存の変更（N項目）をすべて破棄しますか？』を出す。確定ボタンは『破棄する』(処理中は『破棄しています…』)。
- **離脱**: 未保存のまま画面内リンクで外へ移るときは、『保存していない変更があります。移動しますか？ 下書きは端末に残ります。』を出す。ボタンは『移動する』(処理中は『移動しています…』)と『とどまる』。
- **読込の状態**: 失敗したら『設定を読み込めませんでした。』と『再読み込み』を出す。

### 375px の振る舞い

- 1023px 以下では、集計ルール・現金上書き・バックアップの 2 列を 1 列にし、説明パネルの sticky を外して表の下へ回す。
- 760px 以下(375px を含む)では、節ナビを折り返さず 1 行の横並びにし、上端に sticky のまま横へ送る。保存バーのボタンは横幅いっぱいに等分する。ページ全体には横スクロールを出さない。
- 375px の実ブラウザ(headless Chrome・API を CDP で差し替え)で `/settings` を開き、`documentElement` の `scrollWidth` と `clientWidth` がともに 375 で、はみ出す要素 0・実行時例外 0 を確かめた(2026-09-22)。
