AI分析画面(`/ai`)を作り直したときの判断の記録。対象は feature `feat-ai-analysis-screen`(Beads epic `kanjo-5ru`、子タスク SYS-AI-P01〜P13)。画面仕様の正本は `specs/spec-ai-analysis-screen.md`、アーキテクチャは `architecture/ai-analysis-*.md` の 8 章。規則と実装・テストの対応は [`rules.md`](rules.md)、受入の証跡は [`evidence.md`](evidence.md) にまとめた。

この文書は spec を置き換えない。spec が決めていない実装上の判断と、spec どうしの食い違いをどう決着させたかを残す。

## 4. body 上限: 固定 4 MiB の request budget(OI-02 / P03)

- レポート送信と貼り付けは、固定 4 MiB (4,194,304 bytes) の request budget で転送量を制限する。
- 大きな body で Worker のメモリを使い切らないよう、上限は `hono/body-limit` で **JSON を読む前に** 判定する。統合テストは、1 バイト超えで差し戻しの回数が増えないこと(= ハンドラまで届いていないこと)も確かめる。
- 4 MiB は個別 field が契約適合することを保証する値ではない。field・配列の長さと内容は `reportInputSchema` と `normalizeReport` が検証する。
- キャンセル・再実行は本文を使わない操作なので 4KB にした。
- request budget の正本は `packages/api/src/ai/contract.ts` の `REPORT_BODY_MAX_BYTES` とし、route・境界テスト・system-spec はそれを参照する。

## 5. 関数と経路の境界(P02)

- **段階**: `aiTaskStage(t, now)` は、`canceledAt` / `usedAt` / `expiresAt` / `rejectedAt` / `dataFetchedAt` と現在時刻を受け取り、`{ stage, progress }` を返す純関数。api の旧 `taskStatus` はこれに置き換え、旧来の `status` も `aiTaskLegacyStatus` で段階から導く。段階名と進捗 % は D1 に保存しない。
- **新しい経路は 3 本**: `POST /ai/tasks/:id/cancel`、`POST /ai/tasks/:id/retry`、`GET /ai/inventory`。
- **既存経路の変更**:
  - エージェントの認証 `agentGuard` は 0046 より前からある列だけを読む。migration の適用が遅れた D1 でも「認証してから schema の 503」という順が崩れないようにするため。
  - 段階による拒否は、schema の検査の後に全列を読む `agentTask` で行う。キャンセル・失敗・完了なら 401。
  - レポートの送信・貼り付けに body 上限(§4)を付けた。
- **0047 は不変条件**: `storeReport` は task claim と report INSERT を D1 batch にまとめる。版系列の `(user_id, report_type, period_from, period_to, version)` を一意にし、旧重複版は本文・参照を消さず作成順に連番化する。同一 task の旧重複は保持し、今後の INSERT を trigger で止める。
- **レポート保持はアーカイブ**: 画面から不可逆削除を外す。旧クライアントの DELETE は参照を壊さずアーカイブとして扱う。
- **0046 は追加だけ**: `seq` / `data_fetched_at` / `rejected_at` / `reject_count` / `canceled_at` の 5 列と、一意索引 `(user_id, seq)` を足す。既存の行は書き換えないので、既存の依頼は T-番号を持たず「旧 作成日」と表示する。SQLite の一意索引は NULL どうしを重複とみなさないので、`seq` の無い既存行が何行あっても衝突しない。

## 6. 境界のレビューと、集計値だけが外へ出ることの確かめ方(P03)

境界 4 件は、どれも「2 つの条件が同時に成り立ったとき、どちらを採るか」である。

| 境界 | 採った段階 | 理由 |
|---|---|---|
| 期限切れと受信が同時 | 完了 | 結果は届いている。期限は「結果が届かなかった」ことを表すための条件 |
| キャンセル後に期限切れ | キャンセル | 利用者の操作が先。期限切れで「失敗」に見えると、利用者が取り消したことが消える |
| 差し戻し後にデータを再取得 | 実行中 75% のまま | 進捗を戻すと、画面上で進捗が後退して見える |
| 期限ちょうどの時刻 | 待機中 | 期限は「その時刻まで有効」と読む。`agentGuard` も `expiresAt < now` で判定し、同じ側に倒す |

集計値だけが外へ出ることは、次の 2 つで確かめる。

- エージェント向けのデータは `packages/api/src/ai/dataset.ts` の `buildAgentData` だけが作る。この関数は月別・科目別などの集計を返し、明細の行を返す経路を持たない。
- 統合テスト「エージェントへ渡すデータ」は、架空の MF 明細に目印の摘要(`架空摘要-…`)と明細 ID(`ai-line-…`)を入れ、応答にどちらも出ないことを確かめる。同じ明細が科目の集計には入っていることも確かめ、データが渡っていないせいで通る検査にはしていない。検査が効くことは、応答に明細を混ぜる改変を一時的に入れて、このテストが落ちることで確かめた(改変は戻した)。

## 7. 実行の記録(P06〜P10)

実行の日時と結果は [`evidence.md`](evidence.md) に残す。ここには判断だけを書く。

- **P06 品質ゲート**: `pnpm test` / `pnpm typecheck` / `pnpm lint` / `pnpm skills:test` をすべて通す。緑にするために契約やテストの期待値を緩めない。
- **P07 受入の判定**: §1 の主張ごとに PASS / FAIL を付ける。一部だけ満たした受入は PASS と数えない。
- **P08 重複の監査**: 段階の条件分岐(`canceledAt` / `usedAt` / `expiresAt` を組み合わせた判定)が `packages/core/src/ai-screen.ts` の外に 0 件であること、旧 `pages/Ai.tsx` を直接参照するコードが 0 件であること(`pages/Ai.tsx` は `pages/ai/AiPage.tsx` を再 export するだけ)を `rg` で確かめる。
- **P09 配信前の検査**: `build:bundle` の直後に `check:js-budget` を測る(`build:artifact` は manifest を消すので後に回す)。キャンセル済みトークンの 401 は統合テストで、5 タブのキーボード操作(左右の矢印キー)は DOM テストで確かめる。
- **P10 配信してよいかの判断**: P06〜P09 がすべて緑で、§3 の推定値に利用者から異論が無いことを条件にする。判断の結果は [`evidence.md`](evidence.md) に書く。
- **P10 独立最終レビューの結論(2026-09-20)**: 独立したレビューの判定は「条件付きで配信可」。取り返しのつきにくい 3 点(段階の規則、他の利用者のデータに触れないこと、migration 0046 が既存行を書き換えないこと)は仕様どおりで、テストで固定されている。条件にされた指摘と、その扱いは次のとおり。
  - **採番の衝突で採り直しが働いていなかった(中)**: drizzle は D1 のエラーを `DrizzleQueryError` に包み、元の文言を `cause` へ移す。`String(e)` だけで `UNIQUE constraint failed` を探していたので、判定が常に偽になっていた。直し方は、`isUniqueViolation` が `cause` を辿ること。統合テスト「同時発行で (user_id, seq) に衝突したら 1 回だけ採り直し…」は、本物の D1 に先回りの行を入れて衝突を起こす。旧実装ではこのテストが 500 で落ちることを確かめた。**修正済み**。
  - **データが無いときの 400 も差し戻しとして数えていた(低)**: `recordReject` が、`no_data` の 400 を数えないようにした。**修正済み**。
  - **テストの抜け(低)**: 追加したテストは、実行中 50%・75% の取り消しと、取り消し後のトークンでのレポート送信が 401 になること、失敗した依頼の再実行、完了した依頼の再実行が 409 になること、貼り付けで上限ちょうどが保存されること。**追加済み**。
  - **段階/capability の集約**: エージェント送信・画面貼り付け・UI操作は core の `aiTaskStage` / `aiTaskCapabilities` を共有する。認証前の `agentGuard` は旧schemaでも読める列だけで本人確認し、schema guard 後の `agentTask` が capability を確定する。
  - **T-番号の再利用(低・仕様どおり)**: 最も大きい番号の依頼を消すと、次の依頼に同じ番号が振られる。`max(seq)+1` という仕様どおりの挙動なので、変えていない。番号を使い回さないようにするかは、利用者の確認事項として残す。
  - **freee memo の漏れ検査**: 架空の秘密メモを投入し、応答に出ないことを固定した。候補計算の SELECT 自体も必要列だけへ絞った。
- **P13 配信**: PR の merge と本番の Migrate / Deploy は、この作業では行わない(保留)。利用者が PR をレビューしてから行う。

## 8. spec と実装の差

- **使い方の説明の置き場所**: タイトル横の「AI分析の使い方」リンクが、同じ画面の折りたたみ手順を開く。画像の導線と、画面を離れず読める実装を両立する。
- **実ブラウザの図表検査の経路**: `check-financial-visuals.mjs` は、以前は一覧の「読む」ボタンを押してレポートを開いていた。新しい画面は URL で開くので、検査も URL で開く経路に直した(FR-14)。図は「根拠データ」タブにあるので、検査も `/ai/reports/:reportId?tab=evidence` を開く。
- **用語集**: 辞書の `reportType` / `reportVersion` は、新しい画面のレポート詳細のメタ情報と、一覧・版履歴の列見出しから `Term` / `termColumn` で引く。辞書からは外していない。
