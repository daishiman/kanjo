# 総収支画面 アーキテクチャ決定 (SYS-TCSCREEN-P02)

前提は `requirements-baseline.md`。ここでは「どの層に何を置くか」と「なぜその境界か」を決める。

## AD-001 画面の全ての数値は core の純関数から1回で得る

**決定**: API の GET は `totalCashflowScreen(all, allDeals, verdicts, exclusions, range)` という core の関数を1回呼び、
`summary` / `series` / `workbench` / `autoMatches` を含む応答を組む。web 側で合計や差分を計算し直さない。

**理由**: 画像の KPI・棒グラフ・3区分の件数・自動一致の候補は、すべて同じ消し込み結果から導かれる。
別々に計算すると、除外を1件足しただけで「KPI は変わったのに件数は前のまま」という不整合が起きうる。
1 関数 1 スナップショットにすれば、その食い違いが構造上起きない。

**捨てた案**: web で `months` から合計を出す。既存の9列表がそうしているが、
前年同期は当期と別の期間を消し込み直す必要があり、web に data set が無いため成立しない。

## AD-002 派生値は保存しない。保存するのは判定と除外と操作履歴だけ

**決定**: `summary` / `series` / `workbench` / `autoMatches` は永続化しない。
DB に持つのは `duplicate_verdicts`、`freee_deal_exclusions`、そして新設の `total_cashflow_operations` のみ。

**理由**: これが取消 (BR-008) を単純にする唯一の設計。
派生値を保存すると、取消は「判定を戻す」だけでなく「集計も戻す」必要が出て、2つの真実が同期を失う余地ができる。
派生値を持たなければ、判定と除外の行さえ操作前に戻せば総額は必ず一致する。AC-004 の不変条件はこの決定の系である。

## AD-003 前年同期比は「期間を12か月ずらして同じ計算をやり直す」

**決定**: `previousYearPeriod(range)` で開始月・終了月をそれぞれ12か月前へずらし、
同じ `applyPeriod` → `totalCashflowReport` を通す。前年側の全月がデータ範囲に無ければ `null` を返す。

**理由**: 前年の値を「月次系列から拾い直す」方式にすると、除外や判定の効き方が当期と揃う保証がない。
同じ関数を2回通せば、規則が1本しかないことが自明になる。
`analysis-hub` の `previousPeriod` (直前の同じ長さ) とは意味が違うので、名前を分けて共存させる (U-003)。

**コスト**: 消し込みが2回走る。対象は期間内の明細だけなので、月数に比例する線形コストに収まる。

## AD-004 操作履歴は追記のみ。取消も1行として残す

**決定**: `total_cashflow_operations` は `id / user_id / kind / items_json / item_count / undoes_id / undone_at / created_at`。
取消は対象行の `undone_at` を埋め、さらに `kind='undo'` の行を1本足す。`undo` 行自体は次の取消対象にならない。

**理由**: 「取り消せるのは最新の1件」を判定するには、履歴を消してはいけない。
消す実装だと、同時に2つ取り消したときにどちらが最新か判定できなくなる。
`undone_at` と `kind='undo'` の2つを持つことで、「何が起きたか」と「今取り消せるのは何か」を別々に読める。

**やり直し (redo) は持たない**: 仕様が持たないと決めている。`undo` 行から逆再生する誘惑があるが、
その間に別の判定が入ると復元先が定義できないため、持たない方が安全。

## AD-005 総収支の書込みルートを canonical mutation fence に載せる

**決定**: 判定・除外・除外解除・取消の4ルートを `CANONICAL_MUTATION_ROUTES` に加える。

**理由**: これらは正本 (freee 側の消し込み結果の解釈) を書き換える操作。
取込と同時に走ると、取込が作り直した明細に対して古い判定が書かれうる。fence が 409 を返して守る。
今まで載っていなかったのは、画面が単票操作しか持たず一括が無かったため。一括200件を入れる以上、載せる。

## AD-006 3表をバックアップ・復元の対象に加える

**決定**: `duplicate_verdicts` / `freee_deal_exclusions` / `total_cashflow_operations` を
`JSON_SNAPSHOT_MUTATION_CONSUMERS` と復元 payload に加える。

**理由**: 判定と除外は利用者が手で入れた情報で、取込データから再生成できない。
バックアップから外れていると、復元したときに総額だけ戻って判定が消え、画面の数字が前と変わる。

## AD-007 既存の9列月次表は残し、画像の構成を上に足す

**決定**: `TotalCashflowTable` (9列) は消さず、画面の下部へ折りたたみとして残す。
画像の KPI・グラフ・判定作業・除外一覧・自動一致の候補を上に置く。

**理由**: 9列表は「事業費へ寄せた件数」「要確認件数」を月ごとに見る検算用の面。
画像は「今日どれを判定するか」を決める作業用の面で、情報設計が別物。
どちらかに寄せると、片方の用途が失われる。

## AD-008 web の状態は TanStack Query のキャッシュ1本に寄せる

**決定**: 選択中の明細 id、フィルタ、検索語だけをローカル state に持つ。
件数・バッジ・進捗はすべてクエリ結果から導出する。書込み成功後は総収支と分析ハブを invalidate する。

**理由**: 判定を1件送ると、3区分の件数・KPI・自動一致の候補・サイドバーのバッジが同時に動く。
それぞれをローカルに持つと更新漏れが必ず出る。サーバの1スナップショットを唯一の真実にする。
