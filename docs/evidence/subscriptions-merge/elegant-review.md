# サブスク統合の再検証

対象は今回のワークツリーで開発中の `feat-subscriptions-merge` と既存の共通実装。
実データ・secrets・公開環境は対象外。成果物を保持して、過去の判断を正解と仮定せず読み直した。

## フェーズ1：俯瞰

サブスクの名寄せ、取り消し、書込みの順次処理が core → API → web にまたがる。
主要な境界は、保存する定義と実効的な照合一覧、書込みと読み取りの revision、
画面内の操作とサーバーの履歴、現行契約と過去の設計記録。
第一印象の懸念は操作型の二重定義、更新後の再取得範囲の重複、
既存タブ部品と画面専用実装の重複、仕様の複数文書への転記。
この俯瞰を終えてから3担当の並列分析を開始した。

## フェーズ3：改善と再検証

独立したAPI・core・web・文書の改善を並列に実施。公開操作型の共通化と統合検証は親担当。
大幅な構造変更を避け、既存の batch・fence・mutation scope の責務を維持する。
最大3サイクルまで。今回の改善とローカル検証結果を下記へ記録する。

### 完了判定

ユーザー指定の4条件は「矛盾なし・漏れなし・整合性あり・依存関係整合」。
機能目標O1〜O4とは別に評価する。ローカル検証とCI・公開の結果も区別する。
2026-10-01の完了指示を受け、提示済み推奨案の現行再推定を実装者判断で採用した。確認済みの対象範囲について判定を以下に示す。

| 条件 | 判定 | 根拠・残課題 |
|---|---|---|
| 矛盾なし | ローカル確認PASS | O1・AC-001を現行再推定へ統一。各月の実支払額保存はAC-002として区別。確認済み矛盾を修正。 |
| 漏れなし | ローカル確認PASS | 復元・再送・読取競合・別名照合・画面再取得と、異なる支払月・周期の回帰を追加し、数値契約を確定。 |
| 整合性あり | ローカル確認PASS | 公開操作型・照合・集計・タブを共有。型検査・lint・語彙検査が成功。 |
| 依存関係整合 | ローカル確認PASS | core→API→webの共有参照と、198ノード/198章のlineage検査が成功。 |

### 改善後の確認済み成果

- core：統合元正規名の完全一致を照合専用 `exactNames` に保持。保存集計・画面・統合投影の科目参照を `matchSubVendor` に集約。baseline の事業scope判定と保存別名の上限をAPIと共有。担当の全core検証は1,304件成功、既存6件skip。
- 共通契約：操作種別・取り消せない理由・公開操作レコードを `packages/core/src/subscription-operation.ts` に集約。APIの応答配列にも同じ型を付け、webの別定義を型参照へ置換。
- web：既存 `AccessibleTabs` に詳細タブを集約。名称上限と未編集時の最新値への同期、履歴取得失敗と再取得を追加。再取得範囲の同一定義を共有。
- web の成功mutation整理は履歴に同じoperation IDを確認できたものに限定。失敗・未確認・待機・処理中を保持し、再試行前の失敗行が復活する組は除去しない。
- web担当の回帰85件、診断受信3件、モバイル図表8件、型検査・Biomeが成功。
- 文書：specに現行契約を反映し、docsの型・詳細手順のコピーとarchitecture/tasksの重複を参照へ置換。文書担当の最終整理では34ファイル、差し引き465行を削減。ID・依存・凍結済みの質疑・過去の検証結果は維持。
- 補助テスト：runbooks、実データguard、GitHub scripts、seed-admin、skills、deliveryの全段成功。
- API：冪等照合に操作種別とcommandを含める。復元がサブスク状態に触れるときだけ古い統合のundoを遮断し、一般設定復元は阻害しない。読取の前後でrevision・writer・設定と取込の更新を照合し、競合時は不整合な内容を返さず409にする。GET同士は並列に読め、読取でwriter leaseを取らない。

### 確定した数値契約

最終支払月が異なる場合、年払いと月払いが混在する場合の2つの反例をcoreテストで固定した。
いずれも統合前の推定月額の和300に対し、現行の統合後再推定は200。
完了指示に基づき「再推定を維持して適用条件を仕様に明記する」を採用。
O1・AC-001、feature、architecture/tasks、現行system-specの要約を同期した。
各月の実支払額は保存し、推定値は統合後の明細から導出する。
推定規則と既存テスト期待値は変更せず、派生値を保存する状態を追加しない。
過去の質疑・承認・archiveの記録は当時の契約の証拠であり、現在の規範はspecの確定節に置く。
同じ支払月のfixture成功を、推定値の一般的な保存則の証明として扱わない。

契約確定後の再確認：`subs-screen-contract.test.ts` と `subs-contract.test.ts` の2ファイル100件成功。計算処理や期待値の変更は不要だった。lintの全段も成功した。
