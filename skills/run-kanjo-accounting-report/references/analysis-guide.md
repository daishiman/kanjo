# データの読み方と分析観点

## 1. 取得JSONのキー

| キー | 意味 |
|---|---|
| `period` | 対象期間。`from`/`to`(YYYY-MM)、`type`(`monthly` 月次 / `annual` 年次 / `longterm` 長期)、`label`、`requestedMonths`(指定した月の一覧)、`months`(そのうち取込済みの月)、`previous`(直前の同じ長さの期間)、`yearAgo`(1年前の同じ期間)。`previous.months` / `yearAgo.months` が空なら比較は「データ不足」 |
| `dataRange` | 取込済みデータの最初と最後の月・月数。指示文の期間より狭ければ、本文冒頭で「実データは○〜○の○ヶ月分」と明記する |
| `notes[]` | データ生成側からの注意書き。必ず読み、該当するものは本文へ反映する |
| `months` | 取込済みの全月(昇順)。全期間の傾向はこれを使う |
| `unrecordedExpenseMonths` | 事業経費が**未記帳**の月。この月の経費 0 は「支出なし」ではない。増減の比較対象から外す |
| `summary.current` / `previous` / `yearAgo` | 期間合計(売上・経費・利益・経費率・科目別経費・個人収入・個人支出・サブスク・記帳月数)。比較対象が無い側は `null` |
| `pl` | 損益(PL)観点。`current` に売上・経費・利益・経費率・固定費・変動費(科目の型から分類。`fixedAccounts` / `variableAccounts`)。`breakEven` は損益分岐点(固定費合計)と安全余裕率。`available: false` なら計算不能 |
| `bs` | 貸借(BS)観点。**現状は常に `available: false`**。`reason` に理由が入る(freee「取引」エクスポートに資産・負債・残高が無い)。BS の数字を作らない |
| `stats` | 統計分析の可否と結果。`recordedMonths`(記帳済み月数)/ `minMonths`(手法ごとの必要月数)/ `available`(手法ごとの可否)/ `accountProfiles`(科目別の平均・標準偏差・変動係数・傾き・固定費/準変動/スポットの型)/ `outliers`(|z|≥2 かつ 1万円超の外れ値)/ `expenseMovingAvg3`(3ヶ月移動平均)/ `expenseCv`(経費の変動係数) |
| `biz.revenue` / `biz.expenseTotal` | 月別の事業売上 / 事業経費合計(freee 帳簿) |
| `biz.expenseByAccount` | 勘定科目 → 月別金額 |
| `biz.byYear` | 年 → 売上・経費・利益(長期レポートの骨格) |
| `biz.kpi` | 平均売上・平均経費・直近経費・前月比(`expenseMom`)・前年経費・今年の年換算 など |
| `biz.yearTable` / `biz.yearTotals` | 科目別の前年実績と今年の年換算(`delta` は 1=100% の小数) |
| `biz.pareto` | 経費の大きい順と累積構成比(`cumShare`) |
| `personal.byMonth[月].expense` / `.income` | 個人支出(MF 明細のうち公私仕分けで「個人」。キーは大項目または大項目/中項目)/ 個人収入 |
| `personal.livingCost` | 生活費の大項目別(全期間の合計・月平均・年換算・構成比) |
| `personal.explainability` | 個人支出の説明可能率(未分類・カード引落不明を除いた割合) |
| `bizPersonal[月]` | MF 明細のうち「事業」と仕分けされた分の収入・支出(freee とは別集計) |
| `comparison` | 事業と個人を月別に並べた収支。`biz`/`personal` に合計・月平均・年換算 |
| `byOwner` | 個人分の名義別(`business`=事業 / `spouse`=妻 / `family`=家族 / `unset`=未設定)。`unmappedInstitutions` は名義未設定の金融機関 |
| `subscriptions.now` / `vendors` / `vendorTable` / `alerts` / `candidates` | 直近記帳月のサブスク合計・年換算・売上比 / ベンダー別月別支払 / ベンダー別の前年・年換算・直近月額・平均・支払月数 / 重複疑い・急増 / 登録外だが毎月続いている支払先(`score` 0〜100・`reasons`・`avgMonthly`・`activeMonths`/`spanMonths`・`accounts`) |
| `benchmarks` | 経費率・サブスク比率・安全余裕率・貯蓄率・食費比率・通信費比率の現在値と目安 |
| `charts[]` | **図表カタログの10枚(固定順・番号固定)をアプリが計算済み**。`id` `figure` `available` `reason` `monthsNeeded` `status`(`ok` / `source_missing` / `app_missing`)`data`(描画用の数値。AIはこれを読み解くだけで数値を作らない)。対応表は `chart-catalog.md` |
| `coverage[]` | 図ごとの `status` と `detail`。`app_missing` は `dataGaps` に書いて利用者へ伝える |
| `axes` | レポート・図に使ってよい切り口(項目・分類 / 区分 / 期間プリセット / 指標)。**ここに無い軸は作らない**(例: 決済状況は `settlement.available=false`)。詳細は `chart-catalog.md` §2 |
| `previousReports[]` | 同じ型の過去レポート(最新2件。再分析なら親レポートを含む)。`version`・`summary`・`keyFindings`・`reductionItems`・`needs` が入る |
| `supplement` | 利用者が画面で入力した補足情報(無ければ `null`)。数字の根拠に使ってよいが、データと矛盾するときはデータを優先し、その旨を書く |

金額はすべて円の整数。比率は 1=100% の小数(本文では % に直す: 0.123 → 12.3%)。

## 2. レポートの型ごとの重心(5節・10図は固定・重心だけ変える)

図は毎回同じ10枚(`chart-catalog.md` §1)。型で変えるのは**本文の重心と、どの図を主役として読み解くか**だけ。

| 型 | 期間 | 重心 | 主役にする図 |
|---|---|---|---|
| `monthly` 月次 | 1ヶ月 | その月に起きたこと。前月比・前年同月比、当月の外れ値、すぐ効く対策 | 図4(分布・外れ値)→ 図3(寄与度)→ 図10(名義別個人支出) |
| `annual` 年次 | 2〜13ヶ月 | 期間合計と月平均、前年同期比、季節性、固定費/変動費の構造、損益分岐点 | 図2(構成比)→ 図9(科目×月)→ 図6(固定費・損益分岐点) |
| `longterm` 長期 | 14ヶ月以上(最大61ヶ月) | 年ごとの推移、構造変化、トレンド、サブスクと名義別支出 | 図1(推移・四半期粒度)→ 図7(パレート)→ 図8(サブスク)→ 図9/10 |

- 図9は行内の濃淡で科目ごとの季節性・スポット月を読み、科目間の色の濃さは比較しない。主に`change`節へ置く。
- 図10は名義の帯の厚みの変化を読み、全件`unset`なら名義未設定として扱う。主に`split`節へ置く。

- 期間が取込済みデータより広いときは、`dataRange` を冒頭に書き、無い月を推測で埋めない。
- `available=true` の図はすべて本文で「図N」と参照し、`charts` に `caption`(15字以上)を付ける。出せない図は参照せず、`dataGaps` に「図N はあと◯ヶ月分で出せる」と1行。
- 本文と図の責務: **図が示す事実は図に任せ、本文はその図から何が言えるか(解釈)と何をするか(打ち手)を書く**(「図3が示すとおり、増加分の8割は外注費」)。

## 3. 分析のチェックリスト(節ごと)

### keyFindings(冒頭の要点サマリー)— 1件 = 事実 → 解釈 → 次のアクション
- 1件ごとに **`fact`(数値つきの事実)/ `basis`(どのキーからどう計算したか)/ `interpretation`(何を意味するか)/ `action`(次に何をするか)** の4欄を埋める。欠けると検査で落ちる。`expectedEffect` に期待効果(円・年換算)、`chart` に根拠の図の `catalogId`。
- `improvements`: 構造的に直すべき点(例: 経費率の上昇、特定科目の継続増)。`amount` は期間中の影響額か年換算。
- `wasted`: 使われていない・重複・目安超過など「無駄」と言える支出。
- `quickWins`: 利用者が今月中に実行できて金額が確定する対策。`expectedEffect` は削減見込み(年換算と明記)。
- 各1〜5件、`priority` を必ず付ける。**0件の区分は `notes.<区分>` に理由を10字以上**(「該当なし」で済ませない。何を確認して無かったのかを書く)。

### spend(何にいくら)
- 対象期間の事業経費合計・個人支出合計を先に置く(複数月なら合計と月平均)。
- 上位科目を構成比つきで並べる。`pareto.cumShare` が 0.8 を超えるまでの科目が「管理の主戦場」。
- `pl.current` の固定費/変動費を分けて言う。`stats.accountProfiles` の型(固定費/準変動/スポット)を使う。

### change(増減と要因)
- 比較対象は `summary.previous` と `summary.yearAgo`。**`null` なら「データ不足」**と書き、`needs` に「取込画面で○年○月分を取り込む」を入れる。
- 合計の差額と率 → 差額の大きい科目3〜5個 → その科目の月別推移で「一時的か継続的か」。`stats.outliers` に載る月は一時的な可能性が高い。
- `unrecordedExpenseMonths` に含まれる月は比較に使わない(理由を明記)。

### reduction(削減余地)
- 候補は「金額が大きい × 固定的 × 代替がある」順に `priority`。年換算金額・根拠(どの数字から)・注意(事業に必要な支出は削らない)。
- `benchmarks` で目安外の指標があれば、その指標を動かす科目を候補にする。
- 削れないもの(税金・社会保険・家賃など)は候補に入れず「固定で見直し対象外」と一言添える。

### split(事業/個人・事業/妻/家族)
- `comparison` から事業と個人の収支(合計・月平均)。個人の赤字を事業収入で埋めていないか。
- `byOwner` から事業/妻/家族。`unset` が大きい、または `unmappedInstitutions` があれば `needs` に `screen: "settings"` で名義割り当てを入れる。
- `bizPersonal` が大きい月は、MF 側で事業扱いの支出が freee に未記帳の可能性を指摘する(断定しない)。

### subscriptions(サブスク)
- `subscriptions.now` の合計・年換算・売上比を先に置く。`alerts` を必ず反映。
- 整理候補は「解約 / プラン変更 / 年払い切替 / 継続」の4区分で書き、理由を添える。
- `candidates` は登録されていない支払先のうち「サブスクらしい」順に並んだもの(採点: 連続率50点・金額の一定さ30点・科目がサブスク・通信20点)。`score` 70 以上を「登録漏れの可能性」として名指しし、`needs` に `screen: "subscriptions"` で「サブスク分析ページの候補一覧で『これはサブスク』を押す」を入れる。候補に入っているだけでサブスクと断定しない(`reasons` を添えて可能性として書く)。

## 4. 統計・PL・BS の扱い(できることだけ書く)

- **統計手法は `stats.available` が true のものだけ使う**。false の手法は本文で「この手法には `minMonths` ヶ月以上必要。あと○ヶ月分で分析可能」と書く(○ = minMonths − recordedMonths)。必要月数と根拠は §8。
- **PL(損益)**: `pl.current` と `pl.breakEven` の範囲で、収益性(利益・経費率)・費用構造(固定費/変動費)・損益分岐点・安全余裕率を書く。`breakEven.available` が false なら理由とともに省く。
- **BS(貸借)**: `bs.available` が false の間は資産・負債・現預金残高・資金繰りの数字を**一切書かない**。書くのは `bs.reason` の1行(「BSを出すには freee の試算表(貸借対照表)または残高のエクスポートを取り込む機能が必要」)だけ。`needs` にも 1件入れる(`screen: null`。現時点でアプリに取込機能が無いため)。

## 5. 前回レポート・補足情報の使い方

- `previousReports` があれば `followUp` を必ず書く。前回の `keyFindings.quickWins` と `reductionItems` を1件ずつ追い、「解消(数字で確認)/ 未実施 / 悪化」を判定する。判定できないものは「データでは確認できない」と書く。
- 前回の `needs` が今回のデータで解消されているか(例: 名義未設定が減ったか)も1行で触れる。
- `supplement` は根拠として引用してよい(「利用者の補足: 家賃は事業按分済み」)。データと矛盾するときはデータを優先し、矛盾を `dataGaps` に書く。

## 6. データ不足と `needs` の書き方

- `dataGaps`: 何が無いか(例: 2025-08 の個人支出)と、それにより何が言えないか(前年同月比)を1行で。
- `needs`: 同じ内容を「利用者がアプリで行う操作」に翻訳する。`action` は画面名と操作を1文で(「データ取込で 2025年8月の MF 明細を取り込む」)。`screen` は `report-schema.md` の画面 id から選ぶ。アプリで解消できないものは `screen: null`。

## 7. 言葉の規則(非エンジニア・非会計の読者向け)

- 専門用語は初出で括弧の言い換えを付ける: 固定費(毎月ほぼ同額で出るもの)/ 変動費(売上に連れて動くもの)/ 損益分岐点(ここまで売れば赤字にならない売上)/ 安全余裕率(売上がどれだけ落ちても赤字にならないか)/ 変動係数(ブレの大きさ。0.3 以上で大きい)/ 移動平均(直近数ヶ月のならした値)。
- 1文は短く。事実(数字)→ 解釈 → 打ち手 の順。断定できないことは「〜の可能性(根拠: …)」。

## 8. 判定に使う数値の閾値と根拠(再現性のために固定。AI が独自の閾値を作らない)

閾値はすべてアプリ側(`packages/core/src/analysis.ts` / `packages/api/src/ai/dataset.ts`)で計算済みで、GET 応答の `stats` / `subscriptions.alerts` / `benchmarks` / `axes.indicator` に結果が入る。AI は結果を読み、下表の言葉で説明する。同じデータからは同じ判定になる。

| 判定 | 閾値 | 根拠 | 応答のキー |
|---|---|---|---|
| 科目の型 | 変動係数(CV=標準偏差÷平均)**<0.6 固定費 / <1.5 準変動 / それ以上 スポット** | CV<0.6 は「月ごとのブレが平均の6割未満」で毎月ほぼ同額と言える範囲。1.5 以上はゼロの月が混じる散発的支出 | `stats.accountProfiles.*.type` |
| 外れ値 | **\|z\| ≥ 2 かつ 1万円超** | 正規分布なら ±2σ の外は約 4.6%。少額(1万円以下)はブレても意思決定に影響しないため除外 | `stats.outliers`、図4 の帯 |
| 外れ値・移動平均の必要月数 | **6ヶ月** | 平均と標準偏差を出すのに最低 6 点。3ヶ月移動平均を 3 点以上引ける最小 | `stats.minMonths.outliers` / `movingAverage` |
| トレンド(傾き) | **12ヶ月** | 季節の影響を1周含めて傾きを見るため | `stats.minMonths.trend` |
| 前年同月比 | **13ヶ月** | 対象月と前年同月の両方が必要 | `stats.minMonths.yearOverYear`、図5 |
| 季節性 | **24ヶ月** | 同じ月を2回観測して初めて「毎年」と言える | `stats.minMonths.seasonality` |
| 科目の上昇/低下シグナル | 傾き **>0.3**(上昇)/ **<−0.3**(低下)かつ平均 1万円超 | 傾き = 直近3ヶ月平均 ÷ それ以前の平均 − 1。3割超の変化を継続的とみなす。1万円以下はノイズ | `stats.accountProfiles.*.slope` |
| サブスク重複疑い | **中央値の1.8倍超 かつ 2万円超 かつ 中央値5千円超** | 同額の請求が同月に2件あると約2倍になる。年払い・少額を除外 | `subscriptions.alerts`、図8 |
| サブスク急増 | **中央値の3倍超 かつ 1.5万円超** | 値上げ(1.1〜1.5倍)ではなく契約追加やプラン変更の水準 | `subscriptions.alerts` |
| サブスク候補(登録漏れ) | **score 70 以上** | 連続率50点+金額の一定さ30点+科目20点。70 は「連続していて金額も安定」の最低ライン | `subscriptions.candidates` |
| 経費率 | 目安 **20〜40%** | 直近3ヶ月の事業経費平均 ÷ 売上のある月の平均売上。フリーランスの一般的な範囲 | `benchmarks.expenseRatio` |
| サブスク対売上比 | 目安 **15%以内** | 直近3ヶ月のサブスク平均 ÷ 平均売上 | `benchmarks.subsShare` |
| 安全余裕率 | 目安 **30%以上** | (平均売上 − 損益分岐点)÷ 平均売上。売上が3割落ちても赤字にならない水準 | `benchmarks.safetyMargin`、図6 |
| 貯蓄率(世帯) | 目安 **20〜30%**(下限 20%) | 家計の(収入 − 生活費)÷ 収入 | `benchmarks.saveRate` |
| 食費比率 | 目安 **15〜20%**(上限 20%) | 生活費に占める食費 | `benchmarks.foodShare` |
| 通信費比率 | 目安 **5%以内** | 生活費に占める通信費 | `benchmarks.telecomShare` |
| 損益分岐点 | 固定費(CV<0.6 の科目)の直近3ヶ月平均の合計 | 変動費を売上比例と見なす簡便法。売上のある月が3ヶ月未満なら `available=false` | `pl.breakEven`、図6 |
| パレートの区切り | 累積構成比 **80%** | 「上位2割の科目が経費の8割」の経験則。80% までの科目を見直し対象にする | `biz.pareto.cumShare`、図7 |
| 図の粒度 | 月次は最大 **36ヶ月**、超えたら四半期 | 36本を超える柱は 375px 幅で判読できない | `charts[].granularity` |

目安(benchmarks)は業種で異なるため、「目安外=悪い」と断定しない。「目安の範囲外(根拠: …)。前期からの変化と合わせて判断」と書く。

## 9. 再現性(同じデータ → 同じ結論)

- 数値の判定は §8 の閾値と応答のキーだけを使う。本文で新しい閾値を持ち出さない。
- 2回生成して要点(keyFindings の `label` と `amount`)が入れ替わるのは、閾値の近傍に値があるときか、`priority` の付け方が揺れたとき。`priority` は **high=金額が期間経費の5%超かつ今月中に着手できる / mid=どちらか一方 / low=どちらでもない** で付ける。
- 図の数値はアプリが計算するため、生成のたびに変わらない。変わり得るのは本文と要点だけ。
