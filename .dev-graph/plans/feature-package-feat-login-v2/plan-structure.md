## このタスクの目的と、導入で得られる価値

### 技術的な詳細 (エンジニア向け)
- **目的 (何をするか)**:
  - 金融明細を預かる入口を、テナント管理者に招待された本人だけが、自分で選んだ認証手段 (Google アカウント、またはメールアドレスとパスワード) で入れる場にする。
  - 管理者は他人の秘密 (仮パスワード) を一切持たず、招待はメールのリンクで本人に届く。
  - 本人はパスワードを自分で再設定でき、同じメールアドレスの Google とパスワードは再認証とメール確認を経て 1 つのアカウントに連携でき、パスワードでのログインには TOTP を重ねる (管理者は必須、一般は任意)。
  - ログイン画面は何が守られるかと稼働状況・ヘルプ・プライバシーをログイン前に示す。
  - 保守者に対しては、認証を Better Auth の正規の機能に寄せて自前の暗号処理 (kanjo_session の署名・世代照合・一時パスワード) を撤去し、既存 20 画面と API の認証契約 (401/403/409・監査の actor 記録) を同じ契約テストで守る。
- **到達状態 (Goal)**: /login が 01-login-v2.png の全構成要素 (ロゴと見出し・説明・Googleでログイン・区切り・メールとパスワードのフォーム (表示切替・保持のチェック・パスワードをお忘れの方)・招待の囲み・連携の囲み・安心 3 項目・フッター (稼働状況・ヘルプ・プライバシー)) を画像と完全一致の文言でトークンと共通部品により描画し、送信中・認証失敗・ロック中・MFA コード入力・再送受付・再設定受付の 6 状態を持ち、未認証で /invite/accept・/reset-password・/mfa・/help・/privacy に到達でき、認証基盤が Better Auth v1.7.5 (メールとパスワード・Google・D1 の session 表・TOTP と復旧コード・連携) へ移って自前の署名と一時パスワードと初回変更の強制が 0 件になり、既存の PBKDF2 利用者が再設定なしでログインでき、TOTP 未設定の管理者はパスワードでのログインでも招待の登録直後でも設定を終えるまでセッションを得ず、招待・再送・再設定・MFA の各入口にレート制限と列挙防止が効き、migration 0048 が既存行を書き換えず、既存 20 画面の認証ガードと契約テスト (401/403/409・actor) が緑のままの状態。
