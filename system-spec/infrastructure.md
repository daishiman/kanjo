#### 裏付け質疑: `qa-infrastructure-alternatives-001`

**問**

月次トータル収支の算出について、要求時に毎回導出する以外にどのような選択肢があり、なぜそれを採らないのか。インフラ構成を変える必要はあるか。

**答**

検討した代替案は3つ。(a)cron で夜間に月次合計を事前計算し D1 のテーブルへ書き出す: 採らない。導出値を canonical と二重に持つことになり、取込・取消・undo・利用者の手当てのたびに再計算漏れが起きると、画面の合計と明細が食い違う。この食い違いは利用者からは検算不能で、G3(利用者の手で検算できる)を直接損なう。(b)Durable Objects や KV に集計結果をキャッシュする: 採らない。同じ二重保持の問題に加え、無効化のタイミングという新しい失敗モードを増やす。(c)集計を D1 の SQL 側へ寄せてビュー化する: 採らない。重複判定の規則(min(n,m) の基数規則)を SQL とアプリの二箇所に持つ危険があり、制約『判定を1箇所に置いて複製しない』に反する。毎回導出が成立する根拠は取得済み公式出典 cloudflare-d1-limits にある: Worker 1呼出しあたりのクエリ数は 1,000 (Workers Paid)、SQL文の最大長 100KB、クエリ最大実行時間 30秒、バインドパラメータは1クエリあたり最大100。本機能は月次数十行規模の集計であり、対象期間の明細を数クエリで取得してアプリ側で突合する形に収まる(バインドパラメータ上限100を跨がないよう、期間指定は範囲条件で表現し個別IDの列挙を避ける)。結論としてインフラ構成は変えない。新しいスケジュール実行・新しい監視基盤・新しいデータストアをいずれも追加せず、既存の Cloudflare Workers + D1 + R2 の1系統に載せる。

- (根拠の性質: アシスタントの推定 (利用者確認も検証可能な出典も経ていない) / 出所: アシスタントの分析。代替案の棄却理由は取得済み公式ドキュメント (fetched-references) と既存コードの制約に接地しているが、案の採否そのものは別途 AskUserQuestion で利用者採択を取り直している (末尾 -002 の質疑)。)

### 到達すべき状態 (To-Be)

### 受入条件 (Delta の判定点)

| 目標 | 到達点 | 達成の観測点 (measure) |
|---|---|---|
| O1 | 月次のトータル収支行を導出する読み取りモデルを core に追加する | months の各月について 総収入・総支出・総収支・事業費・家計費・事業費へ寄せた件数 を返す関数が存在し、契約テストで恒等式 総支出 = 事業費 + 家計費 と 総収入 = 事業収入 + 家計収入 がいずれも全月で成立する |
| O3 | 収入の帰属を MF の事業・副業区分で決め、freee 売上との二重計上を避ける | MF の事業・副業入金が事業収入へ、それ以外が家計収入へ計上されることを契約テストで固定し、freee 売上と同額・同発生日で重なる分が総収入へ二度加算されないことを示す。加えて、日付が一致せず消し込めない組が要確認として出ること、および利用者が『同じ』と判断した入金が家計収入から外れて事業収入へ寄り、判断の前後いずれでも総収入 = 事業収入 + 家計収入 の恒等式が成立することを固定する |
| O6 | 一覧表を画面へ出し、判断の入口を既存の明細編集画面に置く | 月次行・合計行・消し込み列・要確認件数を含む表が web 画面に表示され期間切替に追随すること、および要確認の『同じ/違う』判断が既存の取込明細編集画面から行えて判断後に一覧表の数字が更新されることを示す。加えて9列すべてが常時表示されること、および取込完了時に要確認が残っている場合に画面へ警告が出ることを示す |

  - 採択の接地根拠: `qa-decision-trend-method-002`
- **dec-auth-boundary-001**: 本機能 (トータル収支の一覧表と要確認判断API) の認証境界をどこに置くか。既存 /api 認証ゲートの内側に置くか、別経路を設けるか、Cloudflare Access へ一本化するか。
  - 採択: 既存の /api 認証ゲートの内側に置く (`opt-existing-gate`)
  - 目的適合: G1 (一覧表を確認できる) と G7 (期間切替でも一貫) を満たすうえで認証は前提条件であり、既存ゲートに載せることで本機能だけ到達性が異なる状態を作らない。wrangler.jsonc の run_worker_first: ['/api/*'] により、追加する読み取りAPI・DuplicateVerdict 更新API も必ずゲートを通る。
  - 採択の接地根拠: `qa-decision-auth-boundary-002`
- **dec-aggregation-strategy-001**: 月次トータル収支 (総収入・総支出・総収支・事業費・家計費・寄せた件数) をどう算出するか。要求時に毎回導出するか、事前計算して保存するか、SQL 側へ寄せるか。
  - 採択: 要求時に canonical から毎回導出する (`opt-derive-on-request`)
  - 目的適合: G3 (合計が『事業費 + 家計費』として利用者の手で検算できる) を最も直接に満たす。canonical が唯一の真実であり、画面の合計と明細が定義上ずれない。G7 (期間切替でも矛盾しない) も、期間ごとに同じ導出関数を通すだけで満たされる。
  - 採択の接地根拠: `qa-decision-aggregation-002`
