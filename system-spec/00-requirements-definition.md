## U1 本質的目的 (essential_purpose)

『次に何を改善すると最も効くのか』を、診断画面の 1 画面で決められるようにする。利用者が診断を開いた時点で、選んだ期間の収支データから見つかった改善余地が年間の改善インパクト順に並び、なぜその順位なのか (根拠の数値・出典・信頼度) と、対応にどれだけ手間がかかるか、いま自分がどこまで対応したかが読め、次の操作 (明細仕分け・予算・サブスク・照合) へそのまま進める状態にする。改善余地の見つけ方は登録制にして、新しい観点をあとから同じ画面の型で足せるようにする。

## U2 背景 (background)

kanjo の診断タブ (packages/web/src/pages/analysis/Diagnosis.tsx、/analysis/diagnosis) は、事業の科目ごとに平均・中央値・変動係数・z 値・基準レンジを並べた統計プロファイル表と、自動診断の箇条書きを出す画面である。API は GET /api/diagnosis (packages/api/src/routes/analytics.ts:408) で、集計は packages/core/src/analysis.ts の diagnosis() が返す。この diagnosis() は 'サブスク・通信' と '研修費' というカテゴリ名を直書きで分岐しており、観点を足すたびに関数本体を編集する構造になっている。数値は MF 明細の事業側 (data.biz) だけを見ており、家計も、freee 取引と消し込んだ後の取引集合も見ていない。改善余地を金額で並べる仕組みは別の場所にあり、同じ analysis.ts の tradeoffCandidates() が『サブスクの重複疑い・急増・予算超過・基準レンジ超え・未分類支出』を効果額の降順で返しているが、これはやりくり試算 (トレードオフ画面) の持ち物で診断画面には出ていない。診断画面には、改善余地の優先順位・年間の改善インパクト・対応の手間・対応状況・診断の根拠 (データソース別のカバー率)・改善後の見込み・健全性スコア・選択した項目の詳細パネル・下部の選択バーが無い。FINAL-UI の監査 (design/FINAL-UI/spec/AUDIT.md:14) は 08 診断を『良好→整理。結論は明快。根拠・影響額・実行先を一続きにする』とし、FUNCTION-MATRIX (design/FINAL-UI/spec/FUNCTION-MATRIX.md:14) は『改善余地を優先順位化。診断指標、根拠、影響額、優先度、仕分け／予算への実行リンク』を必須としている。PR #49 のデザインシステム基盤、#50 の支出分析ハブ、#54 の照合、#55 の総収支、#56 の推移に続き、FINAL-UI どおりに作り直す順番が診断に回ってきた。先行する 3 サイクル (照合・総収支・推移) は scope_out に『診断の中身はそれぞれの画面サイクルで扱う』と書いて本サイクルを予約している。利用者は 2026-09-18 に 08-diagnosis.png を示し、画像の内容を作れるように既存の内容と画像の内容を分析したうえで UI・UX・フロントエンド・バックエンドのすべてを改善することを依頼した。あわせて 2026-09-18 に 2 つの判断を示した: 健全性スコアは固定費比率・貯蓄率・収支の安定性・データカバー率を定義済みの重みで 0-100 へ合成する規則ベースの指標とし内訳を画面で分解表示する (外部基準に依存せず再現可能にする)、改善アクションの対応状況は D1 の新表へ保存して期間の切替と再取込をまたいで引き継ぐ (照合の reconciliation_actions・総収支の total_cashflow_operations と同じ型)。

## U5 成功基準 (success_criteria)

- S1 (G1): /analysis/diagnosis で 08-diagnosis.png の構成要素がすべて描画され、色・余白・部品はトークンと共通 Button/PageShell/chart の共通設定経由で、直書き色の lint が 0 件である。既存の科目別プロファイルと自動診断は開閉部分に残り、消えていない。
- S2 (G2): 検知器定義を 1 件足すだけで画面と API に新しい課題が現れ、画面と API のコードに検知器 id の分岐が無い。今回登録する 6 種の検知器すべてが、課題文・年間改善インパクト・対応の手間・優先度・次のアクション・根拠の数値・信頼度を定義から埋められる。
- S3 (G3): 健全性スコアの要素スコア・重み・寄与点・総合スコア・区分が境界値テストで算式どおりに一致し、画面の内訳が core の返却値と一致する。要素の実測値が欠ける場合 (データ不足) は要素を除いて重みを正規化し、その旨を画面に示す。
- S4 (G4): 改善アクションの状態が D1 に保存され、期間切替・再取込・再ログインをまたいで復元される。対応済みと見送りは既定の一覧と改善余地の合計から外れ、畳んだ件数と金額が注記に出て、切替で再表示できる。検知結果が消えても記録は残り、再発時に前回の判断が示される。
- S5 (G5): 詳細パネルと選択バーからの遷移で /classify・/budget・/subscriptions・/analysis/reconciliation・/analysis/total-cashflow が対象を絞った状態で開き、診断の条件 (範囲・指標・比較対象・選択した課題・畳みの切替) は URL から復元される。明細サンプルは検知の根拠になった明細だけを示す。
- S6 (G6): 3 指標×3 範囲×2 比較対象のどの組合せでも、画面の数値が core の返却値と一致し、総合=事業+家計 が成り立ち、期間合計は同じ期間の総収支画面の値と一致する。要確認の明細は数値に含めず件数と金額を注記する。見積り・優先度・信頼度・カバー率・改善後の見込みの規則が docs/diagnosis-screen.md にあり、境界値テストで固定されている。
- S7 (G1-G6): 既存の pnpm test / typecheck / lint と packages/web の check 系スクリプト (視覚検査を含む) が全て緑のままである。既存の GET /api/diagnosis を使う画面 (トレードオフ・使い方) が壊れていない。

## U6 ステークホルダー (stakeholders)

- SH1 利用者 (単独の個人事業主): 月次の振り返りで診断を開いたとき、限られた時間で次に手を付ける 1 件を決めたい。改善の余地がいくらあるのか、なぜその順番なのか、対応にどれだけ手間がかかるのか、前回どこまでやったのかを 1 画面で確かめ、決めたらその場で明細仕分けや予算の操作へ進みたい。
- SH2 保守者 (同一人物、および Claude Code などのコーディングエージェント): 改善余地の検知・見積り・スコアの規則が core の純関数と docs にまとまっていて、観点を足すときに画面と API を編集せずに済み、境界値テストで壊れたことが分かる状態にしたい。
- SH3 データ提供元 (MoneyForward の明細 CSV と freee の取引): 取込済みの範囲でしか診断できないため、どこまで取り込めているか (データカバー率) を画面に示し、足りない範囲を根拠なく断定しないこと。

## U7 スコープ (scope)

- **対象 (in)**: 診断タブ (08-diagnosis.png) の画面構成の作り直し: 期間タブ・見出し・条件の帯・診断結果カード・健全性カード・主なシグナル・改善アクションの優先順位の表・改善インパクトのウォーターフォール・診断根拠の表・完了すると変わる指標・詳細パネル (3 タブ)・選択バー、既存の科目別プロファイルと自動診断の開閉化, packages/core に改善余地の検知器の登録制 (6 種の検知器) と、年間改善インパクト・対応の手間・優先度・信頼度の算出, packages/core に健全性スコア (4 要素の合成・内訳・区分) の算出, GET /api/diagnosis の条件 (範囲・指標・比較対象・選択した課題・畳みの切替) と返却の拡張、対応状況の保存と取得の API, D1 の新表 (改善アクションの対応状況) と migration, 実行先への導線: /classify・/budget・/subscriptions・/analysis/reconciliation・/analysis/total-cashflow の絞込クエリ, 計算規則と説明文の規則の docs (docs/diagnosis-screen.md) とテスト
- **対象外 (out)**: AI による改善提案の生成: 検知器の規則による自動生成だけにする (外部送信や LLM 呼出しはしない。AI 分析タブは別画面として既存のまま), 改善の実行そのもの (解約手続き・契約変更の代行): 診断は対象と金額と行き先を示すところまでにする, 今回登録する 6 種以外の検知器の実装: 登録制の型だけ用意し、観点の追加は後続で行う (利用者の選択による), 外部のベンチマーク (業種平均・世帯平均) との比較: 健全性スコアは自分のデータだけから規則で出す (利用者の選択による), 取引先の名寄せ規則: 明細の内容をそのまま取引先として扱う (推移サイクルの決定を踏襲する), 共通シェル (サイドバー・ヘッダー・フッター・月次クローズの進捗) の変更: 既存の共通シェルをそのまま使う, 照合・総収支・マトリクス・推移の各タブの中身: それぞれの画面サイクルで確定済みの内容を変えない, web 以外の platform (専用アプリ)

## U8 制約 (constraints)

- C1 技術: pnpm monorepo (core は依存ゼロの純関数、api は Hono の Cloudflare Worker と D1、web は React 18 + react-router-dom 7 + TanStack Query 5 + chart.js 4)。集計は core に置き api/web へ重複実装しない。
- C2 データ: 取込済みの MoneyForward 明細と freee 取引だけを使う。数値は総収支・推移と同じ取引集合 (消し込み後) から数え、要確認の明細は事業にも家計にも数えない。外部 API へ明細を送信しない。
- C3 UI: design/FINAL-UI のトークンと共通部品 (PageShell・Button・DataTable・chart.js の共通設定) の上に組み、色・余白を直書きしない。表は横スクロール可能にし、CI の headless Chrome (pointer:none) でも操作できる形にする。
- C4 移行: D1 の新表は追加のみで、既存の表と行を書き換えない。migration は連番の追加 1 本に収め、Deploy の migration ゲートを通す。
- C5 運用: 単独利用の個人事業主向けで、Cloudflare Workers Free と D1 Free の枠内に収める。診断 1 回の読み取りは総収支 API と同じ量に収める。
- C6 対象 platform: web のみ。専用アプリ (mobile / tablet / desktop) は提供しない。

#### この承認を名指ししている質疑: `qa-target-platforms-diagnosis-001`

**問**

診断画面 (08-diagnosis) の作り直しは、どの platform を対象にしますか。web / mobile / tablet / desktop-windows / desktop-linux / desktop-macos の6 種それぞれについて、対象に含めるか外すかを決めてください。

**答**

対象は web のみとする。mobile / tablet / desktop-windows / desktop-linux / desktop-macos の 5 種は本サイクルの対象外とする。

理由: 本プロダクト kanjo は Cloudflare Workers 上の API (packages/api) と、ブラウザへ配信する SPA (packages/web、React 18 + react-router-dom 7) の 2 つだけで構成されており、専用アプリの成果物・配布経路・ビルド設定はリポジトリに存在しない。直前の総収支画面 (PR #55)・照合画面 (PR #54)・推移画面 (PR #56) の各サイクルも同じ理由で web のみを対象としており、本サイクルで方針を変える理由がない。上位概念の対象外 (scope.out) にも『web 以外の platform』を明記して利用者承認済み (appr-foundation-diagnosis-001)。

なお web はレスポンシブで提供するため、スマートフォンのブラウザからも閲覧できる。ここで対象外にしたのは『専用アプリという成果物』であって『小さい画面』ではない。小さい画面での表示は ui-ux / frontend の web セルで扱う。
