## U1 本質的目的 (essential_purpose)

明細仕分け画面を、『未整理の明細を、根拠を見ながら確定しますか？』という問いに 1 画面で答え切る場にする。利用者が期間 (1年 / 2年 / 3年 / 任意) を選ぶと、未整理・要確認・手動変更・完了の件数を最初に掴み、絞り込みで片付ける対象を選び、一覧で提案カテゴリと信頼度を見比べ、右の編集パネルで信頼度の根拠と取引の履歴を読んだうえで確定できる。複数件はまとめて保存し、一部が失敗しても失敗した明細だけを再試行でき、繰り返し現れる取引はその場でルールにして、今後どの明細にどう適用されるかをプレビューで確かめてから適用できる。分割は合計が元の金額に一致することを確かめて適用でき、削除は元に戻せ、入力中の下書きは画面を離れても失われない。未整理・手動変更・完了の件数は排他で和が全件に一致し、要確認は未整理の内訳として数え、ナビのバッジと月次クローズの『仕分け』と同じ定義から導く。取込データは外部へ送信しない。

## U2 背景 (background)

現行の /classify (packages/web/src/pages/Classify.tsx、1188 行の 1 ファイル) は対象月を単月の select で選び、KPI は明細数・総収入などの金額で、画像の件数 KPI (未整理 / 要確認 / 手動変更 / 完了) ではない。絞り込みはツールバー横並びで、保存したフィルタ・一覧のチェックボックスと 50 件ページング・右の編集パネル・一括保存 (部分失敗の報告と再試行)・取引の履歴・下書きの自動保存と復元・ルール作成前の適用プレビューがどの層にも無い。提案カテゴリと信頼度は core の recommendationFor にあるが /review-queue 専用で /transactions には載らず、信頼度が数値になるのは過去の同取引先 (vendor_memory) 由来のときだけで、ルール・MF 中項目由来は null。『要確認』の定義はどこにも無い。design/FINAL-UI/images/13-classify.png はこれらを 1 画面に統合した完成形で、design/FINAL-UI/spec/AUDIT.md も『中核は良い。分割、全フィルタ、ルール適用、下書き/離脱防止を追加』と指摘している。総収支・推移・マトリックス・サブスク・家計収支を同じ流儀で作り直し終えた今、『整える』段階の入口である仕分け画面を揃える時期にある。画像の『領収書・証憑』欄は #42 で製品として廃止し spec-v1.1 で外部の正本側 (freee) 管理と定めた機能で、今回も再導入しない (利用者決定)。

## U5 成功基準 (success_criteria)

- S1 (G1): /classify で 13-classify.png の構成要素がすべて描画され、色・余白・部品はトークンと共通部品経由で、直書き色の lint が 0 件である。証憑欄は無く freee 管理の案内がある。期間内の明細 0 件で空状態になる。
- S2 (G2): 同じ期間で 未整理・手動変更・完了の件数の和が全件に一致し、要確認は未整理を超えず、ナビのバッジと月次クローズの『仕分け』の件数と画面の件数が同じ関数から出る。信頼度は全由来で 0〜100 の整数か、提案が無いときだけ null である。外部送信が 0 件である。
- S3 (G3): 一括保存で一部が失敗しても成功分が保存され、画面の通知が成功件数と失敗件数を正しく示し、再試行は失敗分だけを送る。削除は元に戻せる。
- S4 (G4): ルール作成前のプレビューの件数・明細と、適用後に変わった明細が一致し、手動変更の明細は変わらない。分割ルールの行の和が元の金額に一致する。
- S5 (G5): 保存フィルタ・取引の履歴が D1 に残り、下書きが画面の再読込後に復元できる。migration は追加のみで既存行の書き換えが 0 件である。
- S6 (G1-G5): 期間は usePeriod / localStorage から復元し、絞り込みと選択は URL に保つ。既存の仕分け・照合・月次クローズ・家計収支・総収支の数値テストが緑のまま、pnpm lint・typecheck・初期 JS 予算を CI で通す。既知の逸脱・未実施・一部適合は受入 PASS に数えない。

## U6 ステークホルダー (stakeholders)

- SH1 利用者 (個人事業主とその家族の家計を 1 人で管理する): 月次クローズの『整える』段階で、取り込んだ明細のうち自動では決まらなかったものを、なぜその提案なのかを確かめながら素早く確定し、同じ取引先が次から自動で決まるようにしたい。まとめて保存したときに一部が失敗しても、何が失敗したか分かり失敗分だけやり直したい。入力途中で画面を離れても作業を失いたくない。

## U8 制約 (constraints)

- C1 技術: pnpm monorepo (core は依存ゼロの純関数、api は Hono の Cloudflare Worker と D1/Drizzle、web は React 18 + react-router-dom 7 + TanStack Query 5)。判定と集計は core に置き api/web へ重複実装しない。
- C2 デザイン: docs/design-system.md に従い、色は design-tokens.ts 由来のトークンだけ、共通部品 (PageHeader・KpiCard・Button・ConfirmDialog) を使う。一括操作バーは共通部品ではなく、サブスク・診断と同じく画面専用に置く。
- C3 migration: D1 の migration は追加のみ (新表・新カラム) とし、行を書き換える migration は作らない。本番反映は既存の Deploy / Migrate の手順とゲートに従う。
- C4 セキュリティ: /api/* の authGuard・mustChangePasswordFence・runtimeSchemaGuard・canonicalMutationFence の内側に置く。入力は zod で検証し、メモ・フィルタ名・キーワードは長さを制限し React の既定エスケープで描画する。取込データを外部へ送信しない。証憑ファイルを受け付けない。
- C5 性能とコスト: Cloudflare の無料枠 (Workers の CPU 時間・D1) の範囲で動かし、初期 JS 予算 (CI 実測) を超えない。一覧はサーバ側で 50 件ずつ返す。
- C6 数値の正本: 13-classify.png の数値はモックであり、画面の件数・金額は実データから core で算出したものを正本にする。

## 確定の接地根拠 (承認)

> 上の `status` を確定たらしめている利用者承認の実体。承認範囲がここに現れない項目は、本章の確定内容ではない。

### 承認: `appr-foundation-classify-002`

完成度評価 (high: 分類ステータスの定義漏れ) を受けた上位概念の改訂を利用者が承認。要確認を未整理の内訳にし、提案どおりの確定は完了・提案と異なる確定は手動変更とする (qa-classify-decision-005/006)。一括操作バーを画面専用部品と改める。選択肢は『この内容で承認 / 修正して再提示』で利用者は承認を選択 (2026-09-19T13:44:19Z、transcript の回答行の実測時刻)。basis=user-decision。

### 明確化: `appr-foundation-classify-003`

Q-1 は、承認済みの契約「提案どおりの確定と自動決定は完了」に従う。取込時に vendor_memory が materialize した手当ては、`matched_proposal` が NULL でも `done`（完了）とし、要確認には数えない。新しい区分や保存値は追加せず、core の既存判定と実テストに固定する（2026-09-21）。
