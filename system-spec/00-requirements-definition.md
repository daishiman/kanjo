## U1 本質的目的 (essential_purpose)

個人事業主として事業と家計が一体になっている実態に対し、freee(事業帳簿)とMoney Forward(家計)へ分かれて記録された収入・支出を、二重計上を明細単位で消し込んだうえで1つの一覧表へ束ね、月ごとの『トータルの収入・支出・収支(プラスマイナス)』と費用の推移を、消し込んだ根拠ごと確認できる状態を保つ。

## U2 背景 (background)

現状 analysis.ts の balanceMonth() は Money Forward 側の収支だけを balance とし、freee の revenue / bizExpense は隣に並ぶ参照列に留まっている。comparison() は事業と家計を左右に並べる割合ビューであり、合算は行わない。このため『家計と事業の割合』は読めるが『全部でいくらプラスマイナスなのか』『費用が全体としてどれだけ推移しているか』が読めない。さらに単純合算はできない: 個人カード・口座から払った事業経費(bizAdvance)は freee にも経費として記帳されており、事業口座から個人口座への振替(bizIncome)は freee 売上の再登場であるため、収入・支出の双方で二重計上が発生する。重複源のひとつである三井住友銀行のカードは Money Forward 側で3口座が同一表記になっており、口座名だけでは重複範囲を口座単位に切り分けられない。一方でコミット b6c0059 で追加された expense-projection.ts が、金額・日付(±3日)・支払先による freee↔MF の明細照合と、確定できない明細の理由付き列挙(ExpenseReview)を既に備えている。ただしこの照合器はいま『未記帳の事業経費の洗い出し』にしか使われておらず、また1対1に限定した保守的な照合であるため、トータル収支の消し込み規則としてはそのまま流用しない。本機能の重複除外は利用者判断により次の単一規則を採る: Money Forward 明細の日付と freee 取引の発生日(FreeeDeal.date。dueDate / settledDate は用いない)が一致し、かつ金額が一致する支出は『事業で使う費用』とみなし、freee 側を正として事業経費に一度だけ計上し、Money Forward 側は家計の生活費から外す。支払先を見ないため同額・同日の無関係な支出も同じ扱いになりうるが、規則の単純さと予測可能性を優先する。日付が一致しない重複(カード利用日と freee 発生日のズレなど)は自動判定の対象外となり、要確認として可視化する。支出の帰属は『重複したものは事業費、それ以外は家計費』とし、収入は Money Forward 側で事業・副業に分類される入金を事業収入として扱う。この収入側の区分は既に実装されている: DEFAULT_RULES に `事業・副業` が cls='biz' として含まれ、applyClassification() が biz 判定の入金を bizPersonal.income へ集約している。本機能はこの既存分類を収入の帰属根拠としてそのまま用いる。

| G2 | Money Forward の日付と freee の発生日が一致し金額も一致する支出は『事業で使う費用』として freee を正に事業側へ一度だけ計上し、それ以外の支出は家計側へ計上して、二重計上のない支出合計を出す状態にする |

| G6 | 合算後も事業側・家計側の内訳を保持し、トータルの増減がどちらの側のどの科目で起きているかまで辿れる状態にする |
| G7 | 期間を切り替えても、合算・消し込み・トレンド判定が同じ規則で再計算され、期間ごとに矛盾した数字が出ない状態にする |

## U5 成功基準 (success_criteria)

- 利用者が一覧表の1行を見るだけで、その月に全体でいくらプラスかマイナスかを言える
- 合計値について『なぜこの額なのか』を、事業費/家計費の内訳列と要確認件数から利用者自身が説明できる
- 同じ支出が freee と MF の双方に載っていても、トータル支出に二度加算されず、事業費として一度だけ現れる
- 同じ入金が freee と MF の双方に載っていても、総収入に二度加算されず、事業収入として一度だけ現れる
- 日付が一致せず自動判定できなかった明細が、黙って家計費へ紛れ込まず、必ず要確認として件数に現れる
- 期間を切り替えたとき、合計・消し込み・トレンドの数字が互いに矛盾しない

## U6 ステークホルダー (stakeholders)

- 利用者本人(個人事業主。事業と家計を一体で回しており、この表の唯一の読み手かつ判断者)
- 税務申告の受け手(freee 側の帳簿が正本であり続けることを前提とする。本機能は帳簿を書き換えない)

## U7 スコープ (scope)

- **対象 (in)**: freee 取引CSV と Money Forward 家計簿CSV の既存取込データからのトータル収支の導出, freee↔MF 間の重複支出・重複収入の明細単位の照合と消し込み, 自動照合できない明細の要確認一覧と、利用者判断の永続化・再適用, トータル支出のトレンド判定と、事業/家計の内訳保持, 月次一覧表の web 画面表示と期間切替への追随
- **対象外 (out)**: 新しい取込元の追加(事業用Money Forward・家計用freee の取込は行わない。利用者確認により現状の3区分で足りる), freee 帳簿そのものの書き換え(税務の正本は freee のまま。本機能は読み取り専用の投影), Money Forward 内部の重複(利用明細と引落の二重計上。既存の isTransfer 判定で除外済み), 予算・目標設定機能の変更, モバイル/タブレット/デスクトップ専用アプリの提供

## U8 制約 (constraints)

- canonical データを書き換えず、現在値から毎回導出する読み取りモデルとして実装する(既存 expense-projection.ts と同じ方針)
- 金額の帰属を自動で決める判定器は『MF明細の日付 = freee取引の発生日(FreeeDeal.date) かつ 金額一致』の1本だけとし、判定を1箇所に置いて複製しない。freee 側の dueDate / settledDate は判定に用いない。これとは別に、合計を一切動かさない候補抽出器として『金額一致 かつ 発生日が±3日以内』の照合を置き、要確認一覧の生成にのみ用いる(日付許容幅は既存 expense-projection.ts と同じ値を流用する)。候補抽出器は自身では帰属を変えず、利用者の明示判断を経た場合にだけ帰属へ反映される。両者は役割が異なるため同居を許すが、帰属を動かす権限を持つのは前者と利用者判断だけである
- 判定規則は支払先を用いない。同額・同発生日の無関係な支出も事業費として扱われうることを既知の限界として仕様に明記する(利用者判断により単純さと予測可能性を優先)
- 支出の帰属は『重複したものは事業費、それ以外は家計費』の二分とし、どちらにも入らない支出を作らない(総支出 = 事業費 + 家計費 を恒等式として保つ)。利用者判断による付替の後もこの恒等式を保つ
- Money Forward 側で三井住友の3口座が同一表記であるため、口座名による口座単位の切り分けに依存しない設計とする
- 除外は freee 側の件数を上限とし、freee に存在しない分の MF 明細を消さない(過小計上の防止)
- 金額または日付が一致しない重複候補を推測で除外しない。除外できない分は必ず要確認として可視化する
- 要確認明細に利用者が『同じ』と判断した場合、その判断は自動規則を上書きし、当該 MF 明細を家計費から外して事業費へ寄せる(合計が動く)。上書きも1対1を保ち、freee 側の1取引に対し MF は1件までしか寄せない。『違う』判断は帰属を変えず、次回以降その組を要確認として再提示しない
- 収入側も支出と同じ規則(同額・同発生日)で freee を正として消し込む。ただし freee 売上は発生主義の発生日、MF 入金は入金日であるため日付が一致しない組が多く、実際に消し込まれる件数は少ない見込みである。一致しない組は支出と同様に要確認として可視化する
- 要確認の『同じ/違う』判断は、既存の取込明細編集画面(取り込んだ明細を1件ずつ直せる画面)に組み込む。判断専用の画面やタブを新設しない
- 既存の trend.ts / analysis.ts の公開関数の意味を変えない(追加はするが既存の戻り値の定義を書き換えない)
- 一覧表は 月・総収入・総支出・総収支・事業費・家計費・事業費へ寄せた件数・要確認件数・トレンド の9列すべてを常時表示する。小画面でも列を落とさない。個別明細と勘定科目別の内訳は表に常置せず、行からのドリルダウンで見せる。
- 要確認明細の放置と集計の異常には、CSV取込の完了時点で気付かせる。取込完了時に要確認が残っていればその場で画面に警告を出す。メール・push・外部監視といった通知基盤は追加しない。
