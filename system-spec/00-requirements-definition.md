## U1 本質的目的 (essential_purpose)

データ取込画面を、『複数の明細ファイルを、安全に取り込みますか？』という問いに 1 画面で答え切る場にする。利用者が freee (事業) と マネーフォワード (家計) の CSV / Excel / テキスト明細を複数まとめて選ぶと、確定する前にファイルごとの取込元・対象期間・大きさ・重複・検証の結果を一覧で確かめ、取り込み予定の明細数・影響する取込元・重複の可能性・サブスク候補の要約を見てから、取り込めるファイルだけをまとめて確定でき、結果 (成功 / 失敗 / 重複の可能性 / サブスク候補) からそのまま次の画面へ進め、過去の取込を 1 回ごとに振り返って原本の取得・再取込・取り消しをその場で決着できる状態にする。誤った取込や二重取込で台帳を壊さないこと、取り込んだデータを外部へ送らないことを守る。

## U2 背景 (background)

現行の /import (packages/web/src/pages/Import.tsx、897 行の 1 ファイル) は、選んだファイルを送った時点で 1 ファイルずつ確定する。確定前にファイルごとの重複・検証の結果を並べて見る場所が無く、取り込み予定の明細数やサブスク候補の数も確定後にしか分からない。差分プレビューは MF 明細だけが対象で、freee には無い。取込履歴はファイルごとの 1 行で、1 回の取込 (複数ファイル) の結果と影響 (新規追加・重複スキップ・サブスク候補) をまとめて見られず、詳細の表示や原本のダウンロードの導線も弱い。『前回データを残す』に近い設定は『件数が減る月だけ前回の内容を残す』で、画像の『同一期間の既存データを残して新しいデータを追加』とは意味が違う。API (packages/api/src/routes/imports.ts) は 1 ファイル 25MB の上限を formData を読み込んだ後で判定しており、body の大きさの上限・取込専用のレート制限・Origin の検査が無い。design/FINAL-UI/images/16-import.png は、これらを 1 画面 (3 段のステッパー、1.ファイルを選択 / 2.取込ファイル一覧 / 3.取込内容の確認 / 4.取込結果 / 5.取込履歴と履歴の詳細、下部の選択件数バー) に統合した完成形である。概要・総収支・推移・家計収支・サブスク・診断・決算書・明細仕分け・AI分析を同じ流儀で作り直し終えた今、月次クローズの入口である『取込』段階の画面を揃える時期にある。

## U5 成功基準 (success_criteria)

- S1 (G1): /import で 16-import.png の構成要素がすべて描画され、色・余白・部品はトークンと共通 Button / PageShell 経由で、直書き色の lint が 0 件である。期間は usePeriod から来る。
- S2 (G2): 検査の段階で明細・残高・有効取込の表への書き込みが 0 件であり、確定は検査 ID だけで行われ、同じファイルの 2 回目のアップロードが 0 件である。期限を過ぎた仮置きは夜間保守の後に R2 と D1 に残らない。
- S3 (G3): ファイルの状態・取り込めるか否か・要約・取込 1 回の結果は core の関数だけが決め、api と web に同じ判定の重複実装が 0 件である。
- S4 (G4): 『前回データを残す』オンで同じファイルを 2 回確定しても明細数が増えず、2 回目の新規追加が 0 件・重複スキップが全行になる。オフでは従来の月単位の入れ替えと同じ結果になる。
- S5 (G5): 取込履歴の 1 行が 1 回の取込に対応し、詳細の影響の数値が確定時の記録と一致する。一括削除の前後で明細数が変わらない。既存の取り消し・破棄・置換・削除と 30 日の取り消し期限が作り直し後も同じ結果になる。
- S6 (G6): 上限・オリジン・レート制限の拒否がテストで固定され、取込経路から外部ホストへの送信が 0 件である。migration は追加のみで、既存の取込履歴 (ファイル単位の記録) が作り直し後も履歴と詳細で読め、既存の取込テストと初期 JS 予算 (CI 実測) が緑のままである。

## U6 ステークホルダー (stakeholders)

- SH1 利用者 (個人事業主とその家族の家計を 1 人で管理する): 月次クローズの入口で、freee と マネーフォワードから書き出した複数の明細をまとめて取り込みたい。確定する前に、どのファイルが何件・どの期間で、重複や誤りが無いかを確かめ、誤りのあるファイルだけ外して安心して取り込み、あとから 1 回ごとに振り返って取り消せるようにしたい。
- SH2 保守者 (同一人物、および Claude Code などのコーディングエージェント): ファイルの状態・取り込めるか否か・要約の数え方・『前回データを残す』の規則・仮置きの期限が core の純関数 1 か所と docs・テストで固定されていること。

## U7 スコープ (scope)

- **対象 (in)**: データ取込画面 (16-import.png の全構成要素と読込 / 空 / 失敗の各状態) の作り直しと、Import.tsx の pages/import/ 配下への分割, 検査 (仮置きとファイルごとの検査結果) と確定 (検査 ID 指定) の 2 段階の API、アップロードの進捗表示、未確定の仮置きの夜間の片づけ, core の純関数: ファイルの状態と検証の段階の導出、取り込めるか否か、要約 (対象ファイル・取り込み予定の明細・対象期間・影響する取込元・重複の可能性・サブスク候補) の算出、取込 1 回の結果の導出, 『前回データを残す』の行単位の追加への変更 (既定オン) と、強制再取込の維持, 取込履歴の 1 回の取込ごとのまとめ、詳細ペイン (影響の 3 数値と原本のダウンロード)、再取込・取り消し・記録だけの一括削除, 対応形式の説明とテキスト (.txt) の受け付け、対応サービス (マネーフォワード・freee) の取得方法の案内, 入口の防御: body の上限・ファイル数と合計サイズの上限・取込専用のレート制限・同一オリジンの検査, 追加のみの migration (検査と仮置きの記録、取込 1 回の影響の数値), docs への規則の明記と回帰テスト
- **対象外 (out)**: 銀行・クレジットカードの明細ファイルの取り込み: freee と マネーフォワードの CSV だけで足りるという利用者決定。対応サービスの案内からも外す, 共通シェル (ヘッダーの取引ライン・検索・ダウンロード・ヘルプ、サイドバー、フッター) の作り直し: 既存実装をそのまま使う, 外部サービスの API との自動連携 (freee / マネーフォワードからの自動取得): 利用者が書き出したファイルを取り込む方式を保つ, スマートフォン・タブレット・デスクトップ向け専用アプリ: web のみ, 既存の取込形式 (ZIP・HTML 版互換 JSON・MF 資産推移) の廃止: 画像に無いが受け付けは維持する

## U8 制約 (constraints)

- C1 技術: pnpm monorepo (core は依存ゼロの純関数、api は Hono の Cloudflare Worker と D1/Drizzle と R2、web は React 18 + react-router-dom 7 + TanStack Query 5)。判定と導出は core に置き api/web へ重複実装しない。
- C2 デザイン: docs/design-system.md に従い、色は design-tokens.ts 由来のトークンだけ、ボタンは共通 Button、ページは PageShell。表・詳細ペイン・選択件数バーは既存画面 (AI分析・サブスク) の部品と流儀に揃える。
- C3 migration: D1 の migration は追加のみ (新カラム・新表) とし、行を書き換える migration は作らない。本番反映は既存の Deploy / Migrate の手順とゲートに従う。
- C4 D1 の制約: 1 要求あたりのクエリ数の上限があるため、確定はファイル単位の書き込み権と既存のクエリ予算の計画に従う。
- C5 セキュリティ: 利用者向け API は /api/* の authGuard・mustChangePasswordFence・runtimeSchemaGuard・canonicalMutationFence の内側に置く。入力は zod で検証し、ファイル名や明細の文字列は React の既定エスケープで描画する。
- C6 データの持ち出し: 取り込んだデータと原本は D1 と R2 の中だけに置き、外部へ送らない。税務上の正本は freee のままとする。

#### この承認を名指ししている質疑: `qa-imp-decision-011`

**問**

承認済みの O6 は『上限を超える body・ファイル数・合計サイズを本文を読む前に 413 で拒否する』とするが、multipart のファイル数は本文を読まないと分からない。どう扱うか。
