## U1 本質的目的 (essential_purpose)

金融明細を扱う権限を「共有された1つの秘密」から「個人に帰属するアカウント」へ移し、失効・追跡・権限限定を利用者単位で効かせられる状態にする。5 Whys の帰結: (1)なぜログイン画面を変えるか→現状はパスワード1本で誰がログインしたか分からない (2)なぜ主体を識別したいか→事業と家計の金融明細を扱うのに認証主体が共有パスワード1本で、漏れれば全データが即座に露出し、誰の操作かも追えない (3)なぜ今か→20画面まで育ち audit_log や改善リクエストなど「誰が」を前提にした機能が既に入っている中で、認証だけが主体を持たないまま取り残されている (4)なぜ主体が要るか→責任の所在を切り分け、1人の退出で全員のパスワードを変える運用から抜けるため (5)本質→金融データを預かる責任を共有の秘密ではなく個人へ帰属させ、停止・追跡・限定を個別に効かせられるようにする。ログイン画面の刷新は、その主体変更を利用者が最初に触れる場所として「安心して預けられる」と伝わる形に整えることであり、見た目の改善そのものが目的ではない。

## U2 背景 (background)

現在の認証は二段構えで、ACCESS_AUD と ACCESS_TEAM_DOMAIN が設定されていれば Cloudflare Access の JWT を検証し、未設定ならアプリ内セッション認証 (AUTH_PASSWORD 1本 + HMAC 署名 HttpOnly Cookie) を使う。しかし認証成功後に authGuard が設定するのは c.set('userId', 'default') という固定値であり、利用者という概念がシステムに存在しない。パスワードは verifyPassword が timingSafeEq で平文比較しており、鍵導出関数を通していない。ログイン画面はパスワード入力1つだけで、扱うデータの性質も保護方針も伝えていない。一方でリポジトリには 0033_audit_log.sql や改善リクエストなど「誰が」を前提とする機能が既に入っており、認証だけが主体を持たない非対称が残っている。共有パスワードは1人に渡すと全員に渡り、1人を外すと全員のパスワードを変える必要がある。20画面規模になり月次業務の順序で束ねられた今、この運用コストと事故時の切り分け不能が表面化した。参照UI (design/FINAL-UI/images/01-login.png) は、この主体変更に見合う入口として提示されたもので、既存UIがこれと異なる場合は参照UIを正とする。

## U3 ゴール (goals)

| ID | ゴール |
|---|---|
| G1 | 利用者がメールアドレスとパスワードで本人として認証でき、セッションが誰のものかシステム側で特定できる |
| G2 | 認証情報が漏洩しても即座に全データが露出しない。パスワードは復元不能な形で保存し、セッションは利用者単位で失効できる |
| G3 | 管理者が設定画面から利用者の追加・停止・パスワード再発行を完結でき、共有パスワードの配り直しが不要になる |
| G4 | ログイン画面が、扱うデータの性質と保護方針を利用者へ明示し、初見でも何をする場所か・何が守られるかが分かる |
| G5 | 既存20画面と /api/* 認証ガードの契約を壊さずに認証主体を差し替える |

## U4 目標 (objectives)

| ID | 目標 | 測定基準 |
|---|---|---|
| O1 | users テーブルを新設し、パスワードを鍵導出関数 (WebCrypto PBKDF2) で保存する | migration 適用後の schema に password_hash と salt と反復回数が存在し、平文パスワードを保持するカラムが0件 |
| O2 | セッション cookie に利用者識別子を含め、識別子を署名対象に含める | 利用者識別子を改ざんした cookie が /api/* で401になる契約テストが緑 |
| O3 | 「次回からもログイン状態を保持する」の選択でセッション有効期間を2段階に切り替える | 未選択時と選択時で Set-Cookie の maxAge が異なることを検査するテストが緑 |
| O4 | 管理者が設定画面から利用者の作成・停止・一時パスワード発行を行える | 3操作それぞれに API と画面操作が存在し、非管理者からの呼出しが403になる |
| O5 | ログイン画面を参照UIの構成 (左: ブランド見出し・月次の流れ4ステップ・安心3項目、右: ログインカード) にし、ヘッダー・フッター・サイドバーを持たせない | ログイン画面の DOM に header/footer/サイドバーのナビゲーション要素が0件 |
| O6 | 認証失敗時の応答が、メールアドレスの存在有無を区別しない | 未登録メールと誤パスワードで応答本文・ステータスが同一で、パスワード検証を常に実行して所要時間差を作らない |
| O7 | 既存のログイン rate limit をメールアドレス単位へ拡張する | 同一メールへの連続失敗で当該メールがロックされ、他メールのログインは阻害されないテストが緑 |
| O8 | migration適用後のbootstrap seedで初回管理者を1件作成し、共有パスワード認証経路を撤去する | active runtimeと必須設定に共有パスワード認証分岐が0件で、旧secretを外しても全機能が動作する |

## U5 成功基準 (success_criteria)

- S1: 管理者が作成した利用者が自分のメールアドレスとパスワードでログインでき、発行された cookie に自分の識別子が含まれる
- S2: D1 上でパスワードが平文検索できず、同じパスワードの2利用者でも保存値が一致しない (salt が利用者ごとに異なる)
- S3: 管理者が停止した利用者は、停止前に発行済みのセッションを持っていても /api/* が401を返す
- S4: 「次回からもログイン状態を保持する」の有無で cookie の有効期間が変わり、未選択時はブラウザセッション相当の短い期間になる
- S5: ログイン画面に Cloudflare Access の導線・ヘッダー・フッター・サイドバーが存在しない
- S6: 未登録メールアドレスと誤パスワードの応答が、本文・ステータスコードのいずれでも区別できない
- S7: 既存20画面の認証ガードが変更前と同じ mount 順序・同じ経路で動作し、既存の契約テストが緑のまま
- S8: AUTH_PASSWORD secret を設定から外した状態で、ログインを含む全機能が動作する
- S9: 管理者が最後の有効な管理者を停止・降格して誰も管理できなくなる状態を、システムが拒否する

## U6 ステークホルダー (stakeholders)

- 利用者本人 (事業と家計を1人で見ている運営者): 月次を締めようとする状況で、まず迷いなくログインし、自分の作業として記録を残したい。共有パスワードでは自分の操作という感覚が持てない
- 管理者 (現状は利用者本人が兼ねる): 家族や委託先に一部の作業を任せたい状況で、個別に発行し、任せ終わったら個別に止めたい。全員のパスワードを変える運用を避けたい
- 将来の共同利用者 (招待される側): 招待を受けた状況で、自分だけが知るパスワードを自分で決めたい。他人と秘密を共有したくない
- 事後の調査主体 (事故や誤操作の後に運営者自身が担う): 何がいつ誰の操作で起きたかを調べる状況で、操作を主体に結びつけたい
- システムを新しく開く人 (初見の利用者): 金融データを預ける前に、何を扱う場所で何が守られるのかを知りたい

## U7 スコープ (scope)

- **対象 (in)**: users テーブルの新設と、鍵導出関数によるパスワード保存, メールアドレス+パスワードによるログインと、セッションへの利用者識別子の埋め込み, ログイン状態保持 (セッション有効期間の2段階切替), 管理者による利用者の作成・停止・一時パスワード発行 (設定画面), 参照UI (design/FINAL-UI/images/01-login.png) に沿ったログイン画面の刷新, ログイン画面専用レイアウト (ヘッダー・フッター・サイドバーを持たない), ログイン rate limit のメールアドレス単位化, migration適用後のbootstrap seedによる初回管理者作成と、既存データを共有tenantのまま保持して今後の操作だけをactorへ紐付ける移行, AUTH_PASSWORD による共有パスワード経路の撤去, ログイン画面からの Cloudflare Access 導線の撤去
- **対象外 (out)**: メール送信基盤 (招待メール・パスワードリセットメール): 利用者決定 2026-09-11 により送信手段を持たない。管理者が一時パスワードを発行し別経路で伝える, 利用者による自己登録 (サインアップ): 利用者決定 2026-09-11 により管理者招待制のみとする。金融明細を扱うため第三者の自己登録を塞ぐ, SSO・ソーシャルログイン: メールアドレスとパスワードのみとする利用者決定による, 多要素認証 (TOTP/WebAuthn): 本サイクルでは扱わない。将来の追加余地は残すが要件に含めない, サーバー側 Cloudflare Access 検証経路の削除: 利用者決定 2026-09-11 により残置する。撤去するのはUI導線のみ, 細粒度の権限ロール設計 (画面別・操作別の権限行列): 本サイクルは管理者と一般利用者の2区分に留める, web 以外のプラットフォーム (mobile / tablet / desktop-windows / desktop-linux / desktop-macos): 専用アプリを提供しておらず、対象を web のみとする

## U8 制約 (constraints)

- C1: Cloudflare Workers + D1 + R2 の既存構成上で動くこと。パスワード鍵導出は WebCrypto (PBKDF2) で行い、Node 固有 API への依存を増やさない
- C2: メール送信基盤を持たない (利用者決定 2026-09-11)。招待とパスワード再発行は管理者による一時パスワード発行と別経路での伝達で成立させる
- C3: サーバー側 Cloudflare Access 検証経路 (ACCESS_AUD / ACCESS_TEAM_DOMAIN) は残置する (利用者決定 2026-09-11)。撤去はUI導線に限る
- C4: 対象プラットフォームは web のみ。専用アプリを提供していない
- C5: 既存 /api/* 認証ガードの mount 順序と既存契約テストを壊さない
- C6: 実質的に単独運用のため、運用者が1人でも回る手順にする。管理者が自分自身を締め出して復旧不能になる状態を作らない
- C7: 金融明細を扱うため、認証失敗の応答から利用者の存在有無を推測できてはならない
- C8: 既存データには所有者列が無く userId は 'default' 固定であるため、既存データを特定利用者へ遡及紐付けせず、今後の操作主体だけをactorとして記録する
- C9: パスワードは復元不能な形で保存し、管理者を含む誰も他人のパスワードを閲覧できない
- C10: 参照UI (design/FINAL-UI/images/01-login.png) を正とする。既存UIがこれと異なる場合は参照UIへ寄せる

### 承認: `appr-foundation-account-login-001`

U1-U9 要約 (本質的目的・背景・ゴールG1-G5・目標O1-O8・成功基準S1-S9・ステークホルダー5区分・スコープ in/out・制約C1-C10・具体的意図I1-I15) を提示し、利用者が「この内容で確定する」を選択して承認した。推定で加えた S9/I15 (最後の管理者を停止・降格できない) を含めた上での承認である。

#### この承認を名指ししている質疑: `qa-basis-correction-001`

**問**

design_applications 8件 / doctrine_applications 13件 の basis を 'user-decision' として記録したが、これらの適用記述はエージェントが確定セルを読んで合成した文章であり、利用者が個々の文を選択・承認したものではない。basis の申告を実態に合わせて訂正せよ。

**答**

訂正する。21件の適用記述 (design 8 / doctrine 13) の basis を 'agent-inference' へ改める。記述内容そのものは変更しない — 確定セルの内容を読んで『その上流指針が本章のどこへ効いたか』を書いたという事実は変わらず、変わるのは『誰がそう判断したか』の申告である。利用者から得ているのは上位概念 (U1-U9, appr-foundation-account-login-001) と各カテゴリの確定回答であって、適用記述の一文一文ではない。併せて、同じ回で記録した qa-backend-web-002 / qa-database-web-002 の basis 'observed-fact' も実態と異なる: これらの答えの実体は既存コードの観測ではなく『U7 scope.in の語をどこまで狭く読むか』というエージェントの解釈判断であり、agent-inference が正しい区分である。qa-uiux-web-002 の basis 'user-decision' も、レイアウト・文言・ヘッダー等の不在は利用者の明示指示だが、『パスワードをお忘れの方』押下でダイアログを開くという UI 実装形式は利用者指示から演繹した推論であり、この部分に限り agent-inference である。qa_log の basis は fill-once で上書きできないため、これらの訂正は本 entry を裏付け質疑として当該セルへ添えることで記録に残す (誤った申告を消さずに残すことが、訂正そのものの監査可能性を保つ)。残る軽微な不正確として、qa-uiux-web-002 の required_info_items に無関係な 'target-platforms' が含まれ、qa-design-doctrine-application-001 には required_info_items が欠落している。いずれも接地判定 (target-platforms は qa-platform-scope-001 で接地済み) に影響しないため訂正質疑を重ねず、本 entry に記録して残す。
