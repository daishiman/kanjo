## U1 本質的目的 (essential_purpose)

収支が『いつ・なぜ』変わったかを、推移画面の 1 画面で掴めるようにする。利用者が推移を開いた時点で、選んだ期間の収入・支出・純収支の月次推移と、前期間または前年との差が総合/事業/家計で読め、最も変化が大きい月の増減要因 (どのカテゴリのどの取引先がいくら動いたか) が根拠の明細まで辿れる状態にする。指標は登録制にして、収支以外の推移もあとから同じ画面の型で追えるようにする。

## U2 背景 (background)

kanjo の推移タブ (packages/web/src/pages/analysis/Trends.tsx、/analysis/trends) は、支出だけを科目単位で並べ、MK 検定と Theil-Sen の傾向判定・前半→後半の寄与度・パレート図から『手を打つ順番』を決める画面である。API は GET /api/trends (packages/api/src/routes/analytics.ts) で、集計は packages/core/src/trend.ts の trendsReport が返す。収入・純収支の系列、前期間/前年との比較、月を選んだときの詳細と増減要因、取引先の内訳、データの出典、該当明細への導線、上位増減のカード、選択バーが無い。前期間 (analysis-hub.ts の previousPeriod) と前年 (period.ts の previousYearPeriod) の関数は別の場所にあり推移では使っていない。明細画面 /classify は month と cls しか絞り込めない。FINAL-UI の監査 (design/FINAL-UI/spec/AUDIT.md) は 07 推移を『事業/家計切替と展開行が見えにくい。比較条件をヘッダー直下へ集約』とし、FUNCTION-MATRIX は『事業/家計範囲切替、複数チャート、Pareto、前年差、展開行、期間比較』を必須としている。PR #49 のデザインシステム基盤、#50 の支出分析ハブ、#54 の照合、#55 の総収支に続き、FINAL-UI どおりに作り直す順番が推移に回ってきた。利用者は 2026-09-16 に 07-trends.png を示し、画像の内容を作れるようにバックエンド・フロントエンド・UI・UX の観点で改善すること、既存に引っ張られすぎないこと、画像のままで汎用性が無いなら様々な情報の推移を管理できるように整えることを依頼した。

## U5 成功基準 (success_criteria)

- S1 (G1): /analysis/trends で 07-trends.png の構成要素がすべて描画され、色・余白・部品はトークンと共通 Button/PageShell/chart の共通設定経由で、直書き色の lint が 0 件である。
- S2 (G2, G3): 3 指標×3 範囲×2 比較対象のどの組合せでも、画面の KPI・チャート・表の値が core の返却値と一致し、総合=事業+家計・純収支=収入-支出が成り立つ。総合・事業・家計の期間合計は同じ期間の総収支画面の値と一致する。
- S3 (G2): 指標定義を 1 件足すだけで画面と API に新しい指標が現れ、画面と API のコードに指標 id の分岐が無い。
- S4 (G4): 詳細パネルと選択バーからの遷移で、/classify が月・範囲・カテゴリ・取引先で絞り込み、推移の URL は category+side で同名カテゴリを一意に復元する。
- S5 (G5): 計算規則と説明文の規則が docs に書かれ、境界値テストを含む vitest が通り、既存の傾向判定のテスト (trend-contract.test.ts) も壊れていない。

## U6 ステークホルダー (stakeholders)

- SH1 利用者 (単独の個人事業主): 月次の振り返りで推移を開いたとき、収支がいつ・どれだけ変わったか、その原因のカテゴリと取引先はどれかを前期間や前年と比べて掴み、必要なら根拠の明細を開いて確かめたい。
- SH2 保守者 (同一人物、および Claude Code などのコーディングエージェント): 集計・比較・説明文の規則が core の純関数・docs・テストで固定され、指標を足すときに画面と API を個別に直さずに済むこと。

## U7 スコープ (scope)

- **対象 (in)**: 推移タブ (07-trends.png) の情報階層を共通シェル上に構築: 条件帯・KPI・意味付き推移チャート・詳細・カテゴリ・符号付きパレート・上位 3・選択バー、旧傾向判定の固有部分だけを開閉化, packages/core の推移集計の拡張と指標定義の登録制 (収入・支出・純収支), GET /api/trends の条件 (範囲・指標・比較対象・選択月・カテゴリ side) と返却の拡張, 明細画面 /classify のカテゴリ・取引先の絞込クエリ, 計算規則と説明文の規則の docs とテスト
- **対象外 (out)**: 収入・支出・純収支以外の指標 (件数・口座別残高など) の実装: 登録制の型だけ用意し、指標の追加は後続で行う (利用者の選択による), 取引先の名寄せ規則: 明細の内容をそのまま取引先として集計する (利用者の選択による), AI による説明文の生成と利用者のメモ入力: 規則による自動生成だけにする (利用者の選択による), 共通シェル (サイドバー・ヘッダー・フッター・月次クローズの進捗) の変更: 既存の共通シェルをそのまま使う, 照合・総収支・マトリクス・診断の各タブの中身: それぞれの画面サイクルで扱う, web 以外の platform (専用アプリ)

## U8 制約 (constraints)

- C1 技術: pnpm monorepo (core は依存ゼロの純関数、api は Hono の Cloudflare Worker と D1、web は React 18 + react-router-dom 7 + TanStack Query 5 + chart.js 4)。集計は core に置き api/web へ重複実装しない。
- C2 デザイン: docs/design-system.md に従い、色は design-tokens.ts 由来のトークンとチャート系列色だけを使い、ボタンは共通 Button、本文は PageShell を使う。WCAG 2.2 AA (文字 4.5:1、部品 3:1) を維持し、増減の良し悪しを色だけで伝えない (符号と文字を併記する)。
- C3 データ: 取込データは外部送信しない。説明文は端末外のサービスを使わずに作る。
- C4 互換: 既存の傾向判定 (trendsReport の rows/pareto/breakdown) の値と既存テストを壊さない。旧 /trends の転送も維持する。傾向の判定は MF 明細だけを入力とする現行の基準のまま残し、画面上で基準の違いを明記する。
- C5 運用: 単独利用で予算は Cloudflare の無料枠内。スキーマ変更が不要なら migration を足さない。
