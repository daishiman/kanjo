## U1 本質的目的 (essential_purpose)

利用者が日々の記帳を止めずに完了できる状態を保つこと。そのために(1)本番データベースのスキーマをデプロイ済みコードが前提とする版へ一致させ続け、(2)利用者が使っていて気づいた不便や不具合を、その場の画面と状況ごと開発側へ届けて改善へつなげる経路を保つ。
外出先や片手操作のモバイル環境でも、収支の変化・異常・次に確認すべきことをグラフと要約から即座に理解し、見落としや誤操作なく判断を完了できるようにする。

## U2 背景 (background)

現行Webアプリはナビゲーションや一部の表をモバイル対応済みだが、財務グラフ・比較図・高密度情報はデスクトップ前提が残り、モバイルでは表示欠落、狭幅での判読困難、横スクロール中の文脈喪失が起き得る。直前featureは現在地と画面探索を改善したため、今回は画面内の財務可視化と主要操作をAppleのモバイル設計原則に照らして見直す。

また、記帳を続けるなかで利用者が気づく不便や不具合は、これまで画面外の手段で伝えるほかなく、どの画面のどの状態で起きたのかが失われていた。調査の結果、改善要望を受け付ける機能はこのリポジトリに実装されたことがなく (削除コミット0件)、新規に設ける必要がある。改善作業は Claude Code / Codex で行うため、要望はそのまま着手できる指示文と証跡 (スクリーンショット・診断情報) の形で取り出せる必要がある。

## U5 成功基準 (success_criteria)

- 承認済み pending manifest の全項目が本番の d1_migrations に記録され、同じ repository head / ordered migrations digest に対する未適用が0件である
- 本番画面でファイルを選び「取込を実行」してサーバーエラーが発生しない
- 取込履歴が「サーバー側で処理に失敗しました」を出さず一覧表示される
- 適用前後で mf_transactions / freee_deals / imports の行数が減少していない
- デプロイパイプラインで未適用がある、または状態を判定できない場合、Worker の新版が配信されない
- スキーマ版数不一致時のエラー応答が、汎用サーバーエラーではなく原因を特定できる内容である
- どの画面でも右下に固定された導線から改善要望を投稿でき、投稿後に一覧で内容・スクリーンショット・診断情報を確認できる
- 自動取得されたスクリーンショットに改善要望モーダルが写っておらず、そのとき見えていた本文が写っている
- 送信前に、一緒に送られる画面・表示環境・診断情報の中身を利用者自身が読める
- スクリーンショットへ枠を書き込め、その枠が送信される画像に残る
- 改善要望の詳細から Claude Code 向け / Codex 向けの指示文をコピーでき、AI分析と同じ操作感である
- 指示文を受け取ったエージェントが、追加の口頭説明なしにスクリーンショットと診断情報を取得して改善に着手できる
- エラーが起きていない要望では診断情報が空でも投稿が成立し、エラーがある要望では原因特定に足る診断情報が付く
- 保存された診断情報に秘匿値が含まれない
- 改善要望が対応完了になってから30日でスクリーンショットと診断情報が自動削除され、削除後も要望本文と対応記録は残る
- 改善要望のスクリーンショット・診断情報を保持するテーブルが夜間バックアップ (BACKUP_SNAPSHOT_SQL) の対象に含まれず、テストでその不在が固定されている
- モバイル幅で主要な財務グラフ・比較図がCSSやレイアウト都合で非表示にならない
- グラフを操作しなくても見出し・要約・凡例・値の代替表から結論を理解できる
- グラフの軸・ラベル・凡例が狭幅で重なった場合は、表示密度を下げても意味情報を失わない
- safe-areaと下部タブバーに本文・操作・tooltipが隠れない
- ページ全体の横あふれ、44px未満の主要タップ領域、200%拡大時の情報欠落が0件
- 匿名データだけを使うunit/DOM/build/実描画回帰検査がすべてPASSする

## U8 制約 (constraints)

- 実行基盤は Cloudflare Workers + D1 + R2 で、wrangler.jsonc の migrations_dir は ../../migrations である
- 本番D1への適用コマンドの実行主体は利用者本人とし、AIは手順の提示と検証までを担う (不可逆操作の承認を人間が握る)
- 適用対象は番号上限で固定せず、作業開始時と適用直前のremote listとrepositoryのmigrations/を突合して得たordered pending listを、人間がMigrateで承認したmanifestに限る
- manifestはrepository head・ordered migrations digest・remote applied head・ordered pending files・取得日時・人間の承認日時を持ち、承認後にrepository head・ordered migrations digest・remote listのいずれかが変われば承認を無効化して再取得する
- 恒久policyと通常のD1変更手順のSSOTはdocs/ci-cd-operations.mdとし、incident runbookはremote baseline・承認済みpending manifest・行数突合・証跡へのリンクだけを持つ
- 本番には既存データが存在し、データ喪失ゼロが必須である
- 0007/0010/0011 は cash_entries / attachments を再定義するため、適用順序の逸脱や部分適用を許さない
- D1 には1リクエストあたりのクエリ本数上限があり、取込処理は既存の query budget 設計 (上限未満50) を壊さない
- 明細内容や金額をログ・エラー応答へ含めない既存のセキュリティ方針を維持する
- スクリーンショット撮影はブラウザ内で完結させ、外部のレンダリングサービスへ画面内容を送出しない
- 診断情報は1件あたりの総バイト上限を設け、超過時は古いものから落として省略件数を記録する (無制限に保存しない)
- 診断情報の保存前に Cookie / Authorization / Bearer トークン / パスワード相当の値をマスクする
- 指示文が参照する取得用 API は既存 AI 分析と同じく使い捨て Bearer トークン (prefix 付き・ハッシュ保存・短命) とし、恒久トークンを発行しない
- スクリーンショットと診断情報は会計証憑ではなく税務保存義務の対象外として扱い、対応完了から30日で自動削除する
- 既存の夜間バックアップ (wrangler.jsonc の Cron "0 18 * * *" と scheduledMaintenance / nightlyBackup) は頻度・実装とも変更しない。改善要望の保持期限切れ削除は新規 Cron を増やさず既存 scheduledMaintenance へ1ジョブとして相乗りさせる
- 改善要望のスクリーンショット・診断情報を BACKUP_SNAPSHOT_SQL の列挙対象へ追加しない (追加すると対応完了から30日での削除がバックアップ側で最大30日ぶん骨抜きになるため)
- React 18、Chart.js 4、react-chartjs-2、既存route metadataとCSS tokenを維持する
- モバイルは専用ネイティブアプリではなくレスポンシブWebとして提供する
- 情報を単にdisplay:noneで削除せず、優先度に応じて要約・段階表示・密度調整へ変換する
- 会計値の正確性を保ち、視覚簡略化で符号・期間・単位・比較基準を失わない
- public repositoryのため実データ・口座明細・秘密情報を成果物やテストへ含めない
- 外部UI/chart依存の追加は原則避け、bundle budgetとreduced-motionを維持する
