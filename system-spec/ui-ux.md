- **G3**: 選択を表示に左右されないものにする。選択 (URL の sel に行の key で持つ、最大 50 件) は絞り込み・ページ・並べ替え・期間を変えても保ち、一括バーの選択一覧は表示外の選択も含めて全件を出す (qa-classify-bulk-decision-043)。分割の内訳行は選べず、チェックの代わりに理由を示す (qa-classify-bulk-decision-034・qa-classify-bulk-delegated-002)。分割の設定が不正な明細の行も選べず、理由『分割の設定を直してから保存してください』を示す (qa-classify-bulk-decision-038)。見出しの全選択は表示中の先頭から 50 件までで止め、止めたことを選択の件数の横に示す (qa-classify-bulk-decision-053)。保存はサーバが選択した明細を引き直し、G1 の順で値を解決する。一覧の応答から絞り込み後の全件を外し、選択の中身は行の key を受ける専用の API で読む (qa-classify-bulk-decision-043・qa-classify-bulk-decision-034・qa-classify-bulk-delegated-002)。
- **G4**: 取引一覧を 13-classify.png どおりに読めるようにする。『取引先 / 内容』を 2 段の 1 列にまとめた 6 列 (選択・日付・取引先/内容・金額・提案カテゴリ・信頼度) にし、表示件数の選択 (25 / 50 / 100 件) と全 N 件のページ送りを置く。編集パネルは明細を開いたときだけ幅を取り、閉じている間は一覧へ幅を渡す。それでも足りない幅では表の中だけを横スクロールし、1264px 幅でも文字を 1 字ずつ折り返さない (qa-classify-bulk-decision-044)。

### 本章がかなえる具体的やりたいこと (U9)

- **I1**: 一括操作バーに一括指定欄 (区分・カテゴリ大/中・所有者・支払い方法) を足し、保存の前に内訳 (保存する件数と値の出所、そのうち『カテゴリなし』で保存する件数、外す件数と理由) を出す。
- **I2**: POST /api/transactions/bulk を拡張し、一括指定と各明細の下書きを受け取る。サーバは明細を引き直し、core の解決関数で、未整理の明細は 一括指定→下書き→提案、確定済みの明細は 一括指定→下書き→今の値 の順に値を決める。区分に合うカテゴリの組がどこにも無い明細は、明細の編集の大項目の欄に『カテゴリなし』の予約の値を入れて保存する (『カテゴリなし』のための表と列は足さない。qa-classify-bulk-decision-045)。予約の値は core の 1 か所で定め、一括指定と編集の値としては受け付けない (qa-classify-bulk-decision-048)。値を決められない明細と、区分とカテゴリの組が候補に合わない明細は、明細単位の失敗として返す (画面は保存前に外すので、通常は届かない)。書き込みは json_each で束ねた 1 回の batch で行い (qa-classify-bulk-delegated-001)、batch が失敗したら要求を 2xx で返して保存対象の全件を write_failed にする (qa-classify-bulk-decision-057)。同じ要求を送り直しても、明細の値 (更新時刻を除く)・提案との一致 (done か manual か)・月次集計・履歴は 1 回目の後と変わらない。書き込む前に予算 (1 回の batch の文 50 本・束ねた JSON 2MB) を超えると分かった要求は、明細ごとの結果を持たない 413 で返す。
- **I3**: 選択中の行の key (最大 50 件、利用者ごとに分離) を受けて、表示外の明細も含めて一覧の行の形で返す読み出し API を追加し、一覧の応答から絞り込み後の全件を外す。
- **I5**: 選択を URL の sel に行の key で持ち、絞り込み・ページ・並べ替え・期間の変更で消さない。一括バーの選択一覧は I3 の API から全件を出す。内訳行と分割の設定が不正な行は選べず理由を出し、見出しの全選択は表示中の先頭から 50 件で止めて知らせる。
- **I6**: 取引一覧を 6 列 (取引先/内容の 2 段) にし、表示件数の選択とページ送りを置く。編集パネルを明細を開いたときだけの可変幅にし、表の中だけを横スクロールさせる。画面検査に 1264px と 1280px の明細仕分けを足す。
- **I7**: 再試行を、書き込みの失敗 (results の ok=false かつ code=write_failed) を返した明細にだけ出し、押すとその txId だけを送る。ほかの失敗には理由を出す。要求全体の失敗は、ApiError の status を 1 つの関数で分け、文言と再試行の有無をそこから引く。通信の失敗と 5xx は一覧を読み直し、通信の失敗・5xx・409 には直前の要求の本文をそのまま送る『同じ内容で再試行』を出し、400・403・413 にはサーバの文言を出す。401 は既存のログイン切れの扱いに従う。
- **I9**: 『カテゴリなし』の予約の値を core の 1 か所で定め、家計の集計・総収支の内訳・説明可能率・分類の状態・候補の検査・履歴・バックアップで、予約の値を未分類と同じ扱いに通す。予約の値と同じ名前のカテゴリの候補は作れなくする。

### 本章に効く確定意思決定

### 本章での適用

Information Design card の『task 頻度 × 失敗コストで束に順位を付ける』を、明細仕分け画面の一括操作バーに適用した。最も頻度が高い task は『選んだ明細をまとめて確定する』なので、一括指定欄 (区分・カテゴリ大/中・所有者・支払い方法) と保存ボタンを選択一覧の直下の 1 か所に集める。失敗コストが最も高いのは『数十件を意図しない値で保存する』と『保存できたと誤解する』なので、保存ボタンの直前に保存前の内訳 (保存する件数と値の出所ごとの件数、そのうち『カテゴリなし』で保存する件数、外す件数とその理由) を置き、押したあとは成功件数を status、失敗を alert に分けて出す。失敗の後に出す操作も失敗の種類で絞り、送り直すと結果が変わりうる失敗 (書き込みの失敗を返した明細と、要求全体の通信の失敗・5xx・409) にだけ再試行を出し、結果の変わらない失敗には理由だけを出す (qa-classify-bulk-decision-018・qa-classify-bulk-decision-054〜057)。『残す・落とす・加工する』は取引一覧に当て、取引先と内容を 2 段の 1 列に加工して 6 列に絞り、所有者・支払い方法・メモは編集パネルへ落とす。

### Information Design (表現物の情報設計) — deep knowledge card

- 出典カード: `ref-system-design-knowledge/references/information-design.md`

#### 目的

保持しているデータを、受け手が**その利用文脈で最短の認知コストで目的を達成できる形**へ翻訳する。「見た目を良くする」ことではなく、情報の意味的な順序付け・取捨選択・加工を設計判断として明示し、視覚表現をその写像として導出できる状態にする。

#### 解決する問題

- 保存形式 (DB の値・API のフィールド) をそのまま表示形式として採用し、受け手が頭の中で変換させられる (生年月日を見せて年齢を計算させる、絶対日時を見せて「何日前か」を計算させる)。
- 全要素が同じ大きさ・同じ濃度で並び、どこから見ればよいか分からない (強弱の欠如)。
- ラベル・罫線・説明文など「無くても伝わる要素」が削られず、本体の情報を圧迫する。
- 最初に一つの形式 (表・リスト・箇条書き・JSON ダンプ) を作ってしまい、他の形式との比較機会が失われる (早期形式固定)。
- 装飾が「今風に見せる」ために使われ、操作可能性・状態・重要度といった意味を運んでいない。
- 情報の物理的な近さがグループの意味と一致せず、無関係な要素が隣接して誤読を生む。
- 「設計」と「デザイン」を別工程・別担当に分割し、前工程の出力が後工程の到達可能な品質の上限を決めてしまう。

#### 適用条件

- 人間が読む表現物を生成・レビューするとき (UI 画面、report、slide、ダッシュボード、CLI 出力、通知、エラーメッセージ、仕様書)。
- 出せる情報量が受け手の一度に処理できる量を上回り、取捨選択が避けられないとき。
- 受け手と利用文脈が一つに定まる、または文脈ごとに別表現を作る余地があるとき。

#### 非適用条件

- 機械が消費する成果物 (JSON/DB スキーマ/ログの構造化フィールド) — ここでは網羅性・安定性・後方互換が優先し、削減や加工はむしろ有害。
- 監査・法定表示・原本性が要件で、**元の値をそのまま**提示する義務があるとき (加工は併記に留める)。
- 習熟した専任者が長時間・大量に操作する高密度業務画面。一覧性と一括操作の効率が学習容易性より重い場合、表形式・高密度・等価表示が正解になりうる (Nielsen のユーザビリティ 5 指標のうち efficiency を優先する状況)。
- 探索的な使い捨て成果物で、寿命が短く投資が回収できないとき。

#### トレードオフ・失敗モード

- **学習容易性 ⇄ 効率性**: 情報を削って強弱を付けるほど初見は分かりやすくなるが、熟練者の一覧性・一括操作は落ちる。どちらを取るかは context of use が決めるのであって、原則が決めるのではない。
- **加工 ⇄ 検証コスト**: 表示値を加工するほど元データとの突合テストが増える。加工の各件に「どの task を助けるか」を書けないなら加工しない。
- 優先順位付けを飛ばしたまま視覚変数だけ調整し、「なんとなく今風」だが読み順が崩れた表現物を作る (最頻の失敗)。
- 削減を進めすぎて、文脈を持たない受け手が識別できなくなる (会員 No. のラベルまで落とす等)。削減の停止条件は「ラベルなしで受け手が識別できるか」。
- 「シンプルにする」を目的化し、必要な状態表示・エラー理由・可逆性の手がかりまで削る。
- 原則を checklist 化して機械適用し、非適用条件 (高密度業務画面・監査表示) に当てはめて品質を落とす。
- 強弱を色だけで表現し、色覚特性・モノクロ印刷・低コントラスト環境で情報が消える。

#### goalへの寄与

- 要件定義段階で「この表現物の受け手・task・優先順位」を宣言させることで、実装後の主観的な「なんかダサい」を**設計判断への差し戻し**に変換できる (レビューが好みの表明でなくなる)。
- 順位・グループ・削除理由・加工理由が構造化データとして残るため、生成 AI・人間のどちらが作っても同じ根拠で検証できる。決定論ゲート (`../../../scripts/validate-information-priority.py`) が手順の順序制約 (装飾より前に順位が確定していること) を機械検査する。
- 成果は「見た目の評価」ではなく outcome で測る: 目的達成までの操作数・初見での到達率・誤操作率・問い合わせ件数。装飾の量では測らない。
