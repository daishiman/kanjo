## U1 本質的目的 (essential_purpose)

改善リクエスト画面を、『画面の文脈を保ったまま、改善を共有しますか？』という問いに 1 画面で答え切る場にする。使っていて困ったことを、そのとき見えていた画面 (個人情報を伏せた画像) と診断情報ごと 1 画面で送り、送った依頼の状態・履歴・関連する依頼を同じ画面で追い、Claude Code / Codex がそのまま着手できる指示文として取り出す。送る前に何が伏せられるかを利用者が確かめられ、送った後も誤って消した依頼を戻せることで、改善の経路から個人情報と記録の欠けを無くす。

## U2 背景 (background)

改善要望は 2026-09-02 のサイクルで実装済みである (migrations/0029_improvement_requests.sql、packages/core/src/improvement.ts、packages/api/src/routes/improvement.ts、packages/web/src/pages/Improvement.tsx 255 行、投稿は components/ImprovementRequestButton.tsx のモーダル)。現行は見出しが『改善要望』で、件名 120 字＋本文 4000 字を入力し、状態は未対応/対応中/対応済み/対応しない。一覧に検索・状態別の件数タブ・ページングが無く、詳細にアクティビティ履歴・関連する依頼・削除が無い。番号は内部 id (TEXT) のみ。マスクは秘匿値・メール・10 桁以上の数字・URL クエリだけで、画像そのものは伏せない。プライバシーの確認も無い。design/FINAL-UI/images/20-improvement.png がこれらを 1 画面に並べた完成形を示したため、画面を作り直す。

## U5 成功基準 (success_criteria)

- S1 (G1): /improvement で 20-improvement.png の構成要素 (共通シェルの文言を除く) がすべて描画され、色・余白・部品はトークンと共通部品経由で、直書き色の lint が 0 件である。
- S2 (G2): 本文・関連ページ・診断情報は保存前にサーバで再マスクする。画像は撮影時に伏字にして利用者がプレビューを確認する。画像内の機密情報 0 件は保証しない。
- S3 (G3): 状態・概要・番号・検索・件数・ページング・関連・アクティビティ・診断要約・マスクが core だけで計算され、API と web はその結果を写すだけである。
- S4 (G4): 他の利用者の依頼の取得・変更・削除・復元が 404、不正な入力 (空の本文、1000 字超、プライバシー確認の欠け、候補外の状態、形式外・2MB 超の画像) が 400 になり、削除した依頼は『元に戻す』で同じ番号のまま戻る。

## U6 ステークホルダー (stakeholders)

- SH1 利用者 (個人事業主とその家族の家計を 1 人で管理する): 使っていて困ったことを、その画面を離れずに、個人情報を心配せずに送りたい。送った依頼がいまどうなっているかを一覧で追い、対応済みのものを確かめたい。
- SH2 開発兼運用者 (Claude Code / Codex で改善する): 依頼を、画面と診断情報つきの指示文として取り出し、追加の説明なしに着手したい。受付から完了までの状態を変え、その経緯を履歴に残したい。

## U7 スコープ (scope)

- **対象 (in)**: 改善リクエスト画面 (20-improvement.png の構成要素と読込 / 空 / 失敗の各状態) の作り直しと、Improvement.tsx の pages/improvement/ 配下への分割。見出しを『改善リクエスト』に揃える, 作成フォームの画面内への配置 (件名欄を廃止し本文 1000 字、概要は本文 1 行目から core で最大 40 字を切り出す)、プライバシー確認 2 つの必須化、自動マスキングの対象の説明, 画面キャプチャの浮動パネル (キャプチャする・範囲を選択する)。右下の『改善を送る』から、どの画面でもパネルを出し、撮影後に /improvement の作成フォームへ画像と関連ページを持って移る。撮り直しは関連ページへ戻ってパネルを出す, 撮影用 DOM 複製の伏字 (金額・取引先名・名義・口座など) と、本文・診断情報のマスク規則の拡張 (取引先名は利用者自身の取引先の辞書、金額・電話・住所・個人名の規則), 状態を受付 / 対応中 / 完了 / 再確認 (利用者の確認待ち) に改め、既存の対応しない (wontfix) は完了へ移して理由をアクティビティに残す。30 日削除の起点は完了のまま, 利用者ごとの連番 (IMP-024 表示、削除しても再利用しない)、アクティビティ履歴の表、論理削除の列を足す migration 0054 と、削除・復元・一覧の検索/件数/ページングの API, 詳細パネル (マスク済み診断の表示用要約、関連する依頼 = 同じ関連ページの他の依頼を新しい順に最大 3 件、状態の変更、再発行、Claude Code 用 / Codex 用のコピー、削除)、選択中バー、コピー完了トースト, core の純関数 improvement-screen と API の拡張、夜間の完全消去の相乗り
- **対象外 (out)**: 共通シェルの文言 (取引ライン / 最終更新 / 月次クローズ / フッター) の変更。画像の文言は期待値にしない, 改善を起点とした自動修正・自動 PR 作成、外部の課題管理サービスへの連携 (2026-09-02 サイクルの範囲外を維持), 関連する依頼の手動紐付け (自動導出だけにする), 複数利用者間での依頼の共有と権限分離 (単一利用者の運用を維持), モバイル・タブレット・デスクトップ専用アプリ (レスポンシブ web で狭い幅に対応する)

## U8 制約 (constraints)

- C1 技術: pnpm monorepo (core は依存ゼロの純関数、api は Hono の Cloudflare Worker と D1/Drizzle と R2 (FILES)、web は React 18 + react-router-dom 7 + TanStack Query 5)。判定と導出は core に置き api/web は写すだけにする。
- C2 データ: 本機能の D1 migration は `0054_improvement_request_screen.sql` とする（計画時の 0053 は取込画面で使用）。既存の improvement_requests の行・R2 の画像・トークンを失わない。1000 字を超える既存の本文は読めるまま保つ (新規と編集だけ 1000 字で検証)。論理削除の列を足した後、全ての読み取り経路が削除中の行を読まない。
- C3 運用: 夜間の scheduled 処理 (0 18 * * *) の予算内に完全消去を相乗りさせ、新しい Cron を増やさない。改善リクエストの表を BACKUP_SNAPSHOT_SQL へ入れない。単一利用者の運用。
- C4 品質とプライバシー: 撮影はブラウザ内で完結させ外部へ画面を送らない。初期 JS 予算・verify:full・skills:test を緑のまま保つ。public repository のため実データをテストと成果物へ含めない。
