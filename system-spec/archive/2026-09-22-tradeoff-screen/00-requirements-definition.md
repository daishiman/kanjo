## U1 本質的目的 (essential_purpose)

トレードオフ画面を、『新しい支出を増やすなら、何を見直しますか？』という問いに 1 画面で答え切る場にする。利用者が新しい支出 (支出名・金額・単発 / 毎月・開始月・メモ) を置くと、事業経費を科目×取引先ごとに並べた見直し候補 (月額・年額・必要度・直近の推移・理由) から削減先を選べ、core が決まったルールで出す推奨の組み合わせと理由を参考に、年間の差額と防衛ラインへの影響を確かめてから、その条件を記録して予算・サブスク・明細の画面で手を打てる状態にする。アプリ自身は LLM を呼ばず、試算の数字はすべて core の 1 か所から導く。

## U2 背景 (background)

現行の /tradeoff (packages/web/src/pages/Tradeoff.tsx、257 行) は FR-09 やりくり試算として、内容・金額・単発 / 毎月の入力と、診断の検知器の改善案 (サブスク重複・急増・予算超過・レンジ超過・説明不能) を写した候補の選択、『捻出合計 − 予定支出』の月額同士の 2 値判定、試算の保存と翌月の突合を持つ。15-tradeoff.png と比べると、開始月・メモ、候補表の列見出しと検索・カテゴリ絞込、科目×取引先の経費全体からの候補、必要度・直近の推移・理由の列、推奨の組み合わせ、右側の試算結果と年額の差額、防衛ラインへの影響、計算の前提と計算例、下部の選択中バーが無い。単発の支出も月額として比べており、単発は発生月だけに計上するという画像の前提と合わない。計算は画面内のインラインで、core に試算関数が無い。防衛ライン (defenseLine) は core と /api/defense-line にあるが、試算がそれにどう効くかを出す場所が無い。

| G4 | 推奨の組み合わせを core の決まったルールで出す。候補 2〜4 件の組み合わせのうち年間削減額が新しい支出の年額以上になるものを選び、充足度・実行のしやすさ (必要度の低い候補が多いほど易しい)・リスク (必要度の高い候補を含むほど高い) で順位を付けて上位 4 件を示し、選んだ組み合わせの理由の文と関連ページ (サブスク・予算・明細) へのリンクを添える。アプリは LLM を呼ばない。 |
| G5 | 試算条件と候補ごとの上書きを安全に記録する。『この条件で試算』を押すたびに条件 (支出名・金額・単発 / 毎月・開始月・メモ・選んだ候補・差額) を既存 tradeoff_plans へ履歴として追加し、画面は最新の 1 件を復元する。保存一覧と翌月の突合は画面から外すが、既存の行と突合の関数は消さない。列と表は追加のみの migration で足し、入力は zod で検証し文字数に上限を設け、利用者ごとに分離する。 |

## U5 成功基準 (success_criteria)

- S1 (G1): /tradeoff で 15-tradeoff.png の構成要素がすべて描画され、色・余白・部品はトークンと共通 Button / PageShell 経由で、直書き色の lint が 0 件である。期間は usePeriod から来る。
- S2 (G2): 年額・差額・防衛ラインへの影響は core の 1 関数だけが決め、画面の右パネル・選択中バー・計算例が同じ値を示す。単発は発生月だけに計上される。
- S3 (G3): 候補は科目×取引先の経費全体から出て、必要度と推移と理由が全行に付き、利用者の上書きとメモが再読込後も残る。
- S4 (G4): 推奨の組み合わせは同じ入力で同じ上位 4 件を返し、選ぶと理由の文と関連ページへのリンクが出る。
- S5 (G5): 『この条件で試算』で条件が履歴として追加され、再訪時に最新の条件が復元される。migration は追加のみで、既存の試算の行は変わらない。
- S6 (全体): typecheck・lint・core / api / web のテスト・初期 JS 予算の CI 実測が緑である。

## U6 ステークホルダー (stakeholders)

- SH1 利用者 (個人事業主とその家族の家計を 1 人で管理する): 新しいツールや外注を増やしたいとき、どの支出をどれだけ減らせば釣り合うかを 1 画面で試し、防衛ラインを割らないことを確かめてから決めたい。候補の必要度は自分の感覚で直したい。
- SH2 家族 (同じ家計を見る閲覧者): 試算の結論と理由を、数字の出どころが分かる形で読みたい。
- SH3 開発者 (本人): 計算を core の 1 か所に集め、画面・API・テストで重複させず、既存の防衛ライン・診断の検知器・試算の履歴を壊さずに作り直したい。

## U7 スコープ (scope)

- **対象 (in)**: トレードオフ画面 (15-tradeoff.png の全構成要素と読込 / 空 / 失敗の各状態) の作り直しと、Tradeoff.tsx の pages/tradeoff/ 配下への分割, core の純関数: 科目×取引先の候補集計と直近 3 か月平均、推移の区分、必要度の推定、自動の理由、試算 (年額・差額・単発の計上)、防衛ラインへの影響、推奨の組み合わせの列挙と評価と理由, GET /api/tradeoff の応答の作り直し (候補・上書き・防衛ラインの月の余裕・最新の試算条件) と、候補ごとの上書き (必要度・メモ) の保存 API, POST /api/tradeoff の入力に開始月・メモ・候補キーを足した履歴の追加と、最新 1 件の復元, 追加のみの migration (tradeoff_plans への開始月・メモ列、候補ごとの上書きの新表), 下部の選択中バー、候補表の検索・カテゴリ絞込・全クリア、推奨の理由と関連ページへのリンク、計算例, docs への規則 (候補の作り方・必要度・推移・推奨の順位・防衛ラインへの影響) の明記と回帰テスト
- **対象外 (out)**: 共通シェル (ヘッダーの取引ライン・検索・ダウンロード・ヘルプ、サイドバー、フッター、月次クローズの進捗、改善を送る) の作り直し: 既存実装をそのまま使う, 保存済みの試算の一覧と翌月の突合の画面表示: 画面から外す (利用者決定)。既存の行と tradeoffReview は残す, アプリから LLM を呼ぶこと・AI分析レポートからの推奨の取り込み: 推奨は core のルールで出す (利用者決定), 既存の tradeoff_plans の行やテーブルの削除・書換, 税・手数料の考慮: 画像の計算の前提どおり考慮しない, スマートフォン・タブレット・デスクトップ向け専用アプリ: web のみ (既存方針), 画像の数値 (金額・件数・取引先名) の再現: モックであり実データを正とする

## U8 制約 (constraints)

- C1 技術: pnpm monorepo (core は依存ゼロの純関数、api は Hono の Cloudflare Worker と D1/Drizzle、web は React 18 + react-router-dom 7 + TanStack Query 5)。判定と導出は core に置き api/web へ重複実装しない。
- C2 デザイン: docs/design-system.md に従い、色は design-tokens.ts 由来のトークンだけ、ボタンは共通 Button、ページは PageShell。表・選択中バーは既存画面 (サブスク・診断) の部品と流儀に揃える。
- C3 migration: D1 の migration は追加のみ (新カラム・新表) とし、行を書き換える migration は作らない。本番反映は既存の Deploy / Migrate の手順とゲートに従う。
- C4 セキュリティ: API は /api/* の authGuard・mustChangePasswordFence・runtimeSchemaGuard・canonicalMutationFence の内側に置き、入力は zod で検証して文字数と件数に上限を設け、全クエリを user_id で絞る。利用者の文字列は React の既定エスケープで描画する。
- C5 互換: 既存の防衛ライン (defenseLine・/api/defense-line・ヘッダーのバッジ・概要画面) と、診断の検知器 (tradeoffCandidates を使う分析ハブの改善余地) の数字を変えない。
- C6 性能: 初期 JS 予算 (CI 実測) を超えない。トレードオフ画面は遅延読み込みのままにする。組み合わせの列挙は候補数に上限を設けて計算量を抑える。
- C7 数値の正本: 15-tradeoff.png の金額・取引先名はモックで、実データを正とする。
