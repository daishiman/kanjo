## U1 本質的目的 (essential_purpose)

設定画面を、『集計ルールと復元設定を、安全に管理しますか？』という問いに 1 画面で答え切る場にする。利用者は左の節ナビ (集計ルール・名義・統計・現金上書き・データ・バックアップ、続けてアカウント・その他の管理) で目的の節へ移り、集計ルール (勘定科目と取引先の表記ゆれを 1 つの一覧で正規化後のカテゴリへまとめる) を行ごとに編集・並べ替え・一括削除し、右の『この設定の説明』でそのルールが何に影響し、いつ誰が変えたかを確かめて直前の保存値へ戻せる。名義の表示名・統計の最小月数・現金上書き (空欄と 0 円を区別) を同じ下書きで編集し、下部の保存バーで未保存の件数を見て 1 回で保存する。設定だけを JSON で書き出して別の日に復元でき、毎晩 2:00 の自動バックアップを状態・メモ付きで一覧し、現在の設定と比べてから戻せる。設定の変更で集計・分析・レポートの前提が黙って壊れないこと、戻せない操作が 0 件であることを本質とする。

## U2 背景 (background)

現行の /settings (packages/web/src/pages/Settings.tsx、457 行の 1 ファイル) はカードを縦に並べるだけで、節ナビ・説明パネル・保存バーが無く、節ごとに PUT /api/settings を別々に送る。下書き・未保存件数・409 競合の検出が無い。科目正規化マップ (account_norm_map、0000_init.sql) は (user_id, raw, norm) のみで並び順・有効フラグ・更新日時・更新者を持たず、正規化後はテキスト入力である。デザイン (design/FINAL-UI/images/18-settings.png、AUDIT.md『抽象的な分類に寄りすぎ。正規化、名義、最低月数、現金上書き、復元を具体化』) は取引先名の表記ゆれ (スターバックス / スタバ / Starbucks → カフェ・外食) も同じ一覧で扱う。名義の表示名は 4 名義 (事業・配偶者・家族・未設定) の API (GET/PUT /api/settings/owner-labels) があるが編集 UI は家計収支画面にしかない。現金補正 (cash_overrides) は月ごとの入金・支出だけで、空欄は 0 に潰れ、メモ・適用範囲が無く、core のどの集計にも効いていない。JSON 書き出しは取引を含む全データで、復元は HTML 版からの初期移行 (全データ置換、形の検査のみ・サイズ上限なし) しかない。夜間バックアップ (cron 0 18 * * * = JST 3:00、R2 backups/YYYY-MM-DD.json、30 日保持) は状態・メモを持たず失敗はログにしか出ない。設定変更の監査記録は無い。

## U5 成功基準 (success_criteria)

- S1 (G1): /settings で 18-settings.png の構成要素がすべて描画され、色・余白・部品はトークンと共通部品経由で、直書き色の lint が 0 件である。375px で崩れない。
- S2 (G2): 同じ入力で画面の説明パネルの『影響するもの』・集計結果・エクスポートが同じ core の関数から出る。取引先ルールの優先順位と現金上書きの空欄 / 0 の区別がテストで固定される。既存の勘定科目正規化の結果の回帰が 0 件である。
- S3 (G3): 全節の変更が 1 回の保存で確定し、競合は 409 で検出され、変更履歴は追記のみで、『元に戻す』は直前の保存値に戻る。
- S4 (G4): 設定のみの JSON の書き出し→復元で設定が一致し取引は不変、不正な JSON は何も変えずに拒否される。自動バックアップが JST 2:00 に状態つきで残り、比較と復元ができる。
- S5 (G5): migration は追加のみで既存行の書き換え 0 件、外部送信 0 件、画像外の既存設定機能は 1 つも消えない。verify:full が緑である。
