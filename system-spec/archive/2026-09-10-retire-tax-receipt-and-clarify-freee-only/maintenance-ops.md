#### 裏付け質疑: `qa-infrastructure-alternatives-001`

**問**

月次トータル収支の算出について、要求時に毎回導出する以外にどのような選択肢があり、なぜそれを採らないのか。インフラ構成を変える必要はあるか。

**答**

検討した代替案は3つ。(a)cron で夜間に月次合計を事前計算し D1 のテーブルへ書き出す: 採らない。導出値を canonical と二重に持つことになり、取込・取消・undo・利用者の手当てのたびに再計算漏れが起きると、画面の合計と明細が食い違う。この食い違いは利用者からは検算不能で、G3(利用者の手で検算できる)を直接損なう。(b)Durable Objects や KV に集計結果をキャッシュする: 採らない。同じ二重保持の問題に加え、無効化のタイミングという新しい失敗モードを増やす。(c)集計を D1 の SQL 側へ寄せてビュー化する: 採らない。重複判定の規則(min(n,m) の基数規則)を SQL とアプリの二箇所に持つ危険があり、制約『判定を1箇所に置いて複製しない』に反する。毎回導出が成立する根拠は取得済み公式出典 cloudflare-d1-limits にある: Worker 1呼出しあたりのクエリ数は 1,000 (Workers Paid)、SQL文の最大長 100KB、クエリ最大実行時間 30秒、バインドパラメータは1クエリあたり最大100。本機能は月次数十行規模の集計であり、対象期間の明細を数クエリで取得してアプリ側で突合する形に収まる(バインドパラメータ上限100を跨がないよう、期間指定は範囲条件で表現し個別IDの列挙を避ける)。結論としてインフラ構成は変えない。新しいスケジュール実行・新しい監視基盤・新しいデータストアをいずれも追加せず、既存の Cloudflare Workers + D1 + R2 の1系統に載せる。

- (根拠の性質: アシスタントの推定 (利用者確認も検証可能な出典も経ていない) / 出所: アシスタントの分析。代替案の棄却理由は取得済み公式ドキュメント (fetched-references) と既存コードの制約に接地しているが、案の採否そのものは別途 AskUserQuestion で利用者採択を取り直している (末尾 -002 の質疑)。)

## To-Be / Delta

> 本章の**規範**。上位概念 (要件定義書 U3 ゴール / U4 目標 / U9 具体的やりたいこと) を本章の serves_goals で絞り込んだ射影であり、設計知識 card (非規範の参考資料) とは役割が異なる。As-Is (現行実装の姿) は spec-state.json の管轄外のため本節では断定せず、到達点と、その到達を判定する観測点だけを規範として置く。

### 到達すべき状態 (To-Be)

- **G4**: 金額または発生日が一致せず自動で事業費へ寄せられなかった重複候補を『要確認』として理由付きで列挙し、利用者が一度『同じ/違う』を判断すれば、次回以降の取込でその判断が再適用される状態にする
- **G7**: 期間を切り替えても、合算・消し込み・トレンド判定が同じ規則で再計算され、期間ごとに矛盾した数字が出ない状態にする

### 受入条件 (Delta の判定点)

| 目標 | 到達点 | 達成の観測点 (measure) |
|---|---|---|
| O4 | 要確認明細の判断を永続化し、集計へ反映したうえで再適用する | 利用者が下した『同じ/違う』の判断が保存され、再取込後も同じ明細へ再適用されることを結合テストで示す。加えて『同じ』判断が付いた明細が事業費側へ寄り、判断の前後いずれでも 総支出 = 事業費 + 家計費 の恒等式が成立することを契約テストで固定する |
| O6 | 一覧表を画面へ出し、判断の入口を既存の明細編集画面に置く | 月次行・合計行・消し込み列・要確認件数を含む表が web 画面に表示され期間切替に追随すること、および要確認の『同じ/違う』判断が既存の取込明細編集画面から行えて判断後に一覧表の数字が更新されることを示す。加えて9列すべてが常時表示されること、および取込完了時に要確認が残っている場合に画面へ警告が出ることを示す |

### 本章がかなえる具体的やりたいこと (U9)

- **I5**: 自動で確定できなかった重複候補を、理由付きの要確認一覧として出す。候補は『金額一致 かつ 発生日が±3日以内』で抽出し、この抽出自体は合計を変えない
- **I6**: 要確認明細への『同じ/違う』判断を既存の取込明細編集画面から行えるようにし、判断を保存して次の取込でも再適用する。『同じ』判断は合計へ反映する — 支出は当該 MF 明細を家計費から外して事業費へ寄せ、収入は当該 MF 入金を家計収入から外して事業収入へ寄せる (支出と収入で同一の規則)
- **I9**: 期間切替に一覧表・消し込み・トレンドを追随させる

### 本章に効く確定意思決定

- **dec-trend-method-001**: トータル支出の推移(増加/減少/横ばい/判定不可)を判定する統計手法をどれにするか。既存 packages/core/src/trend.ts の基準に合わせるか、別手法を導入するか。
  - 採択: 既存の Mann-Kendall 検定 + Theil-Sen 傾き推定に合わせる (`opt-mk-ts`)
  - 目的適合: G5 を直接満たす。判定語も既存の TrendDirection ('増加'|'減少'|'横ばい'|'判定不可') を共有するため、同一画面でカテゴリ別トレンドとトータルトレンドが異なる基準で判定されることがなく G7 (期間を切り替えても矛盾した数字が出ない) にも資する。
  - 採択の接地根拠: `qa-decision-trend-method-002`
- **dec-auth-boundary-001**: 本機能 (トータル収支の一覧表と要確認判断API) の認証境界をどこに置くか。既存 /api 認証ゲートの内側に置くか、別経路を設けるか、Cloudflare Access へ一本化するか。
  - 採択: 既存の /api 認証ゲートの内側に置く (`opt-existing-gate`)
  - 目的適合: G1 (一覧表を確認できる) と G7 (期間切替でも一貫) を満たすうえで認証は前提条件であり、既存ゲートに載せることで本機能だけ到達性が異なる状態を作らない。wrangler.jsonc の run_worker_first: ['/api/*'] により、追加する読み取りAPI・DuplicateVerdict 更新API も必ずゲートを通る。
  - 採択の接地根拠: `qa-decision-auth-boundary-002`
- **dec-aggregation-strategy-001**: 月次トータル収支 (総収入・総支出・総収支・事業費・家計費・寄せた件数) をどう算出するか。要求時に毎回導出するか、事前計算して保存するか、SQL 側へ寄せるか。
  - 採択: 要求時に canonical から毎回導出する (`opt-derive-on-request`)
  - 目的適合: G3 (合計が『事業費 + 家計費』として利用者の手で検算できる) を最も直接に満たす。canonical が唯一の真実であり、画面の合計と明細が定義上ずれない。G7 (期間切替でも矛盾しない) も、期間ごとに同じ導出関数を通すだけで満たされる。
  - 採択の接地根拠: `qa-decision-aggregation-002`

### Clean Code — deep knowledge card

- 出典カード: `ref-system-design-knowledge/references/clean-code.md`

#### 目的

codeを、次の変更者が意図・制約・failureを短時間で理解し、安全に変更・検証できる作業媒体にする。

#### 解決する問題

- 名前と抽象度が意図を表さず、readerが実装詳細からbusiness ruleを逆算する。
- 一つの変更理由が複数moduleへ散り、副作用とerror pathを予測できない。
- 重複したruleが別々に更新され、仕様のSSOTが崩れる。
- testがimplementation detailへ結合し、refactoringを妨げる。

#### 適用条件

- 複数人・長期保守・高変更頻度・重要ruleがあり、理解と変更の費用が支配的。
- test/lint/review/observabilityで改善効果をfeedbackできる。
- domain languageとcoding conventionをteamで合意・更新できる。

#### 非適用条件

- throwaway explorationでは全規則を先行適用せず、学習後に残すcodeだけを整理する。
- generated/vendor codeへ手動styleを強制しない。generation inputとboundaryを管理する。
- 短い関数、class化、DRY等を絶対値として扱い、局所的な明瞭さを悪化させる場合は適用しない。

#### トレードオフ・失敗モード

- naming/refactoring/testへ時間を使うため、寿命とriskが低いcodeでは投資超過になり得る。
- micro-function化でcontrol flowが多数fileへ散り、かえって読みにくくなる。
- DRYを急ぎ、異なるdomain conceptを一つの抽象へ結合して変更を難しくする。
- commentを全否定して、理由、trade-off、外部制約、security decisionまで消す。
- coverageやlint scoreを目的化し、重要behaviorの未検証を隠す。

#### goalへの寄与

- goalに関わるbusiness ruleを名前とtestで明示し、仕様→code→evidenceのtraceを短くする。
- maintenance objectiveには変更lead time、review指摘、escaped defect、rollback率などのoutcomeを使う。
- 無料toolの導入自体を成功とせず、teamが継続運用でき、重要riskを減らすかで判断する。
