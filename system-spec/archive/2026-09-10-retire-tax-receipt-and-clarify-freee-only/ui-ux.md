**問**

web の一覧表について、読み手は誰で、どのタスクをどの頻度で行い、失敗したときのコストは何か。表に何を残し、何を落とし、何を加工するか。その順位の根拠は何か。

**答**

読み手(audience)は利用者本人1名のみ(個人事業主。事業と家計を一体で回しており、この表の唯一の読み手かつ判断者)。利用環境(environment)は自宅PCのデスクトップブラウザで、時間に追われず腰を据えて読む。熟練度(expertise)は会計ソフト(freee / Money Forward)の日常利用経験があり、本システムの実装者本人でもあるため用語の平易化より正確さを優先してよい。主要タスク(primary_tasks)は3つ: (T1)『その月に全体でいくらプラスかマイナスか』を読む — 頻度は月1〜数回、失敗コストは高(誤った黒字判断で資金繰りを誤る)。(T2)合計の内訳を検算する(総支出 = 事業費 + 家計費 が合うか、事業費へ寄せた件数が妥当か) — 頻度は月1、失敗コストは中(気付けば直せる)。(T3)要確認明細に『同じ/違う』を判断する — 頻度は取込直後、失敗コストは高(誤判断が次回以降の取込へ再適用され累積する)。情報優先度は次の方針を採る。残す: 月・総収入・総支出・総収支(プラスマイナス)・事業費・家計費・事業費へ寄せた件数・要確認件数・支出トレンド判定。落とす: 個別明細(表には出さず行のドリルダウンへ回す)、勘定科目レベルの細分(内訳ビューへ回す)。加工する: 事業費へ寄せた額は必ず件数と併記し『何件ぶんでこの額なのか』を一目で検算可能にする。トレンドは増加/減少/横ばい/判定不可の4語へ丸め、生の統計量は出さない。束の順位は (1)月次のトータル収支行 (2)事業費/家計費の内訳 (3)事業費へ寄せた額と件数 (4)要確認件数 (5)トレンド判定 とする。順位根拠は task 頻度×失敗コスト: T1 が最頻かつ失敗コスト最大のため総収支を最上位に置き、次に T1 の答えを裏づける内訳、その次に T2 の検算材料、最後に T3 への入口という順に並べる。期間切替は表の外側の既存 UI に従属させ、表そのものは期間に依存しない同一の読み方を保つ。

#### 裏付け質疑: `qa-income-verdict-effect-001`

**問**

【AskUserQuestion / 出所=利用者への直接質問・選択肢提示あり】収入側の「要確認」明細を「同じ (= freee と同一の入金)」と判断したとき、合計をどう動かすか。背景: 支出側は qa-verify-verdict-effect-001 で『同じ→家計費から外して事業費へ寄せる』と確定済みだが、収入側は qa-income-dedup-rule-001 で消し込み規則と要確認の可視化まで決めたきり、判断後に総収入・事業収入・家計収入がどう動くかが一度も問われていなかった(独立ヒアリング監査が支出側の H-1〜H-4 と同型の欠落として検出)。

**答**

利用者回答 (選択肢からの明示選択): 「支出と同じ考え方に揃える」を選択。収入側で『同じ』と判断した MF 入金は、家計収入から外して事業収入へ寄せる。freee を正とするため総収入には二重計上分が加算されず、内訳が事業側へ寄る。これにより恒等式が両側で揃う — 総支出 = 事業費 + 家計費、総収入 = 事業収入 + 家計収入。棄却案: (B) MF 側を総収入から落とすだけで内訳の付け替えはしない (支出側と規則が食い違う)、(C) 収入側は判断しても合計を動かさず可視化にとどめる (収入の二重計上が数字に残る)。

## To-Be / Delta

> 本章の**規範**。上位概念 (要件定義書 U3 ゴール / U4 目標 / U9 具体的やりたいこと) を本章の serves_goals で絞り込んだ射影であり、設計知識 card (非規範の参考資料) とは役割が異なる。As-Is (現行実装の姿) は spec-state.json の管轄外のため本節では断定せず、到達点と、その到達を判定する観測点だけを規範として置く。

### 到達すべき状態 (To-Be)

- **G1**: 月ごとのトータル収入・トータル支出・トータル収支(プラスマイナス)を、事業と家計を合算した1つの一覧表として確認できる状態にする
- **G3**: 事業側へ寄せた金額と件数を一覧表の中に明示し、合計が『事業費(freee正) + 家計費(MF残余)』として利用者の手で検算できる状態にする
- **G4**: 金額または発生日が一致せず自動で事業費へ寄せられなかった重複候補を『要確認』として理由付きで列挙し、利用者が一度『同じ/違う』を判断すれば、次回以降の取込でその判断が再適用される状態にする
- **G6**: 合算後も事業側・家計側の内訳を保持し、トータルの増減がどちらの側のどの科目で起きているかまで辿れる状態にする
- **G7**: 期間を切り替えても、合算・消し込み・トレンド判定が同じ規則で再計算され、期間ごとに矛盾した数字が出ない状態にする

### 受入条件 (Delta の判定点)

| 目標 | 到達点 | 達成の観測点 (measure) |
|---|---|---|
| O1 | 月次のトータル収支行を導出する読み取りモデルを core に追加する | months の各月について 総収入・総支出・総収支・事業費・家計費・事業費へ寄せた件数 を返す関数が存在し、契約テストで恒等式 総支出 = 事業費 + 家計費 と 総収入 = 事業収入 + 家計収入 がいずれも全月で成立する |
| O2 | 『MF日付 = freee発生日 かつ 金額一致なら事業費、それ以外は家計費』という支出帰属規則を単一の実装として持つ | (金額,発生日)ごとに MF n 件・freee m 件のとき MF から min(n,m) 件が事業費側へ寄ることを契約テストで固定し、freee 件数を超える付替が0件、支払先を用いた判定が0件、日付近傍(±3日)の照合が要確認候補の抽出にのみ使われ自動付替を1件も行わないこと、および利用者の『同じ』判断による付替が freee 側1取引につき MF 1件までであることを示す |
| O3 | 収入の帰属を MF の事業・副業区分で決め、freee 売上との二重計上を避ける | MF の事業・副業入金が事業収入へ、それ以外が家計収入へ計上されることを契約テストで固定し、freee 売上と同額・同発生日で重なる分が総収入へ二度加算されないことを示す。加えて、日付が一致せず消し込めない組が要確認として出ること、および利用者が『同じ』と判断した入金が家計収入から外れて事業収入へ寄り、判断の前後いずれでも総収入 = 事業収入 + 家計収入 の恒等式が成立することを固定する |
| O4 | 要確認明細の判断を永続化し、集計へ反映したうえで再適用する | 利用者が下した『同じ/違う』の判断が保存され、再取込後も同じ明細へ再適用されることを結合テストで示す。加えて『同じ』判断が付いた明細が事業費側へ寄り、判断の前後いずれでも 総支出 = 事業費 + 家計費 の恒等式が成立することを契約テストで固定する |
| O6 | 一覧表を画面へ出し、判断の入口を既存の明細編集画面に置く | 月次行・合計行・消し込み列・要確認件数を含む表が web 画面に表示され期間切替に追随すること、および要確認の『同じ/違う』判断が既存の取込明細編集画面から行えて判断後に一覧表の数字が更新されることを示す。加えて9列すべてが常時表示されること、および取込完了時に要確認が残っている場合に画面へ警告が出ることを示す |

### 本章がかなえる具体的やりたいこと (U9)

- **I1**: 月ごとに『総収入・総支出・総収支』が並ぶ一覧表を出す
- **I2**: 一覧表に『事業費へ寄せた額』『その件数』の列を置き、支出合計の内訳(事業費/家計費)を見せる
- **I4**: MF 側で事業・副業に分類される入金を事業収入として扱い、それ以外の入金を家計収入とする。freee 売上と同額・同発生日で重なる分は支出と同じ規則で freee を正とし二重計上を避ける。日付が一致せず消し込めない組は要確認として出す
- **I5**: 自動で確定できなかった重複候補を、理由付きの要確認一覧として出す。候補は『金額一致 かつ 発生日が±3日以内』で抽出し、この抽出自体は合計を変えない
- **I6**: 要確認明細への『同じ/違う』判断を既存の取込明細編集画面から行えるようにし、判断を保存して次の取込でも再適用する。『同じ』判断は合計へ反映する — 支出は当該 MF 明細を家計費から外して事業費へ寄せ、収入は当該 MF 入金を家計収入から外して事業収入へ寄せる (支出と収入で同一の規則)
- **I8**: 一覧表の各行から事業側・家計側の内訳へ辿れるようにする
- **I9**: 期間切替に一覧表・消し込み・トレンドを追随させる

### 本章での適用

information-design の『何を残し・落とし・加工するかを先に決める』を、一覧表の列構成に適用した。ただし本章の結論は原理からの導出ではなく利用者の明示選択である — 原理に従えば読み手の主タスク (その月に全体でいくらプラスかマイナスか) に直結しない列は畳むのが定石であり、当初はそう提案した。利用者は 9 列すべての常時表示を選んだ。理由は本件の読み手が単独の個人事業主 1 名で、合計値を見た直後に必ず『なぜこの額か』へ降りるため、畳んだ列を開く操作がそのまま毎回の摩擦になるからである。原理の側を曲げたのではなく、原理が参照する『主タスクの頻度』の実測が提案時の想定と違っていた。要確認の存在は取込完了の時点で画面に警告として出す (これも利用者選択) — 要確認を一覧表の中の件数列だけで示すと、数字が合わない理由に気付くのが読み手の疑問より後になる。

### Information Design (表現物の情報設計) — deep knowledge card

- 出典カード: `ref-system-design-knowledge/references/information-design.md`

#### 目的

保持しているデータを、受け手が**その利用文脈で最短の認知コストで目的を達成できる形**へ翻訳する。「見た目を良くする」ことではなく、情報の意味的な順序付け・取捨選択・加工を設計判断として明示し、視覚表現をその写像として導出できる状態にする。

#### 解決する問題

- 保存形式 (DB の値・API のフィールド) をそのまま表示形式として採用し、受け手が頭の中で変換させられる (生年月日を見せて年齢を計算させる、絶対日時を見せて「何日前か」を計算させる)。
- 全要素が同じ大きさ・同じ濃度で並び、どこから見ればよいか分からない (強弱の欠如)。
- ラベル・罫線・説明文など「無くても伝わる要素」が削られず、本体の情報を圧迫する。
- 最初に一つの形式 (表・リスト・箇条書き・JSON ダンプ) を作ってしまい、他の形式との比較機会が失われる (早期形式固定)。
- 装飾が「今風に見せる」ために使われ、操作可能性・状態・重要度といった意味を運んでいない。
- 情報の物理的な近さがグループの意味と一致せず、無関係な要素が隣接して誤読を生む。
- 「設計」と「デザイン」を別工程・別担当に分割し、前工程の出力が後工程の到達可能な品質の上限を決めてしまう。

#### 適用条件

- 人間が読む表現物を生成・レビューするとき (UI 画面、report、slide、ダッシュボード、CLI 出力、通知、エラーメッセージ、仕様書)。
- 出せる情報量が受け手の一度に処理できる量を上回り、取捨選択が避けられないとき。
- 受け手と利用文脈が一つに定まる、または文脈ごとに別表現を作る余地があるとき。

#### 非適用条件

- 機械が消費する成果物 (JSON/DB スキーマ/ログの構造化フィールド) — ここでは網羅性・安定性・後方互換が優先し、削減や加工はむしろ有害。
- 監査・法定表示・原本性が要件で、**元の値をそのまま**提示する義務があるとき (加工は併記に留める)。
- 習熟した専任者が長時間・大量に操作する高密度業務画面。一覧性と一括操作の効率が学習容易性より重い場合、表形式・高密度・等価表示が正解になりうる (Nielsen のユーザビリティ 5 指標のうち efficiency を優先する状況)。
- 探索的な使い捨て成果物で、寿命が短く投資が回収できないとき。

#### トレードオフ・失敗モード

- **学習容易性 ⇄ 効率性**: 情報を削って強弱を付けるほど初見は分かりやすくなるが、熟練者の一覧性・一括操作は落ちる。どちらを取るかは context of use が決めるのであって、原則が決めるのではない。
- **加工 ⇄ 検証コスト**: 表示値を加工するほど元データとの突合テストが増える。加工の各件に「どの task を助けるか」を書けないなら加工しない。
- 優先順位付けを飛ばしたまま視覚変数だけ調整し、「なんとなく今風」だが読み順が崩れた表現物を作る (最頻の失敗)。
- 削減を進めすぎて、文脈を持たない受け手が識別できなくなる (会員 No. のラベルまで落とす等)。削減の停止条件は「ラベルなしで受け手が識別できるか」。
- 「シンプルにする」を目的化し、必要な状態表示・エラー理由・可逆性の手がかりまで削る。
- 原則を checklist 化して機械適用し、非適用条件 (高密度業務画面・監査表示) に当てはめて品質を落とす。
- 強弱を色だけで表現し、色覚特性・モノクロ印刷・低コントラスト環境で情報が消える。

#### goalへの寄与

- 要件定義段階で「この表現物の受け手・task・優先順位」を宣言させることで、実装後の主観的な「なんかダサい」を**設計判断への差し戻し**に変換できる (レビューが好みの表明でなくなる)。
- 順位・グループ・削除理由・加工理由が構造化データとして残るため、生成 AI・人間のどちらが作っても同じ根拠で検証できる。決定論ゲート (`../../../scripts/validate-information-priority.py`) が手順の順序制約 (装飾より前に順位が確定していること) を機械検査する。
- 成果は「見た目の評価」ではなく outcome で測る: 目的達成までの操作数・初見での到達率・誤操作率・問い合わせ件数。装飾の量では測らない。
