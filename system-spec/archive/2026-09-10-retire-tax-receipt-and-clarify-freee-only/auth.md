#### 裏付け質疑: `qa-auth-web-001`

**問**

認証方式と認可モデルはどうするか。本機能は新しい認証境界を作るか。

**答**

既存の二段構えをそのまま用い、本機能は新しい認証境界を作らない。ACCESS_AUD と ACCESS_TEAM_DOMAIN の両方が設定されていれば Cloudflare Access の JWT を検証し(第一候補)、未設定時はアプリ内セッション認証(AUTH_PASSWORD による照合 + SESSION_SECRET を鍵とする HMAC-SHA256 署名の HttpOnly Cookie 'kanjo_session'、TTL 14日)を既定で有効化する。wrangler の run_worker_first: ['/api/*'] により /api 配下は必ず Worker の認証ゲートを通り、未認証で /api のデータへ到達できる経路は存在しない。本機能が追加する読み取りAPIと DuplicateVerdict 更新APIも同じ /api 配下に置き、同一の認証ミドルウェアの内側に入れる。認可モデルは利用者が単独の個人事業主1名であるためロール分割・テナント分離を持たず、認証を通った唯一の主体が全データへアクセスできる単一主体モデルとする(将来の多主体化は上位概念 U7 のスコープ外)。パスワード認証には既存の login-rate-limit.ts によるブルートフォース対策(失敗回数窓・ロック秒数)が適用され、本機能でこれを迂回する経路を作らない。

- (根拠の性質: コード・設定・公式文書で検証できる観測事実 / 出所: アシスタントによる既存リポジトリの読解 (wrangler.jsonc / packages/{api,core,web} / migrations) に基づく現状記述。利用者への個別確認は経ておらず、誤りがあればコードとの突合で検出される種類の回答である。)

#### 裏付け質疑: `qa-auth-alternatives-001`

**問**

本機能の認証境界について、既存の /api 認証ゲートに載せる以外にどのような選択肢があり、なぜそれを採らないのか。

**答**

検討した代替案は3つ。(a)本機能専用の読み取り専用トークンを発行し、一覧表だけを別経路で公開する: 採らない。認証境界が2つになり、片方の失効・ローテーション漏れが財務データの露出に直結する。単一利用者しかいない本システムで境界を増やす利得がない。(b)一覧表だけ認証不要の公開エンドポイントにする: 採らない。トータル収支は事業と家計の全体像そのものであり、明細より要約のほうが機微性が高い場面すらある。公開する理由が存在しない。(c)Cloudflare Access に一本化し、アプリ内セッション認証を廃止する: 採らない。Access は ACCESS_AUD / ACCESS_TEAM_DOMAIN が設定された環境でのみ機能し、ローカル開発やプレビューでは動かないため、既存の二段構え(未設定時はアプリ内セッション認証)を壊すと開発と本番で認証経路が分岐する。結論として、本機能は新しい認証境界を作らず既存 /api 認証ゲートの内側に置く。run_worker_first: ['/api/*'] により追加する読み取りAPI・DuplicateVerdict 更新APIも必ずゲートを通る。認可はロール分割を持たない単一主体モデルのままとする。

- (根拠の性質: アシスタントの推定 (利用者確認も検証可能な出典も経ていない) / 出所: アシスタントの分析。代替案の棄却理由は取得済み公式ドキュメント (fetched-references) と既存コードの制約に接地しているが、案の採否そのものは別途 AskUserQuestion で利用者採択を取り直している (末尾 -002 の質疑)。)

### 到達すべき状態 (To-Be)

- **G1**: 月ごとのトータル収入・トータル支出・トータル収支(プラスマイナス)を、事業と家計を合算した1つの一覧表として確認できる状態にする
- **G7**: 期間を切り替えても、合算・消し込み・トレンド判定が同じ規則で再計算され、期間ごとに矛盾した数字が出ない状態にする

### 受入条件 (Delta の判定点)

| 目標 | 到達点 | 達成の観測点 (measure) |
|---|---|---|
| O1 | 月次のトータル収支行を導出する読み取りモデルを core に追加する | months の各月について 総収入・総支出・総収支・事業費・家計費・事業費へ寄せた件数 を返す関数が存在し、契約テストで恒等式 総支出 = 事業費 + 家計費 と 総収入 = 事業収入 + 家計収入 がいずれも全月で成立する |
| O3 | 収入の帰属を MF の事業・副業区分で決め、freee 売上との二重計上を避ける | MF の事業・副業入金が事業収入へ、それ以外が家計収入へ計上されることを契約テストで固定し、freee 売上と同額・同発生日で重なる分が総収入へ二度加算されないことを示す。加えて、日付が一致せず消し込めない組が要確認として出ること、および利用者が『同じ』と判断した入金が家計収入から外れて事業収入へ寄り、判断の前後いずれでも総収入 = 事業収入 + 家計収入 の恒等式が成立することを固定する |
| O6 | 一覧表を画面へ出し、判断の入口を既存の明細編集画面に置く | 月次行・合計行・消し込み列・要確認件数を含む表が web 画面に表示され期間切替に追随すること、および要確認の『同じ/違う』判断が既存の取込明細編集画面から行えて判断後に一覧表の数字が更新されることを示す。加えて9列すべてが常時表示されること、および取込完了時に要確認が残っている場合に画面へ警告が出ることを示す |

## 適用された設計知識

> 以下の deep knowledge card は設計判断を支援する**非規範の参考資料**であり、実装済み・検証済みの証拠ではない。カード内の `採否: applied` は設計採用を意味し、実装状態は意味しない。規範となる差分は本章の To-Be / Delta 節と参照先仕様で管理する。

### 本章での適用

secure-by-design の『信頼境界は一箇所に集約し、境界の外側に検証を配らない』を、認証面の形に適用した。本章は認証を web の /api 認証ゲート 1 本に集約し、専用アプリ向けの別資格情報を作らないことを確定させた。これは対象 platform が web だけであることの帰結であると同時に、境界が増えるほど『どこかに認証を通さない入口が残っていないか』を人手で確認し続ける必要が生じるためでもある。今回追加する一覧表とトレンドの読取 API は既存の /api 配下に置き、集計専用の公開エンドポイントを新設しない。集計結果は明細より要約されているぶん漏洩時の実害が小さく見えるが、事業と家計を合算した月次収支は本人の全所得を一行で示すため、明細と同じ扱いにする。

### Secure by Design — deep knowledge card

- 出典カード: `ref-system-design-knowledge/references/secure-by-design.md`

#### 目的

利用者の注意や運用後のpatchへ安全性を押し付けず、systemのdefault、architecture、development lifecycleに安全な結果を組み込み、被害可能性と復旧費を下げる。

#### 解決する問題

- 認証・認可・data protectionが後付けで、business flowと矛盾する。
- defaultが過大権限/公開状態で、利用者の完全な設定に安全性が依存する。
- 単一防御の突破で全面侵害になり、検知・封じ込め・復旧の証拠が無い。
- dependency、secret、build、releaseの供給chain riskが製品境界外として放置される。

#### 適用条件

- identity、個人/機密data、金銭、外部入力、admin操作、multi-tenant boundaryを扱う全system。
- compromise時の影響がgoal、法規、信頼、運用継続を損なう。
- vendor/serviceを使う場合も、共有責任とfailure/exit planを明示できる。

#### 非適用条件

- security自体が不要なsystemは原則ない。asset/threatが極小ならcontrolを軽量化できるが、根拠付きrisk acceptanceが必要。
- controlがthreatを減らさず、accessibility/availability/safetyを重大に損なう場合はそのcontrolを採用しない。代替・補償統制を設計する。
- checklist準拠だけでproject固有のtrust boundaryとabuse caseを置き換えない。

#### トレードオフ・失敗モード

- friction、latency、delivery費、運用負荷が増えるため、risk reductionと明示的に釣り合わせる。
- security theaterとしてcontrol数だけ増やし、owner、evidence、responseを持たない。
- fail closedを無差別適用してavailability/safety incidentを起こす。degraded modeとbreak-glass監査が必要。
- secretを隠しても過大権限や長期credentialを残す、暗号化してもkey lifecycleを設計しない等の局所最適。
- free tier製品を価格だけで選び、audit、export、retention、MFA、incident support不足を見落とす。

#### goalへの寄与

- stakeholderの安全・信頼・継続性をsuccess criteriaへ変換し、threat/control/evidenceをgoalへトレースする。
- security controlは「導入済み」ではなく、阻止/検知/復旧時間、権限範囲、data exposureで効果を測る。
- 予算0制約でも、secure default、最小data、短命credential、標準機能、open-source検査を優先し、残余riskを隠さない。
