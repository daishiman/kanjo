## U1 本質的目的 (essential_purpose)

AI分析画面を、『AIに分析を依頼し、根拠と版を確認しますか？』という問いに 1 画面で答え切る場にする。利用者が共通の期間 (1年 / 2年 / 3年 / 任意) を選ぶと、AI へ渡すデータの中身 (件数と集計値だけで明細は渡さないこと) を確かめたうえで Claude Code / Codex 用の依頼をワンステップでコピーでき、依頼が今どの段階にあるか (待機中 / 実行中 / 完了 / 失敗 / キャンセル と進捗) を一覧で追い、取り消し・再実行・削除をその場で決着でき、返ってきたレポートを取り込んで要約 → 根拠データ → 改善提案 → 関連リンクの順に読み、版の履歴と 2 つの版の差を確かめてから、仕分け・予算・総収支などの画面で手を打てる状態にする。アプリ自身は LLM を呼ばず、データは利用者が依頼をコピーするまで外へ出ない。

## U2 背景 (background)

現行の /ai (packages/web/src/pages/Ai.tsx、1277 行の 1 ファイル) は、独自の期間プリセット (月 / 四半期 / 13か月 / 5年) を持ち共通の期間選択 (usePeriod) と揃っていない。依頼の状態は 結果待ち / 期限切れ / 受信済み の 3 値だけで、依頼番号・進捗・取り消し・再実行が無く、結果の貼り付け欄は依頼ごとに散らばり、JSON の誤りは行と位置を示さない。レポートは長い 1 ページの読み物で、タブ・一覧の検索・版の説明・関連画面への導線が弱い。AI へ渡すデータの件数を依頼前に確かめる場所も無い。API (packages/api/src/routes/ai.ts) は依頼ごとの使い捨てトークン (SHA-256 保存・24 時間) でエージェントを認証するが、エージェント用の経路 (/api/ai/tasks/:id/report など) には body の大きさの上限が無く、データ取得や差し戻しの時刻も記録していないため段階を導けない。design/FINAL-UI/images/12-ai.png はこれらを 1 画面 (1.依頼 / 2.実行中 / 3.レポート と下部の選択中バー) に統合した完成形である。総収支・推移・家計収支・サブスク・診断を同じ流儀で作り直し終えた今、残る『確認』段階の画面として揃える時期にある。

## U5 成功基準 (success_criteria)

- S1 (G1): /ai で 12-ai.png の構成要素がすべて描画され、色・余白・部品はトークンと共通 Button / PageShell 経由で、直書き色の lint が 0 件である。期間は usePeriod から来て、旧プリセット (月 / 四半期 / 13か月 / 5年) が画面から消えている。
- S2 (G2): 依頼の段階と進捗は core の 1 関数だけが決め、api と web に同じ判定の重複実装が 0 件である。依頼 ID は利用者ごとに T-0001 から欠番なく振られる。
- S3 (G3): キャンセル済みの依頼のトークンはエージェント経路で 401 / 410 相当の拒否になり、行は一覧に キャンセル として残る。受信済みの依頼は削除できない。
- S4 (G4): 取り込みで JSON が壊れていても入力が消えず、行と位置が日本語で示される。レポート JSON の schema と skill (run-kanjo-accounting-report) は変更 0 件である。
- S5 (G5): AI へ渡るデータは集計値 (科目・支払先ごとの月別合計など) だけで、明細行と摘要が 0 件である。エージェント経路と貼り付け経路の body 上限が効き、migration は追加のみである。
- S6 (G1-G5): 既存の AI レポート (受信済み・アーカイブ済み・版つき) が作り直し後も一覧と詳細で読め、既存の API テストと初期 JS 予算 (CI 実測) が緑のままである。

## U6 ステークホルダー (stakeholders)

- SH1 利用者 (個人事業主とその家族の家計を 1 人で管理する): 月次クローズの『確認』段階で、期間を選んで AI に分析を頼み、渡すデータの範囲に納得してから依頼をコピーし、返ってきたレポートを根拠と版つきで読み、手を打つ画面へ進みたい。取り消しや再依頼で迷いたくない。
- SH2 外部の AI エージェント (Claude Code / Codex と skill run-kanjo-accounting-report): 依頼ごとの使い捨てトークンでデータを取りに来てレポートを返す。契約 (レポート JSON v3) が変わらないこと、差し戻しの理由が機械で読めることが要る。
- SH3 保守者 (同一人物、および Claude Code などのコーディングエージェント): 段階の導出規則・版の説明規則・タブへの振り分け・データの持ち出し範囲が core の純関数 1 か所と docs・テストで固定されていること。

## U8 制約 (constraints)

- C1 技術: pnpm monorepo (core は依存ゼロの純関数、api は Hono の Cloudflare Worker と D1/Drizzle、web は React 18 + react-router-dom 7 + TanStack Query 5)。判定と導出は core に置き api/web へ重複実装しない。

- C3 migration: D1 の migration は追加のみ (新カラム・新表) とし、行を書き換える migration は作らない。本番反映は既存の Deploy / Migrate の手順とゲートに従う。
- C4 セキュリティ: 利用者向け API は /api/* の authGuard・mustChangePasswordFence・runtimeSchemaGuard・canonicalMutationFence の内側に置き、エージェント経路は依頼ごとの使い捨てトークン (SHA-256 保存・24 時間) だけで認証する。入力は zod で検証し、レポートの文字列は React の既定エスケープで描画して HTML として解釈しない。
- C5 データの持ち出し: AI へ渡すのは集計値だけで、明細の摘要は渡さない。アプリは外部へ自動送信しない。
- C6 互換: レポート JSON 契約 v3 と skill run-kanjo-accounting-report を変えない。既存の受信済みレポートとアーカイブ・版の関係を読めるまま保つ。
- C7 性能: 初期 JS 予算 (CI 実測) を超えない。AI分析画面は遅延読み込みのままにする。
- C8 数値の正本: 12-ai.png の件数・日時・進捗はモックで、実データを正とする。
