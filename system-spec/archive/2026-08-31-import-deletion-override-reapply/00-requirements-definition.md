## U1 本質的目的 (essential_purpose)

freee・マネーフォワード側で元データが後から書き換えられても、利用者が『今ある取込データを、どう消して・どう上書きして・どう入れ直すか』を自分で選んで実行でき、かつ一度自分で直した科目・項目・公私区分といった手当てが取込のたびに失われず継続的に再適用されることで、毎回の入力の手間を極限まで下げながら、帳簿を正しい最新状態へ収束させられる状態を保つ。

## U2 背景 (background)

収支統合管理はfreeeの取引エクスポートとマネーフォワードME の収入・支出詳細/資産推移CSVを取り込んで帳簿を作る。しかし取込元は生きたサービスであり、後から科目名の変更・項目名の変更・明細の追加削除・金額修正が行われる。その結果、既に取り込んだ内容と再ダウンロードしたCSVの内容が食い違う。現在の実装は取込単位では『ファイルに含まれる月の既存データを消して置き換える』月単位の洗い替えだけを持ち(mfCommitStatements の deleteReplacement / assetsCommitStatements の deleteImported)、原本をR2から取込枠へ戻す再取込(POST /restore)も備える。一方で取込APIには削除系のエンドポイントが1本も無く(POST /imports・GET /imports・GET /imports/:id/original・POST /restore のみ)、『この取込をなかったことにする』『この期間を空にする』『全部消して入れ直す』手段が利用者に無い。さらに上書き時に既存と新規のどちらを採るかは実装が一律に決めており、利用者が明細単位・項目単位で判断する余地が無い。手動で入れた公私仕分けのoverride・分割(tx_splits)・現金の記帳(cash_entries)・証憑(attachments)は明細IDが一致する限り維持される設計だが、元データ側でIDが振り直されると黙って孤立する。取込履歴画面には『この取込をやり直す』しか操作が無く、削除も差分確認も存在しない。 さらに、利用者は取り込んだ明細に対して科目や項目名を自分で書き換えて運用している。同じ取引先からの入金・支払いは毎月繰り返し発生するため、取込のたびに同じ手当てを入力し直すことが大きな手間になっている。現状の手当ての受け皿は rules (keyword→公私区分)・overrides (tx_id→公私区分)・account_norm_map (raw科目→正規科目) の3つだが、overrides は tx_id に依存するため、マネーフォワード側でIDが振り直されると手当てが黙って孤立する。また『前回取り込んだときの原本値』をどこにも保持していないため、いま目の前にある値と新しいCSVの値が食い違ったときに、利用者が直したのか取込元が変わったのかを機械的に区別できず、どちらを採るべきかの判定ができない。利用者は将来的に、こうした選択を都度行わなくても自動で判定される状態を望んでいる。

## U3 ゴール (goals)

| ID | ゴール |
|---|---|
| G1 | 取込済みデータを、取込単位・期間単位・データ種別単位・全件のいずれの粒度でも、利用者が意図して削除できる状態にする |
| G2 | 同じ対象を取り込み直すとき、既存と新規が食い違う箇所を実行前に可視化し、上書き・保持・個別選択を利用者が決められる状態にする |
| G3 | 削除と上書きのどちらの経路でも、手動で入れた記録(公私仕分け・分割・現金の記帳・証憑)が意図せず失われず、失う場合は事前に件数で示される状態にする |
| G4 | 削除・上書きは不可逆操作であることを踏まえ、実行前の確認・実行後の取り消し・監査可能な記録を備え、誤操作から回復できる状態にする |
| G5 | 削除・上書き後も、月次集計・現行指紋(import_active_targets)・取込履歴・残高などの派生状態が実データと矛盾しない状態へ必ず収束する |
| G6 | 利用者が一度直した科目・項目・公私区分などの手当てを、同じ取引先・同じ性質の明細へ継続的に再適用し、取込のたびに入力し直す手間をなくす |
| G7 | 取込元の変更と利用者の手当てが衝突したとき、前回取込時の原本値を基準に『利用者が変えたのか取込元が変わったのか』を機械的に区別し、既定でどちらを採るかを自動判定する。判定できない箇所だけ利用者へ問う |

## U4 目標 (objectives)

| ID | 目標 | 測定基準 |
|---|---|---|
| O1 | 取込単位の取り消しを提供する | 取込履歴の各行から、その取込が書いた明細だけを取り消せ、取り消し後にその取込のimport_idを参照する行が0件になる |
| O2 | 期間単位・種別単位・全件の削除を提供する | 月または期間、freee仕訳/MF明細/資産推移/現金記帳の種別、および全件を指定して削除でき、指定範囲外の行が1件も減らない |
| O3 | 取込実行前に既存との差分を提示する | 追加・変更・削除・不変の件数と、変更については項目単位の新旧値を実行前に確認でき、確認せずに書き換えが起きない |
| O4 | 上書きポリシーを利用者が選べる | 同一キーの食い違いに対し『新規で上書き』『既存を保持』『1件ずつ選択』を選べ、選択結果どおりに反映される |
| O5 | 手動記録の巻き添えを事前に示し保全する | 削除・上書きの確認画面に、影響を受ける公私仕分け・分割・現金記帳・証憑の件数が表示され、保全可能なものは実行後も残る |
| O6 | 削除・上書きを取り消せる | 実行直後に取り消し操作があり、取り消し後の各テーブルの行数と内容が実行前と一致する |
| O7 | 派生状態の再収束を保証する | 削除・上書き後にmonthly_agg・import_active_targets・imports・balance_entriesが実データから再計算した値と一致する |
| O8 | 手当てを継続的に再適用する | 一度科目や公私区分を直した取引先の明細が、次回以降の取込で自動的に同じ扱いになり、同じ手当ての再入力が0件になる |
| O9 | 3点比較で変更の出どころを判別する | 前回取込原本値・現在値・新規原本値の3点から、利用者が触っていない項目は新規値、利用者が直した項目は現在値を既定で採り、両方が変わった箇所だけを利用者へ提示する |
| O10 | 利用者へ問う件数を逓減させる | 手当ての蓄積に応じて確信度が上がり、閾値以上は自動適用、閾値未満だけを提示するため、同種の取引について問われる件数が回を追って減る |
| O11 | 学習した決め事を利用者が確認・取り消せる | 自動適用された決め事の一覧を画面から確認でき、個別に取り消すと以後の自動適用が止まる |

## U5 成功基準 (success_criteria)

- 取込履歴から任意の取込を取り消せ、取り消し後にその取込由来の明細が0件になり、他の取込由来の明細が1件も減らない
- 月・期間・種別・全件を指定した削除ができ、指定範囲外のデータが変化しない
- 取込実行前に、追加/変更/削除/不変の件数と変更内容の新旧値を確認でき、確認を経ずに書き換えが起きない
- 同一明細の食い違いに対して上書き・保持・個別選択のいずれかを選べ、選択どおりに反映される
- 削除・上書きの確認時に、失われる可能性のある手動記録の件数が示され、示された件数以外は失われない
- 実行直後の取り消しにより、実行前の状態へ完全に戻せる
- 削除・上書き後に月次集計・現行指紋・取込履歴・残高が実データと矛盾しない
- 誰がいつ何をどれだけ削除・上書きしたかが記録として残り、後から確認できる
- 同じ取引先の明細について、一度直した科目・公私区分が次回以降の取込で自動的に同じ扱いになる
- 利用者が触っていない項目は新規CSVの値が採られ、利用者が直した項目は手当てが維持される
- 利用者の手当てと取込元の変更が同じ項目で衝突した箇所だけが提示され、それ以外は自動で決まる
- マネーフォワード側で明細IDが振り直されても、日付・金額・取引先などの安定した手掛かりで手当てが追随する
- 自動適用された決め事を一覧で確認でき、取り消せば以後適用されない

## U7 スコープ (scope)

- **対象 (in)**: 取込単位(import_id)の取り消しと、その取込が書いた明細・派生状態の巻き戻し, 期間単位(月・期間指定)の削除, データ種別単位(freee仕訳/MF明細/資産推移/現金記帳)の削除, 全件削除(初期化), 取込実行前の差分プレビュー(追加/変更/削除/不変の件数と項目単位の新旧値), 上書きポリシーの選択(新規で上書き/既存を保持/1件ずつ選択), 削除・上書きが手動記録(公私仕分け・分割・現金記帳・証憑)へ与える影響の事前提示と保全, 削除・上書きの取り消し(undo), 削除・上書きの監査記録, 削除・上書き後の派生状態(monthly_agg/import_active_targets/imports/balance_entries)の再収束, 取込履歴画面への削除・差分確認・上書き選択のUI追加, 前回取込時の原本値の保持と、3点比較(前回原本・現在値・新規原本)による変更元の判別, 取引先単位の決め事(科目・項目・公私区分)の学習と、新規明細への自動適用, 自動適用の確信度と、利用者へ問う閾値の設計, 明細の同一性を取込元IDだけに頼らず、安定した手掛かり(日付・金額・取引先・口座)でも辿れるようにすること, 学習した決め事の確認・取り消しUI
- **対象外 (out)**: CSV/ZIPのパース仕様そのものの変更 (列の追加・形式判定ロジックの変更), freee/マネーフォワードのAPI連携による自動同期, 取込以外の経路で作られたデータ(手入力の予算・ルール定義など)の一括削除, 認証方式の変更, D1以外のストア(R2の原本オブジェクト)の保持期間ポリシーの変更, 明細データを外部サービスやLLMへ送信して学習させること (明細は外部送信しない既存方針を維持する), freee/マネーフォワード側のデータを本システムから書き換えること

## U8 制約 (constraints)

- 実行基盤は Cloudflare Workers + D1 + R2 で、D1には1リクエストあたりのクエリ本数上限があり、既存の query budget 設計 (D1_FREE_QUERY_LIMIT=50 未満) を壊さない
- 取込は import_writer_claims による利用者別の単一writer claim (TTL 15分) の配下で行われ、削除・上書きも同じ排他の下で実行する
- 重複判定は import_active_targets の現行指紋で行うため、削除はこの指紋の巻き戻しと必ず対で行う
- 明細内容や金額をログ・エラー応答へ含めない既存のセキュリティ方針を維持する
- 税務上の正はfreeeの記帳であり、本システムのデータ削除がfreee側へ波及してはならない
- 本番D1への破壊的操作であるため、削除・上書きは利用者の明示的な確認を経て実行する
- 既存の月単位洗い替え(mfCommitStatements/assetsCommitStatements)と再取込(POST /restore)の挙動を壊さない
- スキーマ変更が必要な場合は migrations/ 配下の連番SQLをappend-onlyで追加し、既存テーブルの破壊的再定義を避ける
- 学習した決め事はブラックボックスにせず、利用者が一覧で確認し個別に取り消せること
- 自動適用は既存の rules (keyword→公私区分) / overrides (tx_id→公私区分) / account_norm_map (raw科目→正規科目) と矛盾させず、優先順位を明示すること
- 明細データを外部へ送信せずローカル(D1)の情報だけで判定すること
