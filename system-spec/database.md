#### 裏付け質疑: `qa-duplicate-rule-001`

**問**

重複した明細をどう扱うか。照合キーは何にするか。同じキーに MF と freee で件数が食い違う場合 (n≠m、とくに freee 側が多い m>n) はどうするか。

**答**

利用者回答: 金額と日付がイコールのものについては freee を正とし、Money Forward 側を削除(集計から除外)する。日付は Money Forward の日付と freee の発生日 (FreeeDeal.date) を突き合わせる。金額と日付が一致するものは基本的に『事業で使う費用』として扱う。それ以外の費用は家計の方につける。ここから導いた基数規則: 同じ(金額, 発生日)のキーに MF が n 件・freee が m 件あるとき、MF から min(n,m) 件を家計費から外して事業費へ寄せる。(i) n>m のとき、MF に freee より多く明細がある = freee に載っていない支出が (n−m) 件あるということなので、その分は家計費に残す。三井住友の残り2口座の支出が消えないのはこの規則による。(ii) m>n のとき、freee 側に MF に現れない事業経費が (m−n) 件ある = 事業口座から直接払った経費であり、MF 側に消すべきものが無いので MF からは n 件しか外さない。いずれの向きでも『freee にない MF 明細を消さない』『MF にない freee 明細を二重に数えない』が保たれる。金額が同一のキー内では、どの MF 明細を外しても合計は変わらないため、外す対象の選び方は合計値に影響しない。既知の限界として、支払先を判定に用いないため偶然に同額・同発生日となった無関係な支出も事業費として扱われうる。利用者はこれを承知のうえで、規則の単純さと予測可能性を優先すると判断した。また freee の dueDate / settledDate は判定に用いない(カード引落日で照合する取り違えを防ぐ)。日付が一致しない重複(カード利用日と freee 発生日のズレ)は自動判定の対象外となり、要確認として可視化する。

### 本章での適用

DDD の『同一性は識別子ではなく値の意味で決める』を、二重計上の判定に適用した。本章が確定させた保持形は、MF 明細と freee 取引を別テーブルのまま D1 に置き、両者を結び付ける外部キーを持たない。両システムは互いの ID を知らないため、参照で結ぼうとすると存在しない対応関係を捏造することになるからである。代わりに (金額, 発生日) の組を照合の値オブジェクトとみなし、同じ組に MF n 件・freee m 件があるとき min(n,m) 件が対応すると解する。この判断は『どの MF 行がどの freee 行か』を特定できないことを認めたうえで、合計だけは正しくなる範囲に主張を限定している (金額が同一なのでどれを外しても合計は変わらない)。要確認の判断結果は明細そのものではなく判断という別の事実として永続化し、再取込で明細が作り直されても判断が生き残るようにした — 判断を明細の属性にすると、明細の再生成が利用者の意思決定を消してしまう。

### Domain-Driven Design — deep knowledge card

- 出典カード: `ref-system-design-knowledge/references/ddd.md`

#### 目的

businessの重要なruleと用語をmodel/code/会話で一致させ、複雑性を適切な境界へ閉じ込め、継続的な学習をsoftwareへ反映する。

#### 解決する問題

- 仕様語、画面語、DB列、code名がずれ、変更時に意味を再解釈する。
- 異なる業務文脈の同名概念を一modelへ押し込み、巨大で矛盾したmodelになる。
- invariantとtransaction ownerが不明で、どこからでもdataを変更できる。
- legacy codeのtechnical構造がbusiness capabilityを隠し、改善順を決められない。

#### 適用条件

- rule、例外、用語、状態遷移が多く、domain expertとの継続的なmodel学習が価値を持つ。
- team/部門ごとに言葉やownershipが異なり、integrationで翻訳が必要。
- core domainの差別化がsystemの本質的目的に直結する。

#### 非適用条件

- 単純CRUD、汎用supporting機能、既製serviceで十分なgeneric subdomain。
- domain expertへアクセスできず、用語とruleを検証するfeedback loopを作れない段階。
- bounded contextをservice数へ機械変換する目的。monolith内moduleでも境界は成立する。

#### トレードオフ・失敗モード

- workshop、model、mapping、専門語彙の維持に継続的な時間が必要。
- aggregateを大きくしすぎてlock/latencyを増やす、細かくしすぎてinvariantをeventual consistencyへ漏らす。
- 「Repository/Entity」等のpattern名だけ採用したanemic modelになり、business ruleがserviceへ散る。
- bounded contextを組織図やDB tableから決め、実際の言語・capability境界を検証しない。
- eventを事実でなくcommandとして命名し、ordering/idempotency/failure recoveryを設計しない。

#### goalへの寄与

- U1-U9の語彙をmodelへ接続し、goalがどのcontext/capability/invariantで実現されるかを示す。
- core domainへ設計投資を集中し、generic領域は無料/低コストserviceや標準実装も比較対象にできる。
- refactoringは一括rewriteでなく、重要なbusiness rule周辺からstrangler/bubble context等で境界を育てる。
