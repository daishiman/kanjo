## 3. KPI 5 枚

横一列に 5 枚。`KpiCard{label, value, note, tone}` を使う。

| # | ラベル | 値 (画像の読み取り) | 補足行 (画像の読み取り) | 採用する補足行 | 定義 (system-spec) |
| --- | --- | --- | --- | --- | --- |
| 1 | 月額のサブスク合計 | ¥64,800 | 前期間比 -¥3,200 (-4.7%) ↓ | 前期間比 ±¥N (±P%) と矢印 | 最新月時点で継続中の各ベンダーの推定月額の和 (年額払いは 12 等分) |
| 2 | 年換算の合計 | ¥777,600 | 前期間比 -¥38,400 (-4.7%) ↓ | 同上 | 月額 × 12 |
| 3 | 直近12か月の支払額 | ¥742,300 | 対象期間の実績合計 | 対象期間の実績合計 | 既存 `subscriptions().now.last12Total` と一致 |
| 4 | 売上比 | 5.4% | 総支出に占める割合 | **売上に占める割合** | 既存 `now.revenueShare` (直近 3 か月の月合計の平均 ÷ 売上の月平均) |
| 5 | 見直し候補 | 2 件 | 重複・不要の可能性 | 重複・不要の可能性 | 未判断の見直し候補の件数 |

- 前期間比の表記: 差額と率を併記し、減少は「-¥3,200 (-4.7%)」と下向き矢印、増加は「+¥N (+P%)」と
  上向き矢印、差 0 は「±¥0 (±0.0%)」で矢印なし。**色だけで増減を区別させない** (ui-ux.md (8))。
  率は小数 1 桁。前期間の値が 0 のときは率を出さず「—」とする。
- 色: 支出の減少は `good`、増加は `danger`、差 0 は `inkSoft`。
- 前期間比の分母は「前期間の同じ定義の値」。画像の -3,200 / 68,000 = -4.7% と、
  -38,400 = -3,200 × 12 は定義どおりに閉じている (§13.4)。
- 5 枚目の件数は、サイドバーのバッジ (§12) と**同じ関数の同じ値**。確認済み (confirmed) と
  指紋一致の除外 (dismissed) は数えない。
- **食い違い (system-spec を採る)**: 画像の 4 枚目補足「総支出に占める割合」は数値の定義 (売上比) と
  合わない。利用者判断 qa-subs-kpi-caption-001 により「売上に占める割合」と書く。
- 売上が 0 または取れないとき (revenueShare が null) は値を「—」、補足行はそのまま。

## 4. カバー率・最終更新・再取得

### 4.1 データソースのカバー率 (左カード)

- タイトル: 「データソースのカバー率」
- 3 区分を横に並べる。各区分はアイコン・名称・% ・(分子/分母)。

| 区分 | 画像の読み取り |
| --- | --- |
| 銀行口座 | 98% (3/3) |
| クレジットカード | 100% (2/2) |
| 電子マネー | 92% (12/13) |

- 定義 (dec-subs-coverage):
  - 分類: 口座名の手がかりで 銀行 / カード / 電子マネー の 3 つに分ける。`packages/core/src/cash.ts` の
    `paymentMethodOf` を拡張し、カードの手がかりは既存の `CARD_HINTS` (`'カード','ｶｰﾄﾞ','CARD','クレジット'`) を使う。
    電子マネーの手がかりの語彙は system-spec が列挙していないため、core の定数として定め
    `docs/subscriptions-screen.md` に書く (未決 §15.4 U-7)。種別は保存せず、毎回口座名から導く。
  - (分子/分母) = 最新月まで取込済みの口座数 / その区分の口座数。
  - % = 期間の (口座 × 月) のうち取引がある割合。整数に丸める。
  - % と (分子/分母) は別の問いに答える数なので、「98% (3/3)」のように食い違って見えても矛盾ではない。
- 分類できない口座は 3 区分に入れず、カードの下端に「分類できない口座 N 件」と件数だけを出す (0 件のときは出さない)。
- 区分に口座が 0 件のときは「— (0/0)」と出す。
- 画像のアイコン (銀行・カード・電子マネー) は既存のアイコンセットから選ぶ。アイコンの具体形は画像で判読できる範囲で合わせる。

### 4.2 最終更新・再取得 (右の小カード)

- 「最終更新 2026年9月10日 10:24」と「再取得」ボタン (副ボタン)。
- system-spec はこの 2 つの意味 (何の時刻か・何を取り直すか) を定めていない。本仕様の暫定:
  - 最終更新 = 本画面の応答を作った時刻 (`generatedAt`)。
  - 再取得 = `GET /api/subscriptions` を取り直す (TanStack Query の `refetch`)。外部サービスへの再取込はしない。
  - 取り直し中はボタンを無効化し、ラベルを「再取得中…」にする。
- 正式な定義は未決 (§15.4 U-8)。

  ブラウザや中継に保存させない (P10 で追加。api テスト `集計と詳細の応答は保存させない`)。

### 13.2 更新系

すべて `authGuard` と `mustChangePasswordFence` の内側。`:id` / `:key` は `userId` と組で引き、無ければ 404。
入力は Zod で検証する。

| メソッド・パス | 状態 | 本文 | 用途 |
| --- | --- | --- | --- |
| `PUT /api/sub-vendors/:id` | 既存 + `category` を追加、ベンダー名・`aliases` は各120文字へ | `{name?, aliases?, accounts?, category?}` | 正規化名・別名・対象科目・カテゴリの変更。統合の取消 (別名の削除) もこれで行う |

| `POST /api/sub-vendors/:id/review` | 既存 | — | 四半期見直しの記録 (`reviewedAt`) |
| `DELETE /api/sub-vendors/:id` | 既存 | — | 登録の解除 |

- 検証: `vendorKey` は 1〜120 文字 (既存の exclusions の `partner` と同じ上限)、`decision` は enum、
  `category` は既定辞書のカテゴリ名の enum または 1〜20 文字。
- 取引名由来の名前は単一定数 `SUB_VENDOR_NAME_MAX = 120` で検証し、`aliases` は **50 件 × 各120文字** に揃える。
  `PUT /api/sub-vendors/:id`・`POST /api/sub-vendors`・候補除外も同じ文字定数を使う。
  統合 API は結合後の総数が 50 件を超えると 400 を返す。
- 成功後は `['subscriptions', ...]`・詳細のクエリ・`['review-queue']` (`REVIEW_QUEUE_KEY`) を invalidate する。
  サイドバーのバッジを出す既存クエリも invalidate する。
- 楽観更新はしない (§11)。
- 判断は正規化したベンダー名 (`vendor_key`) に付く。`PUT /api/sub-vendors/:id` で名前を変えると、
  同じ batch の中で判断を新しい `vendor_key` へ付け替える (付け替え先に古い判断があれば先に消す)。
  `DELETE /api/sub-vendors/:id` は判断も消し、登録し直したときに古い判断が生き返らないようにする (P10 で追加)。
- 判断を保存するときの期間は、画面が表示中の期間 (`withPeriod` で query に付ける)。指紋はその期間で見た規則の組で、
  サイドバーのバッジは直近 1 年で数える。1 年以外で判断するとバッジが減らないことがある (後続課題)。
