# 明細の分割記帳 — 詳細仕様

**対象**: FR-12(`docs/spec-v1.1.md`) / **画面**: P5 公私仕分け(`/classify`)
**関連**: `docs/data-schema.md`「明細の分割記帳(tx_splits)の投影先」、`architecture/arch-transaction-split-projection.md`

銀行の明細には「10万円 引き落とし」としか書かれていない。中身が電気代・携帯・税金の
混在なら、何にいくら使ったかはどこにも残らない。ここで後から割る。

守りたいのは1つだけ: **割った合計が元の金額と必ず一致すること**。ここが1円でもずれると、
元の明細と内訳のどちらを集計に使うかが決まらず、二重計上か計上漏れが静かに起きる。

## 不変条件

| ID | 不変条件 | 破れたときに起きること |
|---|---|---|
| TS-1 | 内訳の合計は親の金額と完全一致する。1円の差も保存させない | 二重計上または計上漏れ |
| TS-2 | 内訳は2〜50行。0円・小数・科目なしの行は保存しない | 集計に入らない行が黙って増える |
| TS-3 | 保存するのは常に金額。割合は入力の便宜であり永続しない | 親金額の変動で確定済み記帳が勝手に動く |
| TS-4 | 割合→金額の変換は最大剰余法。端数は切り捨てで損をした行から順に返し、同順は添字で決める | 入力し直すたび1円が別の行へ飛び、金額が動いた理由が読めない |
| TS-5 | `line_id`(UUIDv4)は並び順`seq`から独立に維持する | 並べ替えで添付先・編集の宛先が動く |
| TS-6 | 親1行は内訳N行へ**置き換える**。親を残して内訳を足さない | 同じ支出を2回数える |
| TS-7 | 内訳の符号は親の符号から復元する(内訳は絶対値で持つ) | 収入の分割が支出になる |
| TS-8 | 公私・科目は内訳の値、名義・メモは親の値を引き継ぐ | 内訳ごとに名義を選び直させることになる |
| TS-9 | 合計不一致・親金額変動・`line_id`重複・`identity_stable=0` は内訳を集計へ出さず、親の金額のまま数える(fail-closed) | 人の入力ミスが銀行の記録を上書きする |
| TS-10 | fail-closed は黙って隠さず、`splitProjection.state`(`amount_conflict` / `identity_unstable`)を画面へ返す | 直せない不整合が画面から見えない |
| TS-11 | 証憑は内訳ごとではなく**親取引に1件**添付する | 領収書1枚に対して添付先がN個できる |
| TS-12 | 派生した子行に対する quick/edit 操作は409で拒否し、分割エディタへ責務を集約する | 仕分けの経路が二重化する |

**元の明細は銀行の記録そのもので、必ず正しい。内訳は人が入れたもので、間違っていることがある。
迷ったら、確かなほうを残す。** TS-9 はこの原則の実装である。

## 集計への波及

分割は画面上の見た目ではなく**投影**である。`loadDataset()` の既定が `withSplits: true` で、
`projectAccountingDataset()` が `applySplits` → `recomputeClassification` の順に走る。

| 届く先 | 反映のされ方 |
|---|---|
| 家計の科目別支出(P6/P7/P1) | 親の1行が消え、内訳の科目ごとに積まれる(`personal[月].expense[大項目]`) |
| 名義別(本人/配偶者/家族) | 親の名義を子行が引き継ぐ(`personalByOwner`) |
| 事業立替(`bizPersonal`) | 事業にした内訳だけが回り、家計の科目別からは外れる |
| 証憑インベントリ(P17) | 子行を親1件へ畳み、`accounts` に内訳の科目を全部並べる |
| 確定申告書の科目別金額(P16) | **合流しない。** 科目別の正本はfreee帳簿(`data.biz.categories`)。MF側は「事業立替の合計」までを持つ |
| 取込計画の下見 | 合流しない(`withSplits: false` のraw canonical Dataset) |

子行は `projectedEdit` に `cls`/`big`/`mid` を持ち、`resolveTx` が
`t.projectedEdit ?? edits[t.id]` の順で先に読む。分割の科目は手動編集と同じ枠に入るため、
仕分けの解決経路は増えない。

## 画面の表示契約

| ID | 契約 | 理由 |
|---|---|---|
| TS-U1 | 残額(あと¥X / ¥Xはみ出し)を入力中ずっと表示する | 保存を押してから合わないと知るのでは遅い |
| TS-U2 | 分割エディタの科目パネルは浮かせず、その場に開く(`position: static`) | 浮かせた要素は最も近いスクロール祖先で切られ、小窓の中をスクロールして選ぶ形になる |
| TS-U3 | 分割の表は内側にスクロール枠(`overflow`)を作らない | 枠がパネルの切り取り枠になる。横幅は元の明細表(`min-width: 1160px`)で確保済み |
| TS-U4 | 科目列は開く前から幅を確保する(480px) | 開いた瞬間に列が伸びると隣の金額欄が動いて押し間違える |
| TS-U5 | 狭幅(≤640px)では1行=1カードへ畳む既存の`stack-sm`契約を維持する | 分割だけ別のレイアウト規則を持たない |

判断の背景は `docs/ui-decisions.md`「決定の更新(2026-08-30 / feat-transaction-split-readability)」。

## 対象外

- 事業科目別の内訳をfreee帳簿へ書き戻すこと(正本の二重化になる)
- 内訳ごとの証憑添付(領収書は親に1枚)
- `identity_stable=0` の明細の分割(再取込を案内する)
