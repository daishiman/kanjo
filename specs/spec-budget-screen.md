# 予算画面 再現仕様 (14-budget.png)

この文書は `/budget`（予算）を `design/FINAL-UI/images/14-budget.png` どおりに作り直すための再現仕様である。後段の exact-13 実装計画は、この 1 本を画面・算出規則・API・migration の正本として参照する。

正本の優先順位は次のとおり。

1. `system-spec/` 配下（00-requirements-definition.md と 8 章、spec-state.json の質疑）。本書と食い違ったら system-spec に従い、本書を直す。
2. 本書。
3. 画像 14-budget.png。画像の数値はモックで、画面に出す金額は実データから core で算出する（ui-ux-web-001「数値は画像のモックではなく実データから core で算出したものを出し」）。画像の文言・数値と system-spec の決定が食い違う欄は、§UI・状態遷移 7.12「画像と決定の差分」表に置き換え先を示す。

注記の書き方: 利用者が確認していない agent の推定値には「(agent 推定・利用者未確認。根拠 qa-...)」を付ける。注記の無い値は、利用者決定か、既存コードまたは画像の観測値である。根拠の質疑 id は `system-spec/spec-state.json` にある（例: qa-budget-ui-ux-web-002）。

## 目的と成功状態

### 目的

利用者（SH1、個人事業主）が、過去の実績を根拠に来期 12 か月の予算を科目ごとに決められるようにする。自動提案がどの数値から組み上がったかを確かめ、事業の計画（人を増やす等）を自分で調整額と理由として足し、その結果が年間の純収支と防衛ラインの余裕にどう効くかをその場で見られるようにする（U1・G1・G2）。入力の途中で画面を離れても作業を失わないようにする（G4）。

保守者（SH2）に対しては、予算の数値を core の純関数 1 か所（`packages/core/src/budget-screen.ts`）から導き、ヘッダの防衛ライン・診断の予算カバー率・予算の着地見込みと同じ関数を共有させて、画面どうしで値がずれないようにする（G5）。

## 用語と主体

| 用語 | 定義 |
|---|---|
| 実績期間 | usePeriod で選んだ期間（1年 / 2年 / 3年 / 任意）。サーバでは `loadScoped(c)` の `period.applied` で、既存の `resolvePeriodQuery` の規則で解決する。 |
| 予算対象 | 予算を立てる 12 か月。開始月 `start`（YYYY-MM）から 12 か月。既定は実績期間の終了月の翌月（agent 推定・利用者未確認。根拠 qa-budget-ui-ux-web-002）。 |
| 行（科目） | 予算一覧の 1 行。収入の行は『売上高』（`biz.revenue`）と『その他収入』（実績 0 の手入力行）。支出の行は `data.biz.categories` の各科目（G2）。 |
| 種別 kind | `income`（収入）/ `expense`（支出）。 |
| 前期実績 | 実績期間の科目別合計を 12 か月あたりに換算した額。式は 合計 × 12 ÷ 月数（agent 推定・利用者未確認。根拠 qa-budget-backend-web-002）。 |
| 増減率 | 過去 12 か月の増減率。直近 12 か月の合計 ÷ その前の 12 か月の合計 − 1、±30% で頭打ち（agent 推定・利用者未確認。根拠 qa-budget-backend-web-002）。 |
| 季節性補正 | 月ごとの平均からの偏りを使う補正。24 か月以上の実績があるときだけ効く（agent 推定・利用者未確認。根拠 qa-budget-backend-web-002）。 |
| 計画による調整 | 利用者が行ごとに入力する調整額（円、整数、負も可）と理由（100 字以内）。取込データに無い事業計画（人を増やす等）を推奨値に反映する唯一の経路（qa-budget-decision-003）。 |
| 自動提案 | 前期実績 × (1 + 増減率) + 季節性補正 + 計画による調整 を千円に丸めた額（G2）。画面の表示は『自動提案』で、『AI』『AI・統計』とは書かない（qa-budget-decision-003）。 |
| 来期予算（保存済み） | 予算対象について D1 の `budget_plans` に保存された年額。保存行が無い期間では既存 budgets の月額 × 12（初期値）。 |
| 来期予算（入力） | 利用者が編集中の年額。保存済みの値に下書きを重ねた現在値。 |
| 差額 | 来期予算 − 前期実績（ui-ux-web-001）。 |
| 見通し | 予算対象の各月について、実績のある月は実績、無い月は自動提案の月割（季節性を反映）とした額と、その 12 か月の和（G2）。 |
| 過不足 | 見通し − 来期予算（G2・ui-ux-web-001）。支出の行だけを過不足カテゴリに出す。 |
| 調整によるインパクト | 来期予算 − 自動提案 の支出の行の和（年間の支出差）と、そのときの予算純収支（G2・ui-ux-web-001）。 |
| 防衛ライン | 既存 core の `defenseLine(data).line`（個人支出の直近 3 か月平均 + 事業固定費の月平均の和、月額）。ヘッダの表示と同じ関数・同じ期間の Dataset から出す。 |

| 下書き | 来期予算の入力・この値を適用・実績から提案・計画による調整の未保存の値。端末の localStorage に予算対象の期間単位で保存する（G4）。 |

## ユースケースとユーザーフロー

### UC-1 実績から来期の予算を立てる

1. 利用者はナビ『計画』の『予算』を開く。
2. 実績期間は usePeriod の値（既定は保存値、初回は 1年）。予算対象は実績期間の終了月の翌月から 12 か月（agent 推定・利用者未確認。根拠 qa-budget-ui-ux-web-002）。
3. 一覧に、収入の行（売上高・その他収入）と支出の行が、前期実績・来期予算（保存済み）・自動提案・差額・見通し・来期予算（入力）の列で並ぶ。
4. 『実績から提案』を押すと、チェックした行（未選択なら全行）の来期予算（入力）に自動提案が入る（G4・agent 推定の対象選択。根拠 qa-budget-ui-ux-web-002）。
5. 入力を変えるたびに、KPI・グラフ・今後の見通し・過不足カテゴリ・調整によるインパクトが組み直される（I4）。
6. 『予算を保存』で保存済み値と異なる dirty 行を 1 回の要求で保存する。GET の revision が一致するときだけ確定し、成功すると下書きが消えて最終保存の時刻が更新される。

### UC-2 自動提案の根拠を確かめ、計画を足す

1. 一覧の行を押すと、右の科目パネルにその行が開く（agent 推定・利用者未確認。根拠 qa-budget-ui-ux-web-002）。
2. 『提案の根拠』タブで、自動提案の値と前期差、推奨の根拠の文、計算の詳細（前期実績・増減率・計画による調整・季節性補正・推奨値）、月別の実績推移（過去 12 か月）を読む（I2）。
3. 取込データに無い計画（例: 人を 2 名増やす）は、計画による調整の額と理由に入力する。自動提案がその額だけ動き、根拠の文と『主な根拠データ』に理由が出る。
4. 『この値を適用』で、その行の来期予算（入力）に自動提案を入れる。
5. 『この行を元に戻す』で、その行を保存済みの値（適用前の値）へ戻す。

### UC-3 実績期間を変えて提案を見直す

期間タブを 2年 にすると、前期実績と自動提案が過去 2 年の実績から計算し直される（I1）。予算対象の開始月は `?start=` に残るので変わらない。保存済みの来期予算と下書きは実績期間に依存しないので、そのまま残る。

### UC-4 予算対象を切り替える

右上の『予算対象』で開始月を選ぶと、その期間の保存済みの予算（無ければ既存 budgets の月額 × 12）と、その期間の下書きが読み込まれる。未保存の入力がある状態で切り替えるときは、下書きが自動保存済みなので確認なしで切り替え、元の期間に戻ると下書きが復元される（agent 推定・利用者未確認。根拠 G4「予算対象の期間単位で自動保存」からの導出）。

### UC-5 調整のインパクトを確かめる

来期予算を自動提案より下げると、『調整によるインパクト』に年間の支出抑制額と予算純収支が即座に出る（I4）。『予算の過不足カテゴリ』で、見通しが来期予算を上回る（支出の増加が見込まれる）科目と下回る科目を確かめる。

### UC-6 診断から予算へ来る

診断の次の一手から `/budget?account={科目}` で来ると、その行を選んで科目パネルを開き、一覧をその行に絞る。絞り込みは状態表示『診断からの絞り込み』で知らせ、『すべて表示』で解除できる（ui-ux-web-001・既存の受け口の挙動を保つ。§7.10）。存在しない科目のときは全件を出す。

### UC-7 下書きを失わない

1. 入力の 800ms 後に下書きを localStorage に保存し、保存バーに『下書きを自動保存 HH:MM』を出す（agent 推定・利用者未確認。根拠 qa-budget-frontend-web-002）。
2. 別画面へ移って戻る、または再読込すると、下書きが復元され、保存バーに未保存 N 項目が出る（I4）。
3. 保存に成功すると下書きを消す。ログアウトでも消す（qa-budget-auth-web-001）。
4. 未保存の入力があるまま再読込・タブを閉じる・画面内のリンクで移動しようとすると確認する（§7.11）。

### 7.3 KPI 4 枚

KpiCard を 4 枚並べる。値は `applyBudgetInputs` の `kpi` をそのまま出し、画面で数え直さない。値は入力中の来期予算（下書きを含む現在値）から出す（agent 推定・利用者未確認。根拠 I4「即座に出る」からの導出）。

| 順 | ラベル | 値の文言 | 式（BR） |
|---|---|---|---|
| 1 | 年間収入予算 | ¥{n}（例: ¥13,200,000） | 収入の行の来期予算の和（BR-09） |
| 2 | 年間支出予算 | ¥{n} | 支出の行の来期予算の和（BR-09） |
| 3 | 予算純収支 | +¥{n} / −¥{n} / ±¥0 | 年間収入予算 − 年間支出予算（BR-09） |
| 4 | 防衛ライン余裕 | +¥{n} / −¥{n} / ±¥0 と ? | 年間収入予算 − 防衛ライン × 12（BR-10） |

- 防衛ライン余裕の ? は `Term`（既存の用語説明の部品）で出し、説明文は『年間収入予算 − 防衛ライン（月額 ¥{line}）× 12。ヘッダの防衛ラインと同じ値から計算しています。』とする（dec-budget-defense-margin の注意「? の説明に式を示す」。文言は agent 推定・利用者未確認。根拠 qa-budget-decision-004）。
- 予算純収支と防衛ライン余裕が負のときは、符号の文字に加えて補足『不足』を併記し、トークンの警告色を使う。正のときは補足を出さない（agent 推定・利用者未確認。根拠 ui-ux-web-001「色だけで区別せず符号と文言を併記」）。

### 7.4 月次の実績・予算・見通しのグラフ

- 見出し: 月次の実績・予算・見通し。単位の表示: （万円）。
- 横軸: 予算対象の 12 か月（ラベルは `{月}月`、例: 9月 … 8月）（agent 推定・利用者未確認。根拠 qa-budget-ui-ux-web-002）。
- 系列と凡例（5 種、完全一致）: 収入 実績 / 収入 予算 / 支出 実績 / 支出 予算 / 見通し (収支)。
  - 収入 実績・支出 実績: 予算対象の月のうち実績のある月だけ棒を描く。値は全実績（`all`）の当該月の売上高の和と、支出の行の和。
  - 収入 予算・支出 予算: 各月の月次予算（BR-11）の収入の行の和と支出の行の和。
  - 見通し (収支): 各月の見通し（BR-07）の収入の行の和 − 支出の行の和を折れ線で描く。
- 境目: 予算対象の中で、実績のある最後の月と次の月の間に縦の破線を引き、左に『実績({開始年}年{開始月}月 - {終了年}年{終了月}月)』、右に『見通し({開始年}年{開始月}月 - {終了年}年{終了月}月)』の注記を出す。予算対象に実績の月が無いときは縦線を引かず、『見通し(…)』の注記だけを出す。予算対象の全月に実績があるときは『実績(…)』の注記だけを出す（agent 推定・利用者未確認。根拠 qa-budget-ui-ux-web-002「境目の縦線はその境に引く」）。
- 縦軸: 0 を含む範囲を自動で決め、目盛りは万円で 5 本前後（既存グラフの目盛り関数 `yenTick` の考え方に揃える）。負の値（見通しの収支が赤字の月）も描ける。
- 描画: 既存の `components/FinancialCharts.tsx` と同じ SVG の自前描画にする（qa-budget-frontend-web-002・C5）。Chart.js の部品は使わない（初期 JS と lazy chunk を増やさないため）。
- 色は `chartSeriesColor` 等のトークン由来の色だけを使う。棒は色に加えて塗りの濃淡（実績は塗り、予算は枠線と薄い塗り）で区別する。

### 7.10 診断からの受け口（?account=）

- `?account={科目}` の科目が一覧の行にあれば、その行を選び、科目パネルを開き、一覧をその行に絞る（ui-ux-web-001「その行を選んで科目パネルを開く」と、現行の受け口の絞り込みの挙動を保つ）。

- 科目が一覧の行に無いときは全行を出し、状態表示とパネルは出さない。URL の `?account=` はそのまま残さず外す（agent 推定・利用者未確認。根拠 qa-budget-frontend-web-002「URL は ?start=YYYY-MM と ?account= を持ち」からの導出）。
- 既存の受け口テスト `packages/web/src/diagnosis-next-action-receivers.dom.test.tsx`（196〜209 行）の扱い。
  - 判定（状態表示の名前『診断からの絞り込み』と本文に科目名、一覧に指定科目があり他科目が無いこと、不存在の科目では全件）は変えず、弱めない。

### 7.11 下書きと離脱確認

- 保存先: localStorage のキー `kanjo:budget:draft:{userId}:{start}`（agent 推定・利用者未確認。根拠 qa-budget-frontend-web-002）。`userId` は既存の `['auth']` 問い合わせ（`/auth/me`）の `user.id`（`pages/statements/StatementsBs.tsx` と同じ取り方）。`userId` が未取得の間は下書きを読まず書かない。
- 値: `{ v: 1, savedAt: "{RFC3339}", rows: { "{科目}": { annualAmount: "{入力文字列}", planAdjustment: "{入力文字列}", planReason: "{文字列}" } } }`。保存済みの値と同じ行は入れない。
- 保存の時機: 入力・この値を適用・実績から提案・計画による調整の変更から 800ms 後（agent 推定・利用者未確認。根拠 qa-budget-frontend-web-002）。
- 読込時: `v` が 1 でない、形が壊れている、30 日を過ぎた下書きは捨てる（30 日は agent 推定・利用者未確認。根拠 qa-budget-frontend-web-002）。

### API: 予算画面の取得（GET /api/budget-screen、新設）

#### 識別と目的

### API: 予算の保存（PUT /api/budget-plans、新設）

#### 識別と目的

- `PUT /api/budget-plans`。保存済み値と異なる dirty 行だけを base revision つきで保存する。未編集行を古い画面の値で上書きしない。
- 同じ期間は上書きで、版は持たない（database-web-001）。

#### 認証・認可

- セッション必須。未認証は 401。パスワード変更が必要な利用者は 403。
- 書込みは自分の dirty 行だけを差分更新する（qa-budget-auth-web-002）。利用者 id は本文から受け取らない。
- `canonicalMutationFence` の内側（consumers: `budget_plans`）。取込の洗替え・JSON の復元と直列化する（qa-budget-security-web-001）。

#### Request

`application/json`。

```json
{
  "start": "2026-09",
  "baseSavedAt": "2026-08-20T01:00:00.000Z",
  "rows": [
    { "account": "売上高", "kind": "income", "annualAmount": 132000000, "planAdjustment": 0, "planReason": null },
    { "account": "人件費", "kind": "expense", "annualAmount": 39600000, "planAdjustment": 500000, "planReason": "4月から2名採用の予定" }
  ]
}
```

| フィールド | 型 | 制約（BR-17） |
|---|---|---|
| start | string | `YYYY-MM`、2000-01〜2100-12 |
| baseSavedAt | RFC3339 または null | GET が返した `savedAt`。保存行が無い期間は null。省略不可 |
| rows | 配列 | 1〜200 行。科目の重複不可 |
| rows[].account | string | 1〜60 字 |
| rows[].kind | `income` / `expense` | 『売上高』『その他収入』は income、それ以外は expense |
| rows[].annualAmount | integer または null | −10,000,000,000〜+10,000,000,000。null はその科目の保存済み行を削除 |
| rows[].planAdjustment | integer | −10,000,000,000〜+10,000,000,000。省略時 0 |
| rows[].planReason | string または null | 前後の空白を除いて 100 字以内。空文字は null として保存 |

本文は `{start, baseSavedAt, rows:[{account, kind, annualAmount, planAdjustment, planReason}]}`。web は保存済み値と異なる dirty 行だけを送り、来期予算を空へ戻した dirty 行は `annualAmount:null` として送る。未編集行は送らず、サーバ側の最新値を保持する。

#### Response

200 `application/json`。

| フィールド | 型 | 説明 |
|---|---|---|
| ok | true | |
| start | `YYYY-MM` | 保存した開始月 |
| count | integer | 受け付けた dirty 行数 |
| savedAt | RFC3339 または null | 更新後の期間 revision。最後の保存行を削除した場合は null |
| revision | RFC3339 または null | `savedAt` と同値。競合制御の明示名 |

#### Validation・ビジネスルール

- 本文は `publicJsonValidator` と zod で検証し、BR-17 を外れたら 400 `invalid_request`（zod の内部詳細は出さない）。
- 種別の食い違い（『売上高』を expense で送る等）と科目の重複も 400。
- 一覧に無い科目名（取込から消えた科目など）も expense として受ける。web は画面の行だけを送るので、消えた科目の行は保存で消える（BR-01）。
- 既存 `budgets` 表には書かない（C3）。

#### Error contract

| HTTP | code | 条件 | クライアントの扱い |
|---|---|---|---|
| 400 | `invalid_request` | 本文の検証に失敗 | 『予算を保存できませんでした。入力内容を確認してください。』。下書きは残す。 |
| 401 | `unauthorized` | 未認証 | 既存のログイン画面へ。下書きは端末に残る。 |
| 403 | `password_change_required` | mustChangePasswordFence | 既存の変更画面へ |
| 409 | `canonical_write_busy` | fence の lease を取れない（取込・復元の進行中） | 『別の取込みまたは更新が進行中です。完了後に再試行してください』（fence の既存文言）と『再試行』。下書きは残す。 |
| 409 | `budget_plan_conflict` | `baseSavedAt` と現行 revision が一致しない | 最新を再取得し、未編集行だけを最新値へ追随させる。dirty 行は下書きとして残し、利用者に再確認を促す。 |
| 503 | `schema_unavailable` | migration 0050 未適用 | 失敗の通知。下書きは残す。 |
| 500 | `internal` | その他（batch の失敗を含む） | 失敗の通知と『再試行』。batch は全体で失敗するので、一部だけ書かれることはない。 |

#### 実行セマンティクス

- `canonicalMutationFence` が同一利用者の変更を直列化している内側で、現行 revision と `baseSavedAt` を照合する。不一致なら書かずに 409 を返す。
- D1 の batch 1 回で、次を順に行う。
  1. dirty 科目だけを JSON 配列でまとめて DELETE
  2. `annualAmount` が null でない dirty 科目だけを `json_each` で INSERT（80 KiB を超える場合だけ分割）
  3. その期間に残る行の `updated_at` を新 revision に統一
  4. JSON snapshot を無効化
- 最大入力でも DELETE 1 文、INSERT 1〜2 文、revision 1 文、snapshot 1 文の 4〜5 文。削除だけなら 3 文で、Worker 呼出しの D1 クエリ予算を十分下回る（Q-7）。
- batch は D1 の中で 1 つのトランザクションとして扱われ、途中で失敗すれば全体が戻る。
- 成功後に同じ `baseSavedAt` の本文を再送すると 409 になり、意図せぬ上書きをしない。現在の revision を読み直した再試行だけが書ける。
- `updated_at` はサーバが発行する RFC3339 (UTC) の revision で、同じミリ秒内の連続保存でも直前より新しくする。期間内の全保存行を同じ値に揃える。

#### キャッシュ・ページング

- ページングは無い。
- 成功後、web は `['budget-screen']` を無効化し、`invalidateAnalysisDerived` を呼ぶ（診断の予算カバー率・着地見込みを取り直すため）。

#### 可観測性と監査

- 既存の要求ログに、経路・所要時間・HTTP 状態・行数を出す。金額・科目名・理由は出さない。
- 監査の記録は `budget_plans.updated_at`（最後の保存時刻）だけ。版と操作履歴は持たない（版管理は対象外）。

#### セキュリティ確認

- 利用者で区切る（DELETE・INSERT とも `user_id` をセッションから入れる）。
- 全値をパラメタで渡す。
- 行数の上限 200 で、1 回の書込みの大きさを抑える（qa-budget-security-web-001「1 回の保存の行数に上限を置く」）。
- 理由は描画時に React の既定エスケープ。CSP（`packages/web/public/_headers`）は緩めない。
- fence の内側なので、取込の洗替え・JSON の復元と同時に書かれない。

#### Contract tests

- 期間ごとに保存され、同じ期間の 2 回目の PUT で行が置き換わる（1 回目にあって 2 回目に無い科目が消える）。
- 別の期間の行は変わらない。
- 未認証 401。fence の lease を別に取った状態で 409 `canonical_write_busy`。
- 不正値で 400: 201 行、科目 61 字、理由 101 字、年額 10,000,000,001、小数、`start=2101-01`、科目の重複、『売上高』の kind=expense。
- 利用者 A の PUT が利用者 B の行を変えない。
- PUT の後に JSON snapshot が無効化されている（`import_active_targets` の `json:global` の行が消える）。
- migration 0050 が既存行を 1 行も書き換えない（`budgets` の行数と内容が適用前後で同じ）。
- `budget_plans` が JSON の書き出しに入り、復元で戻る（BR-24）。

- 新しい認証方式は作らない（qa-budget-auth-web-001）。

## エラー・例外・回復

| 事象 | 検知 | 利用者に見えるもの | 回復 |
|---|---|---|---|
| 画面の取得失敗 | GET が 5xx・ネットワークエラー | 失敗状態『予算を読み込めませんでした。』と『再読み込み』 | 再取得。実績期間は usePeriod、予算対象と科目は URL に残る。 |
| 不正な `?start=` | GET が 400 | 何も出さない | `?start=` を外して既定の予算対象で取り直す |
| 保存の検証失敗 | PUT が 400 | 『予算を保存できませんでした。入力内容を確認してください。』 | 下書きは消さない。欄の検証文言を見て直す。 |
| 保存が取込と重なった | PUT が 409 `canonical_write_busy` | fence の既存文言と『再試行』 | 取込の完了後に再試行。下書きは残る。 |
| 他画面の保存後に古い版から保存した | PUT が 409 `budget_plan_conflict` | 『この予算はほかの画面で更新されています。』 | 最新を再取得し、未編集行だけを追随。dirty 行は下書きとして残して再確認する。 |
| 保存の失敗（その他） | PUT が 5xx・ネットワークエラー | 『予算を保存できませんでした。時間をおいてもう一度お試しください。』と『再試行』 | 最新を再取得して revision と反映結果を確認してから再送する。batch 自体は全体で成功または失敗する。 |
| migration 未適用 | 503 `schema_unavailable` | 失敗状態・失敗の通知 | Migrate を適用する（運用。既存の手順） |
| 入力が整数でない・範囲外 | web の検証 | 欄の下に『整数で入力してください（±100億円以内）』。『予算を保存』を押せない。 | 欄を直す |
| 理由が 100 字を超える | web の検証（入力の上限） | 残り字数が 0 で、それ以上入らない | 理由を短くする |
| localStorage が使えない | try/catch | 下書きの時刻を出さない | 下書き無しで動き続ける。保存は通常どおり。 |
| 下書きが壊れている・形式が古い・30 日を過ぎた | 読込時の検証 | 何も出さない | その下書きを捨てる |
| 下書きの科目が一覧に無い | 読込時の照合 | 何も出さない | その科目の下書きを捨てる |
| 未保存のまま離れる | beforeunload・リンクの capture | 離脱の確認 | とどまるか、移動する（下書きは残る） |
| 他のタブで同じ期間を保存した | 保存時の revision 不一致または保存後の再取得 | 『この予算はほかの画面で更新されています。』（`role="status"`） | 最新の保存済みの値を読み込み、未編集行だけを追随させる。dirty 行は残し、新しい保存済み値に対して差分を数え直す。 |
| 実績 0 か月 | `empty: true` | 空状態と『データ取込』への導線 | 取込を行う |
| 実績が 24 か月未満 | `seasonalEnabled: false`・g = 0 | 推奨の根拠に『実績が24か月に満たないため…』 | 取込で実績が増えれば自動で効く |

- 他のタブの更新の文言は agent 推定・利用者未確認（根拠 既存 spec-classify-screen の同じ事象の型）。
- 回復の原則: 利用者の入力は、保存に成功するまで端末から消さない。800ms の debounce 前でも期間切替・unmount・pagehide で同期的に dirty patch を退避する。保存は dirty patch 全体が成功するか全体が失敗する。

## イベント・非同期処理

N/A: サーバ側に非同期処理は無い。キュー・Cron・Durable Objects・外部 Webhook は足さない（qa-budget-infrastructure-web-001: 構成は変えない）。保存は要求の中で同期的に D1 へ書く。毎晩のバックアップ（既存の nightly backup）は JSON の書き出しを通じて `budget_plans` を含むようになるが、バックアップの仕組みそのものは変えない。

|---|---|---|
