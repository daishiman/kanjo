## 目的と成功状態

目的: 利用者 (個人事業主とその家族の家計を 1 人で管理する本人) が、freee (事業) と マネーフォワード (家計) から書き出した複数の明細ファイルをまとめて選び、確定する前にファイルごとの取込元・対象期間・大きさ・重複・検証の結果と取り込み予定の要約を確かめ、取り込めるファイルだけを確定し、結果からそのまま次の画面へ進み、過去の取込を 1 回ごとに振り返って原本の取得・再取込・取り消しを決着できるようにする (U1)。誤った取込や二重取込で台帳を壊さないこと、取り込んだデータを外部へ送らないことを守る。

成功状態 (U5 の S1-S6 をこの画面の単位で読んだもの):

- `/import` が 16-import.png の構成要素 (問いの見出し・期間タブ・対象期間カード・3 段のステッパー・1〜5 の各節・履歴の詳細ペイン・下部の選択件数バー) をすべて描画し、色・余白・部品はトークンと共通 Button / PageShell 経由で、直書き色が 0 件である。期間は `usePeriod` から来る (S1、G1)。
- 検査の段階で明細・残高・有効取込の表への書き込みが 0 件で、確定は検査 ID だけで行われ、同じファイルの 2 回目のアップロードが 0 件である。期限を過ぎた仮置きは夜間保守の後に R2 と D1 に残らない (S2、G2、qa-imp-decision-003)。
- ファイルの状態・取込可否・要約・取込 1 回の結果・上限の判定は `packages/core/src/import-screen.ts` の関数だけが決め、api と web に同じ判定の重複実装が 0 件である (S3、G3)。
- 『前回データを残す』オンで同じファイルを 2 回確定しても明細数が増えず、2 回目の新規追加が 0 件・重複スキップが全行になる。オフでは従来の月単位の入れ替えと同じ結果になる (S4、G4、qa-imp-decision-002)。
- 取込履歴の 1 行が 1 回の取込に対応し、詳細の影響の数値が確定時の記録と一致する。一括削除の前後で明細数が変わらない。既存の取り消し・破棄・置換・削除と 30 日の取り消し期限が作り直し後も同じ結果になる (S5、G5、qa-imp-decision-004)。
- 新しい検査・確定・置換経路で上限・オリジン・レート制限の拒否がテストで固定され、取込経路から外部ホストへの送信が 0 件である。migration は追加のみで、既存の取込履歴 (ファイル単位の記録) が作り直し後も履歴と詳細で読める (S6、G6)。互換 `POST /imports` の制限は「既存経路の扱い」に記録する。

## 用語と主体

| 用語 | 意味 |
| --- | --- |
| 検査 | 選んだファイルを一度だけ受け取り、R2 に 24 時間仮置きして、ファイルごとの検査結果を返す段階。明細の表には書かない (qa-imp-decision-003)。 |
| 検査 ID | 検査 1 要求に 1 つ発行する ID。取込 1 回 = 1 つの検査 ID = 取込履歴の 1 行 (qa-imp-decision-005)。`crypto.randomUUID` で作る (qa-imp-auth-web-004 = agent 推定)。 |
| ファイル項目 | 検査 ID の中のファイル 1 つ分の記録。ファイル項目 ID と検査結果を持つ (qa-imp-decision-005)。 |
| 確定 | 検査 ID と、取り込むファイル項目 ID と詳細設定を送って明細を書く段階。ファイルは再送しない。 |
| 取込 1 回 | 1 つの検査 ID を確定した結果。`import_runs` の 1 行で表す (I5)。 |
| 前回データを残す | オンのとき、同一期間の既存明細を残し、まだ無い行だけを足す。同一の行は重複スキップに数える。既定オン (qa-imp-decision-002)。 |
| 強制再取込 | 取込済みと同一内容のファイルも再適用する (qa-imp-decision-002)。 |
| 重複の可能性 | 既存の `duplicateMatchScore` (`packages/core/src/total-cashflow.ts`) による二重計上候補の件数 (qa-imp-backend-web-005 = agent 推定)。 |
| サブスク候補 | 取込後に `subsCandidates` (`packages/core/src/subs.ts`) が新たに出す候補の件数 (qa-imp-backend-web-005 = agent 推定)。 |
| 影響の 3 数値 | 取込 1 回の 新規追加・重複スキップ・サブスク候補。確定時の値を記録する (qa-imp-decision-004)。 |
| 一括削除 | 履歴の記録を画面から片づけるだけの操作。明細は消さない (qa-imp-decision-004)。 |

主体:

- 利用者 (SH1): セッション cookie で認証された本人。画面の全操作を行う。
- 保守者 (SH2): 同一人物とコーディングエージェント。規則を core・docs・テストで読む。

## ユースケースとユーザーフロー

1. 選ぶ: 1.ファイルを選択 にファイルをドラッグ&ドロップするか「ファイルを選択」で複数を選ぶ → 送る前に core の上限判定で 1 ファイル 25MB・10 ファイル・合計 30MB を確かめ、超えるファイルは送らずに取込不可と理由を出す → 残りを 1 つの multipart 要求で送る。ステッパーは 1 (ファイル選択) が現在の段。
2. 待つ: 2.取込ファイル一覧 に各ファイルが「アップロード中 n%」→「検査中」と出る。応答で検査 ID とファイルごとの取込元・対象期間・サイズ・重複・バリデーション・明細数が返り、ステータスが「取込準備完了」か「取込不可」になる。ステッパーは 2 (内容確認) へ進む。
3. 確かめる: 3.取込内容の確認 で対象ファイル数と取込可能数・取り込み予定の明細数・対象期間・影響する取込元・重複の可能性・サブスク候補を読み、エラーのファイルが除外される注記を読む。
4. 直す: 取込不可の行の「再試行」、または後からのファイル追加は、同じ検査 ID へ足す (送る前に既存の項目と合わせた累計を判定する)。不要な行は「削除」で検査から外す。アップロード中の行は「キャンセル」で止める (qa-imp-decision-008)。
5. 詳細設定を決める: 「強制再取込」(既定オフ) と「前回データを残す」(既定オン) を必要なら切り替える。
6. 取り込む: 下部バーの「N ファイルを取り込む」→ 検査 ID と選んだ取込可能なファイル項目 ID と詳細設定で確定する。エラーのファイルは確定から自動で外れる。ステッパーは 3 (取込結果)。
7. 結果から進む: 4.取込結果 の 4 枚のカードを読み、「総収支で確認する」で重複の可能性へ、「サブスクで確認する」でサブスク候補へ移る。エラーのファイルがあれば「エラーのファイルのみ再試行」(I7)。
8. 振り返る: 5.取込履歴 の行の「詳細」で履歴の詳細ペインを開く (選択中の履歴は URL に残る)。影響の 3 数値を読み、「この取込のファイルをダウンロード」で原本を取り出し、必要なら再取込・取り消し (30 日以内) を行う。取り消し済み・失敗の履歴は選んで「選択した履歴を一括削除」で記録を片づける。

## 機能要件

- FR-1 期間: 期間タブは `usePeriod` (`packages/web/src/period.tsx`) の値をそのまま使う。対象期間 (グローバル) のカードは同じ値を「2025年9月 - 2026年8月（1年）」の形で出す。取込そのものは期間で絞らない (ファイルの対象期間はファイルの中身から決まる。**agent 推定・利用者未確認**)。
- FR-2 受け付ける形式: `.csv`・`.xlsx`・`.xls`・`.txt` に加え、既存の `.zip`・`.json` を受け付ける (qa-imp-decision-001)。`.txt` はタブ区切りまたはカンマ区切りの CSV として扱う (qa-imp-frontend-web-005 = agent 推定)。取込元の判定は既存のヘッダー判定 (`import-pipeline.ts` の `classifyRows`)、文字コードは既存の `decodeBuf` (`packages/core/src/csv.ts`) を使う。
- FR-3 送信前の上限判定: web は `packages/core/src/import-screen.ts` の `IMPORT_LIMITS` と超過理由の判定関数を import して判定し、web に上限の数値リテラルを書かない (qa-imp-frontend-web-005 = agent 推定)。
- FR-4 検査: 選んだファイルを 1 つの multipart 要求にまとめて送り、1 つの検査 ID とファイルごとの項目を受け取る (qa-imp-decision-005)。
- FR-5 アップロード進捗: XMLHttpRequest の `upload.onprogress` の累計バイトを multipart に積んだ順のファイルへ割り当てて、ファイルごとの % を出す (fetch はアップロード進捗を取れないため)。アップロード中のキャンセルは要求全体を abort し、そのファイルを外した残りを送り直す (qa-imp-frontend-web-005 = agent 推定)。
- FR-6 追加と再試行: 取込不可のファイルの再試行と後からの追加は `POST /imports/inspections/:id/files` で同じ検査 ID へ足す。上限は検査 ID ごとの累計 (10 ファイル・合計 30MB) で数え、この要求は検査のレート制限に数える (qa-imp-decision-008)。
- FR-7 除外: 確定前の項目は `DELETE /imports/inspections/:id/files/:fileId` で検査から外す (qa-imp-backend-web-005 = agent 推定)。
- FR-8 確定: 検査 ID・取り込むファイル項目 ID・前回データを残す・強制再取込を送る。取込可能が 0 件のとき取り込むボタンは押せない (qa-imp-frontend-web-005 = agent 推定)。
- FR-9 前回データを残す: オンでは MF 明細は `mfStableKey`、freee 取引は `freeeDealKeys` (どちらも `packages/core/src/identity.ts`) で既にある行を飛ばし、新しい行だけを足す。オフでは従来の月単位の入れ替え (qa-imp-decision-002)。行単位の追加の対象は MF 明細と freee 取引だけで、MF 資産推移と JSON 復元は従来の動作のまま (qa-imp-backend-web-005 = agent 推定)。
- FR-10 強制再取込: 取込済みと同一内容 (`content_hash` が一致) のファイルは取込可能から外し、強制再取込のときだけ含める (qa-imp-backend-web-005 = agent 推定)。
- FR-11 取込結果: 確定の応答から 4 枚のカード (取込成功・取込失敗・重複の可能性・サブスク候補) と結果の見出しを出す。重複の可能性は総収支画面の要確認へ、サブスク候補はサブスク画面へのリンクを持つ (I7)。
- FR-12 取込履歴: `GET /imports/runs` で取込 1 回を 1 行で出す (qa-imp-decision-004)。列は 取込日時 / 取込元 / ファイル数 / 取込明細数 / 結果 / 詳細 / 操作 の 7 列 (O1)。
- FR-13 履歴の詳細: `GET /imports/runs/:id` で取込日時・取込元・対象期間・ファイル数・取込明細数・結果とこの取込による影響 (新規追加・重複スキップ・サブスク候補) を出す (G5)。選択中の履歴は URL の検索パラメータに持つ (I1)。
- FR-14 原本・再取込・取り消し: 既存の原本取得 (`GET /imports/:id/original`)・取り消し (`/imports/:id/undo`、30 日)・破棄の経路を取込 1 回の単位へ束ねる (qa-imp-backend-web-005 = agent 推定)。
- FR-15 一括削除: 取り消し済み・失敗の履歴を選んで記録だけを片づける。1 要求 100 件まで。明細は消さない (qa-imp-decision-004 / -010)。
- FR-16 対応サービスの案内: マネーフォワード (家計簿（キャッシュフロー）) と freee (取引（取引先・取引明細）) の 2 件を出し、銀行を外す (qa-imp-decision-001)。
- FR-17 サイドバーのバッジ: 取込のバッジは既存どおり `/review-queue` の `counts.import` を読む。確定・取り消し・削除の後は履歴と review-queue のキーを無効化する (qa-imp-frontend-web-005 = agent 推定)。

## 非機能要件

- 性能: 画面は既存どおり遅延読み込みする。初期 JS 予算 (CI 実測) を超えない (S6)。
- メモリ: Worker 1 isolate のメモリ 128MB の中に収める。検査の 1 要求は multipart 本文 (最大 30MB) を読んだ後、1 ファイルずつ順にパースと展開 (最大 60MB) をして R2 へ置き、前のファイルの展開結果を手放してから次へ進む。同時に展開するのは 1 ファイルだけ (ピーク約 90MB) (qa-imp-decision-007)。90MB は見積もりで実測ではない (「未決事項」)。
- D1: 検査と確定の D1 クエリは既存のクエリ予算に収める。確定は先に全ファイルのクエリ予算を合算し、上限を超えるなら 1 件も書かずに 409 を返す (C4、qa-imp-backend-web-005 = agent 推定)。
- アクセシビリティ: 状態を色だけで伝えない。ステータス・重複チェック・バリデーション・結果の 4 枚カードに文字と件数とアイコンを添え、進捗は数値の % で出す (WCAG 2.2 SC 1.4.1、ui-ux 章の doctrine)。
- 見た目: 直書き色 0。色は `design-tokens.ts` 由来のトークン、ボタンは共通 Button、ページは PageShell。表・詳細ペイン・選択件数バーは既存画面 (AI分析・サブスク) の部品と流儀に揃える (C2)。
- 狭い画面: 段を縦に積み、表は横スクロールにする (qa-imp-ui-ux-web-004 = agent 推定)。
- 保守性: 規則を `docs/import-screen/` に表で残し、同じ表を core の単体テストの期待値にする (qa-imp-maintenance-ops-web-005 = agent 推定)。
- データの持ち出し: 取り込んだデータと原本は D1 と R2 の中だけに置き、外部へ送らない (C6)。

- 段見出し「取込内容の確認」、副題「{N}ファイルのチェック結果サマリーです。内容を確認し、問題なければ取り込みを実行してください。」

## ビジネスルールと検証

以下の規則はすべて `packages/core/src/import-screen.ts` の純関数に置き、api はその結果を契約に載せて返し、web は描くだけにする (G3、qa-imp-backend-web-005 = agent 推定)。関数名は実装計画で決める。

### 上限値 `IMPORT_LIMITS`

| 項目 | 値 | 出典 |
| --- | --- | --- |
| 1 ファイルの大きさ | 25MB | qa-imp-decision-006 |
| 1 回の取込のファイル数 (検査 ID ごとの累計) | 10 | qa-imp-decision-006 / -008 |
| 1 回の取込の合計サイズ (検査 ID ごとの累計) | 30MB | qa-imp-decision-007 / -008 |
| xlsx / ZIP の展開後 1 ファイル | 60MB | qa-imp-decision-007 |
| xlsx / ZIP の中央ディレクトリのエントリ数 | 1,000 件 | qa-imp-decision-009 |
| 一括削除 1 要求 | 100 件 | qa-imp-decision-010 |
| 夜間保守の片づけ 1 回 | 500 件 | qa-imp-decision-010 |
| ファイル名 | 制御文字を除き 255 文字 | qa-imp-decision-010 |
| レート制限 | 検査 30 回/分・確定 5 回/分 (利用者ごと) | qa-imp-decision-006 |
| 仮置きの期限 | 24 時間 | G2 |
| 取り消しの期限 | 30 日 (既存) | G5 |

- 上限値 (1 ファイル 25MB・10 ファイル・合計 30MB・展開後 1 ファイル 60MB・エントリ数 1,000 件) は `IMPORT_LIMITS` の 1 か所だけに置く。ファイルの大きさと数 (追加では既存の項目を含む) から超過の理由を返す判定関数も core に置く。web の送信前の判定と api の 413 の判定 (hono/body-limit の `maxSize` を含む) はどちらもこの定数と関数を import し、数値を書き写さない (qa-imp-backend-web-005 = agent 推定)。
- MB は 1,048,576 bytes とする (**agent 推定・利用者未確認**)。
- 超過の理由は「25MB 超」「10 ファイル超」「合計 30MB 超」(qa-imp-ui-ux-web-004 = agent 推定) と、展開時の「展開後 60MB 超」「エントリ数 1,000 件超」(**agent 推定・利用者未確認**)。
- 一括削除・夜間保守・ファイル名・レート制限・期限を同じ定数へ含めるかは実装計画で決める。数値の出典は上の表のとおりで変わらない。

### ファイルの状態

入力は、送信前の上限判定の結果、アップロードの進捗、検査結果の有無と内容、確定の結果。上から順に最初に当たったものを返す (状態の 6 種は O3。優先順位は **agent 推定・利用者未確認**)。

| 順 | 条件 | 状態 |
| --- | --- | --- |
| 1 | 確定で書込に失敗した | 失敗 |
| 2 | 確定で書き込んだ | 取込済み |
| 3 | 送信前の上限判定で超過、または検査結果がエラー (パース不可・展開の上限超過・取込元を判定できない) | 取込不可 |
| 4 | 検査結果があり取込可能 | 取込準備完了 |
| 5 | 送信が済み、検査結果を待っている | 検査中 |
| 6 | それ以外 (送信中) | アップロード中 (n%) |

- O3 は「チェック中」、ui-ux 章は「検査中」と書く。ステータス列の文字は「検査中」、バリデーション列の検査中の文字は画像どおり「チェック中」とする (**agent 推定・利用者未確認**)。
- 取込済みと同一内容のファイルは、強制再取込がオフなら取込可能から外し、状態は取込準備完了のまま操作だけを変えるのではなく「取込不可」(理由「取込済みと同一」) とする (**agent 推定・利用者未確認**)。強制再取込をオンにすると取込準備完了へ戻る。

### 検証の段階

- 重複: 取込済みと同一 (`content_hash` が有効な取込と一致) → 重複の可能性 n 件 (`duplicateMatchScore` の二重計上候補) → 重複なし の順 (G2、qa-imp-backend-web-005 = agent 推定)。
- バリデーション: エラー (取り込めない行があり、そのファイルを取り込めない) → 警告あり (取り込めるが確かめるべき行がある) → 問題なし の順 (G2)。エラーと警告に数える具体の条件は、既存のパーサ (`packages/core/src/parsers/`) の「保存不可」「集計対象外」などの分類から実装計画で決める。

### 取込可否

取込準備完了、かつ選択中のファイルだけを確定に含める。取込不可・失敗・取込済みは選べない。エラーのファイルは確定から自動で外す (G2)。

### 内容確認の要約

(qa-imp-backend-web-005 = agent 推定)

| 項目 | 数え方 |
| --- | --- |
| 対象ファイル | 検査 ID に属する項目の数。取込可能は取込準備完了の数。 |
| 取り込み予定の明細 | 取込可能なファイルの明細数の合計。前回データを残すオンでも、検査の段階では重複スキップを引かない (**agent 推定・利用者未確認**)。 |
| 対象期間 | 取込可能なファイルの対象期間の最小の開始日から最大の終了日。 |
| 影響する取込元 | 取込可能なファイルを取込元ごとに数えた行。 |
| 重複の可能性 | 取込可能なファイルの重複の可能性の件数の合計。 |
| サブスク候補 | 取込可能なファイルの明細から `subsCandidates` が新たに出す見込みの件数 (**agent 推定・利用者未確認**)。 |

### 取込 1 回の結果

確定したファイルについて、全ファイル成功 = 成功、1 件以上成功かつ 1 件以上失敗 = 一部成功、全失敗 = 失敗 (qa-imp-backend-web-005 = agent 推定)。確定から自動で外したエラーのファイルは「失敗」に数える (画像の「3件成功、1件失敗」はエラーのファイルを 1 件失敗と数えている。**agent 推定・利用者未確認**)。

### 前回データを残す (qa-imp-decision-002)

| 設定 | MF 明細 | freee 取引 | MF 資産推移・JSON 復元 |
| --- | --- | --- | --- |
| オン (既定) | 同一期間の既存行を残し、`mfStableKey` が既にある行を飛ばす。飛ばした行を重複スキップに数える | 同じく `freeeDealKeys` で飛ばす | 従来の動作のまま |
| オフ | 従来どおり月単位で入れ替える | 従来どおり月単位で入れ替える | 従来の動作のまま |

- 画像の意味 (G4) に改めるので、現行の「件数が減る月だけ前回の内容を残す」(`keepOnShrink`) は画面から外す。API の `keepOnShrink` を残すか外すかは実装計画で決める。
- 既定オンは web の既定値と確定 API の省略時の値の両方に置く (**agent 推定・利用者未確認**)。

### 影響の 3 数値

確定時に数えて `import_runs` に記録し、後から明細を数え直さない (取り消しや再取込で値が変わるため。database 章の設計知識の適用)。新規追加 = 書いた行数、重複スキップ = 前回データを残すで飛ばした行数、サブスク候補 = 取込後の `subsCandidates` の新規件数。

## API契約

共通:

- 利用者経路はすべて `/api/*` の authGuard・mustChangePasswordFence・runtimeSchemaGuard・canonicalMutationFence の内側に載る (C5)。
- 他人の・期限切れの検査 ID、別の検査のファイル項目 ID、他人の取込 ID にはすべて 404 `not_found` を返し、存在の有無を区別させない (qa-imp-decision-010)。
- `/api/imports*` の変更要求 (POST / DELETE) は Origin ヘッダーが自サイトと一致しなければ 403 `forbidden_origin` (qa-imp-security-web-004 = agent 推定)。
- エラーの形は既存どおり `{ "error": { "code": string, "message": string } }`。
- 入力は zod で検証する (C5)。
- レスポンスのキー名は本仕様で置く案で、**agent 推定・利用者未確認** である。

### POST /imports/inspections

#### 識別と目的

選んだ 1〜10 ファイルを 1 要求で受け、R2 に 24 時間仮置きして、1 つの検査 ID とファイルごとの項目を返す。明細・残高・有効取込の表には書かない (qa-imp-decision-003 / -005)。

#### 認証・認可

セッション cookie。検査 ID は利用者 ID に結び付けて作る。

#### Request

`multipart/form-data`。ファイルのパートを 1〜10 個。フィールド名は既存の `POST /imports` に合わせる (**agent 推定・利用者未確認**)。

#### Response

201 `{ "inspection": { "id", "expiresAt", "files": [ { "id", "filename", "source", "periodFrom", "periodTo", "size", "rowCount", "duplicate": { "kind", "count" }, "validation": { "kind", "count" }, "state", "reason" } ], "summary": 内容確認の要約 } }`。`state` と `summary` は core の関数の結果 (**agent 推定・利用者未確認**)。

#### Validation・ビジネスルール

判定の順 (qa-imp-decision-011、qa-imp-security-web-004 = agent 推定):

1. Origin の検査。不一致は 403。
2. レート制限 (検査の種別)。超過は 429。
3. hono/body-limit で合計 30MB。Content-Length があればその値で、無ければ本文をストリームで数えて上限で止める。本文を読む前 (または読みながら) に 413。
4. 本文を読んだ直後・パースの前に、ファイル数 (10) と 1 ファイルの大きさ (25MB) を core の判定関数で確かめ、超過は 413。
5. 1 ファイルずつ順に、xlsx と ZIP は展開する前に中央ディレクトリのエントリ数と展開後サイズの合計を確かめ、1,000 件か 60MB を超えるものは展開せずにそのファイルを取込不可にする (要求全体は拒否しない)。
6. パース・取込元の判定・重複と検証の算出・R2 への仮置きを 1 ファイルずつ行い、前のファイルの展開結果を手放してから次へ進む。

ファイル名は制御文字を除き 255 文字で切って記録する (qa-imp-decision-010)。

#### Error contract

| HTTP | Code | Condition | Retryable | Client action |
| --- | --- | --- | --- | --- |
| 400 | invalid_request | ファイルのパートが 0 個、または形式が不正 | no | ファイルを選び直す |
| 403 | forbidden_origin | Origin が自サイトと一致しない | no | 画面から操作し直す |
| 413 | payload_too_large | 合計 30MB 超・10 ファイル超・1 ファイル 25MB 超 | no | 上限の文言を出し、ファイルを減らす |
| 429 | rate_limited | 検査 30 回/分の超過 (`Retry-After` を付ける) | yes | 待ち時間を文言で出す |

`invalid_request` の code は **agent 推定・利用者未確認** である。

#### 実行セマンティクス

`import_inspections` の 1 行と `import_inspection_files` の N 行を作り、原本を R2 の `import-staging/{user_id}/{inspection_id}/{file_id}` に置く (qa-imp-infrastructure-web-002 = agent 推定)。明細・残高・有効取込の表には 1 行も書かない (S2)。同じ内容を 2 回送れば別の検査 ID になる。

#### キャッシュ・ページング

N/A: 単一の作成要求で一覧を返さない。

#### 可観測性と監査

失敗は既存の API エラーログの流儀で code を残す。ファイルの中身・明細の文字列はログに出さない (**agent 推定・利用者未確認**)。

#### セキュリティ確認

本人だけが確定・取得でき、24 時間で消える。外部ホストへ送らない。ファイル由来の文字列は応答に載せても web で HTML として解釈しない。

#### Contract tests

1 ファイル・10 ファイルが 201、11 ファイルと 25MB+1 byte の 1 ファイルがパースより前に 413、合計 30MB+1 byte が Content-Length ありと無しの両方で 413、エントリ数 1,001 件と展開後 60MB+1 byte のファイルが取込不可になり他のファイルは検査される、検査のあと明細の表の行数が変わらない、31 回目が 429、Origin 不一致が 403。

### POST /imports/runs

#### 識別と目的

検査 ID と取り込むファイル項目 ID と詳細設定を受けて確定する。ファイルを再送させない (qa-imp-decision-003 / -005)。

#### 認証・認可

セッション cookie。本人の未期限の検査 ID と、それに属するファイル項目 ID だけ。

#### Request

JSON `{ "inspectionId": string, "fileIds": string[], "keepPrevious": boolean, "force": boolean }`。`keepPrevious` の省略時はオン (**agent 推定・利用者未確認**)。本文は小さい上限で止める (qa-imp-security-web-004 = agent 推定。値は実装計画で決める)。

#### Response

201 `{ "run": { "id", "result", "files": [ { "id", "filename", "state", "rowCount", "reason" } ], "impact": { "added", "skipped", "subsCandidates" }, "duplicateCandidates" }, "remaining": string[] }`。1 要求で先頭の 1 ファイルを確定し、残りの項目 ID を `remaining` で返す。

#### Validation・ビジネスルール

- `fileIds` のうち取込可能でないもの (取込不可・取込済みと同一で強制再取込がオフ) は外す。取込可能が 0 件なら書かずに 400 (**agent 推定・利用者未確認**)。
- 既存の書込の直列化 (`import_writer_claims`) の内側で 1 要求 1 ファイルを書き、画面は `remaining` が空になるまで同じ検査 ID で確定を続ける。2 本目以降の run は最初の run の子にし、履歴を 1 行に保つ。
- 前回データを残すと強制再取込は「ビジネスルールと検証」のとおり。
- R2 の仮置きを既存の取込の鍵へコピーしてから仮置きを消す (qa-imp-infrastructure-web-002 = agent 推定)。検査行とファイル行は期限まで残し、確定済み項目は `r2_key=NULL`・`error_kind='committed'`・`summary_json.commit` の最小 receipt だけにする。
- 同一の検査 ID とファイル項目 ID を再送したときは取込本体を実行せず、receipt と `import_runs` から同じ結果を返す。

#### Error contract

| HTTP | Code | Condition | Retryable | Client action |
| --- | --- | --- | --- | --- |
| 400 | invalid_request | 本文の形が不正、または取込可能が 0 件 | no | 選び直す |
| 403 | forbidden_origin | Origin 不一致 | no | 画面から操作し直す |
| 404 | not_found | 検査 ID が無い・他人の・期限切れ、または別の検査の項目 ID | no | 最初から選び直す |
| 409 | import_busy | 同じ利用者の取込が実行中 (既存) | yes | 少し待って押し直す |
| 409 | query_budget_exceeded | 全ファイルのクエリ予算の合計が上限を超える | no | ファイルを分けて取り込む |
| 413 | payload_too_large | 本文が小さい上限を超える | no | 画面から操作し直す |
| 429 | rate_limited | 確定 5 回/分の超過 (`Retry-After`) | yes | 待ち時間を文言で出す |

`import_busy` は既存の code。`query_budget_exceeded` の名前は **agent 推定・利用者未確認** で、既存の予算超過の code があればそれに合わせる。

#### 実行セマンティクス

ファイル単位で順に書き、ファイルごとの成否を記録する。1 件以上成功・1 件以上失敗なら一部成功で返す。同じ確定要求の再送は保存済みの結果と残りの項目 ID を返し、明細と run を増やさない。

#### キャッシュ・ページング

N/A: 単一の作成要求。成功後に web は履歴と review-queue のキーを無効化する。

#### 可観測性と監査

`import_runs` の行 (影響の 3 数値・結果・前回データを残すの値) と `imports` の行が取込の監査記録になる。

#### セキュリティ確認

別の検査のファイル項目 ID を混ぜられない (404)。仮置きの原本は本人だけが確定できる。

#### Contract tests

確定が検査 ID だけで取り込み、ファイルの再送が要らない。エラーのファイルが外れる。期限切れ・他人の検査 ID が 404。確定応答の消失後に同一選択を再送しても明細と run が増えず、同じ結果と `remaining` が返る。確定を始めた検査への追加・削除は 404。前回データを残すのオンで同じファイルを 2 回取り込んでも明細数が増えず 2 回目の新規追加 0 件・重複スキップ全行、オフで月単位の入れ替えと同じ結果、強制再取込で同じ内容が再適用される。一部成功の結果。6 回目が 429。

## エラー・例外・回復

- 送信前の上限超過: 送らずに行を取込不可にし、理由 (25MB 超・10 ファイル超・合計 30MB 超) を出す。
- 413: 上限の文言を出す。検査の要求が 413 なら、その要求のファイルを取込不可にして選び直せるようにする (**agent 推定・利用者未確認**)。
- 429: `Retry-After` の秒数を「n 秒後にもう一度お試しください」の形で出す (文言は **agent 推定・利用者未確認**)。
- 403 forbidden_origin: 「この画面から操作し直してください」を出す (**agent 推定・利用者未確認**)。
- 404 (期限切れの検査 ID など): 検査結果を捨て、ファイルを選び直す案内を出す。
- 409 import_busy: 少し待って押し直す案内。409 のクエリ予算超過: ファイルを分けて取り込む案内。
- アップロード中のネットワーク失敗: 送った要求のファイルを「失敗」にし、「再試行」で同じ検査 ID へ足す (検査 ID が未発行なら新しい検査として送る。**agent 推定・利用者未確認**)。
- 確定中の失敗: ファイルごとの成否を返し、一部成功として結果を出す。エラーのファイルだけを再試行できる。
- 展開の上限超過・パース不可: そのファイルだけを取込不可にし、他のファイルは続ける。

- Content-Length が無い要求の止まり方: hono/body-limit は本文をストリームで数えて上限で止める、と security 章は書くが、一次出典の確認は無い。実装時に hono の版 (`packages/api/package.json` は `^4.13.5`) で挙動を確かめ、テストで Content-Length ありと無しの両方を固定する。宣言と実長のずれは Workers ランタイムに任せる。
- xlsx 展開時のメモリ: ピーク約 90MB は見積もりで実測ではない。実装時に 25MB の xlsx と展開後 60MB 近いファイルで実測し、128MB に収まらなければ上限を下げる、または xlsx を 1 要求 1 ファイルに限る後退策を利用者に諮る。
- qa_refs の追記漏れ (backend への decision-006・-009、ui-ux への -007): 本文の確定内容は決定 qa の値どおりで、仕様上の影響は無い。
