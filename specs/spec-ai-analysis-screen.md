# AI分析画面 再現仕様

正本の画像は `design/FINAL-UI/images/12-ai.png`、経路は `/ai`。上位の要件は `system-spec/00-requirements-definition.md` (U1-U9、利用者承認 qa-ai-decision-009) とカテゴリ別の章 (ui-ux / frontend / backend / database / auth / security / infrastructure / maintenance-ops) にある。本書はそれらを 1 画面の実装単位へ落とした仕様で、画像のどの文言をそのまま再現し、どの値を期待値にしないかを明示する。

注記の約束: 利用者が決めた値は決定 ID (qa-ai-decision-00N) を添える。画像にも決定にも値が無く、実装の決定論のために置いた値は **「agent 推定・利用者未確認」** と明記する。

## 目的と成功状態

目的: 利用者 (家計と個人事業を 1 人で見る本人) が、AI に分析を依頼し、進み具合を確かめ、返ってきたレポートを根拠と版つきで読んで次の行動へ移るまでを 1 画面で終えられるようにする。アプリ自身は LLM を呼ばず、外部のエージェント (Claude Code / Codex) が依頼ごとの使い捨てトークンで既存の API を呼ぶ構成を保つ。

成功状態:

- `/ai` が 問いの見出し・共通の期間タブ・1.依頼・2.実行中 で描画され、長文のレポートと依頼 1 件の詳細は専用 URL (`/ai/tasks/:taskId`、`/ai/reports`、`/ai/reports/:reportId`) で開ける (G1)。
- 依頼の状態が記録から導いた段階 (待機中 0% / 実行中 50% / 実行中 75% / 完了 100% / 失敗 / キャンセル) で表示され、画面と agentGuard が同じ判定を使う (G2、qa-ai-decision-002)。
- キャンセル・再実行・削除が履歴を残す規則どおりに動く (G3、qa-ai-decision-003)。
- レポートが問い順のタブ・版の説明・版履歴・2 版比較で読める (G4、qa-ai-decision-007 / 008)。
- 使用するデータの件数が実データと一致し、外部へ出るのは集計値だけで、大きすぎる body は読み込み前に止まる (G5、qa-ai-decision-004)。

## 用語と主体

| 用語 | 意味 |
| --- | --- |
| 依頼 | `ai_tasks` の 1 行。期間・補足指示・使い捨てトークンのハッシュ・期限を持つ。 |
| レポート | `ai_reports` の 1 行。依頼 1 件から 1 件だけ作られる。同じ期間の中で版番号が進む。 |
| 段階 | 依頼の記録 (時刻列) と現在時刻から導く表示上の状態。保存しない。 |
| T-番号 | 利用者ごとの連番 `seq` を `T-` と 4 桁のゼロ埋めで表した依頼 ID (画像の `T-0004`)。 |
| 版の説明 | 版履歴の各行に出す 1 行。依頼の補足指示から導く (qa-ai-decision-007)。 |
| 使用するデータ | 期間内の freee 事業取引の件数・MF 家計明細の件数・科目数・取引先数 (qa-ai-decision-004)。 |
| 選択中の依頼 | 結果の取り込み先になる依頼。`/ai` では実行中 → 待機中 → 最新の完了の順で自動的に決まり、`/ai/tasks/:taskId` では開いているその依頼 (qa-ai-decision-005)。 |

主体:

- 利用者: セッション cookie で認証された本人。画面の全操作を行う。
- エージェント: Claude Code / Codex。依頼ごとの Bearer トークンだけを持ち、データ取得とレポート送信だけを行う。
- 保守者: 同一人物とコーディングエージェント。規則を core・docs・テストで読む。

## ユースケースとユーザーフロー

1. 依頼する: 期間タブで期間を選ぶ → 補足指示を書く (下書きは自動保存) → 使用するデータの件数を確かめる → 「Claude Code用プロンプトをコピー」または「Codex用をコピー」を押す → 依頼が発行され、指示文がクリップボードに入り、下書きが消え、その依頼の詳細 (`/ai/tasks/:taskId`) が開く → 利用者が AI に貼り付けて実行する。`/ai` へ戻ると 2.実行中の先頭に待機中 0% の行が出ている。
2. 進み具合を見る: エージェントがデータを取ると実行中 50%、形式エラーで差し戻されると実行中 75%、受信すると完了 100%。期限までに受信しなければ失敗。2.実行中の表と、依頼の詳細 (`/ai/tasks/:taskId`) が段階と進捗を示し、結果待ちのあいだは自動で取り直す。
3. 取り消す: 待機中・実行中の行の「キャンセル」→ トークンが無効になり、行はキャンセルとして残る。
4. やり直す: 失敗・キャンセルの行の「再実行」→ 同じ期間と補足指示で新しい依頼が発行され、指示文が返る。元の行は残る。
5. 消す: 結果の無い行の「削除」→ 確認の後に行が消える。完了の行は消せない。
6. 手で取り込む (ネットワークの使えない AI 向け): 結果待ちの依頼の詳細 (`/ai/tasks/:taskId`) を開き → 結果 JSON を貼り付け → 「結果を取り込む」→ 構文エラーなら行と位置の文が出て入力は残る。契約違反なら issues が出る。成功すると詳細が開く。
7. 読む: `/ai/reports` の一覧から版を選び、`/ai/reports/:reportId` で開く (完了直後は `/ai/tasks/:taskId` からそのまま読める) → 要約 (総評・主な発見・次に取るべきアクション) → 根拠データ → 背景仮説 → 改善提案 → 関連リンクと読み進め、要約の下の関連ページへのリンクで該当画面へ移る。版履歴で過去の版に切り替え、「2つの版を比較」で差を見る。
8. 片付ける: 詳細の「アーカイブ」で一覧から外す。「アーカイブを表示」で戻せる。

## 機能要件

- FR-1 期間: 期間タブは `usePeriod` の値をそのまま使う。1.依頼の対象期間の表示と、依頼・使用するデータの API へ渡す `from` / `to` は同じ値である。前年比較に要る範囲は API が期間から導く (qa-ai-decision-001)。
- FR-2 補足指示: 画面の入力上限は 1000 字 (画像の `0/1000`)。現在の字数を `N/1000` で出す。API の既存上限 (`taskCreateSchema` の supplement 4000 字) は変えない。
- FR-3 下書き: 補足指示を localStorage に自動保存し、保存した時刻を「✓ 下書きを自動保存しました HH:MM」で出す。画面を開き直すと復元する。依頼の発行に成功したら消す。サーバーへは送らない (qa-ai-decision-006)。
- FR-4 コピー: 2 つのボタンと再実行は、返った指示文をクリップボードへ書き、成功後に `POST /ai/tasks/:id/copied` へコピー先を記録する。処理は共有モジュールを使う。
- FR-5 使用するデータ: `GET /ai/inventory` の件数を右カードに出す。「使用データを確認」はカードと同じ期間の依頼に限ってデータセットを開く。AIへは集計値だけを渡し、明細ID・摘要・memoは渡さない (qa-ai-decision-004)。
- FR-6 実行中の表: `GET /ai/tasks` の結果を作成日時の新しい順に出す。列は ID / ステータス / 依頼期間 / 作成日時 / 進捗 / 依頼内容 / 操作。
- FR-7 操作: 段階ごとの操作は「UI・状態遷移」の表のとおり。
- FR-8 依頼の詳細 (`/ai/tasks/:taskId`): 依頼 1 件の T-番号・段階のバッジ・依頼内容・進捗・依頼日時・プロンプトのコピー状況と、段階に応じた「次にすること」と操作 (キャンセル / 同じ条件で再実行) を出す。結果待ちならこの画面で結果を取り込み、完了ならこの画面でレポートを読む。
- FR-9 レポート一覧 (`/ai/reports`): 版 / 作成日時 / レポート名 / 対象期間を出す。検索はレポート名・要約内容・対象期間の表示文字列の部分一致。「アーカイブを表示」で `archived=1` を付けて取り直す。
- FR-10 取り込み: 取り込み欄は結果待ち (待機中・実行中) の依頼の詳細に出し、取り込み先はその依頼。取り込み先が無ければ「結果を取り込む」を無効にする (qa-ai-decision-005)。「クリア」は入力とエラー表示を消す。
- FR-11 詳細 (`/ai/reports/:reportId`、完了した依頼の詳細でも同じ部品): 見出しにレポート名と版と最新版の印、作成日時・対象期間・作成元・ステータス、5 タブ、要約の下に関連ページへのリンクと版履歴、「2つの版を比較」、「アーカイブ」を出す。
- FR-12 版の説明: 補足指示の 1 行目。無ければ v1 は「初回レポート」、v2 以降は「最新のデータで再分析」(qa-ai-decision-007)。
- FR-13 タブの振り分け: 要約 = 総評・主な発見・次に取るべきアクション (上位 3 件の次の一手)。根拠データ = 図表・5 節・データ不足。背景仮説 = 契約の `contextAnalysis` (問いの整理・ヒアリング事実・統計的事実・解釈・仮説と外部の根拠。記録の無い版は「この版は背景仮説の契約追加前に作られたため、記録がありません。」と出す)。改善提案 = 要点 3 分類・前回の指摘。関連リンク = 必要な情報と各画面へのリンク (qa-ai-decision-008。5 タブ構成は 2026-09-21 に利用者が実装どおりへ決め直した。旧: 背景仮説を欠く 4 タブ)。
- FR-14 URL: 依頼とレポートはパスで表す (`/ai`、`/ai/tasks/:taskId`、`/ai/reports`、`/ai/reports/:reportId`)。検索パラメータに持つのはタブ (`tab`、既定の要約のときは付けない) だけで、再読込でタブが復元する。旧 `task` / `report` クエリは状態として復元しない (2026-09-21 に利用者がこの構成へ決め直した)。`/ai` は改訂の下書きのために `reanalyze` / `mode` を受け取る。

## 非機能要件

- 性能: 画面は既存どおり遅延読み込みする。初期 JS 予算 (js-budget) を超えない。`GET /ai/inventory` は期間で絞った件数読み取りだけで作り、AI 用の SQL を増やさない。
- 可用性: migration 0047 の適用前に新しい Worker が動いても壊れないよう、`runtimeSchemaGuard` の期待headを同期する。0047 は既存本文を失わず重複版を連番化して一意制約を張る。
- アクセシビリティ: 状態を色だけで伝えない。ステータスに文字、進捗に数値の % と棒の両方、最新版の印に文字を添える (WCAG 2.2 SC 1.4.1)。
- 保守性: 段階の優先順位・版の説明の既定文・タブの振り分け・使用するデータの数え方を `docs/ai-screen/` に表で残し、同じ表を core の単体テストの期待値にする。
- 見た目: 直書き色 0。色はデザイントークン、ボタンは共通 Button、ページは PageShell。

| `/ai` | 問いの見出し・1.依頼・2.実行中 |

| `/ai/reports` | 保存済みレポートの一覧 |
| `/ai/reports/:reportId` | レポートの詳細 (タブ・版履歴・版比較・アーカイブ) |

3. 問いの見出し「AIに分析を依頼し、根拠と版を確認しますか？」と説明文 2 行「社内の取引データをもとに、Claude Code / Codex で分析を実行します。」「ここでは、分析の依頼から実行状況の確認、結果レポートの取り込み・確認までを行えます。」

5. 2.実行中

### 1. 依頼

- 「補足指示・分析の観点（任意）」の入力欄。placeholder は「例：売上の増減要因を分析し、費用の削減余地がある項目を特定してください。前期と比較し、主な変動要因も示してください。」
- 入力欄の下に「✓ 下書きを自動保存しました HH:MM」と字数「N/1000」。
- ボタン「Claude Code用プロンプトをコピー」(主) と「Codex用をコピー」(副)。
- 注記「データは自動送信されません。コピーしたプロンプトを各AI（Claude Code / Codex）に貼り付けて、実行してください。」

| キャンセル | - | 再実行・削除 | (終端。再実行は新しい依頼を作る) |

キャンセルの進捗を「-」にすること、キャンセルの行に再実行・削除を出すことは画像に例が無いため、**agent 推定・利用者未確認** である。

## ビジネスルールと検証

### 段階と進捗 (core の純関数、qa-ai-decision-002)

入力は依頼の `usedAt` / `canceledAt` / `expiresAt` / `rejectedAt` / `dataFetchedAt` と現在時刻。上から順に最初に当たったものを返す。

| 順 | 条件 | 段階 | 進捗 |
| --- | --- | --- | --- |
| 1 | `canceledAt` あり | キャンセル | なし |
| 2 | `usedAt` あり | 完了 | 100 |
| 3 | `expiresAt` が現在より前 | 失敗 | なし |
| 4 | `rejectedAt` あり | 実行中 | 75 |
| 5 | `dataFetchedAt` あり | 実行中 | 50 |
| 6 | それ以外 | 待機中 | 0 |

段階の意味 (発行済みでデータ未取得 = 待機中 0%、データ取得済み = 実行中 50%、差し戻し = 実行中 75%、受信 = 完了 100%、結果なしで期限切れ = 失敗、取り消し = キャンセル) は利用者の決定である。上の優先順位 (キャンセルが完了より先、期限ちょうどは待機中側) は **agent 推定・利用者未確認** (qa-ai-backend-web-003) である。api の `taskStatus` (done / expired / waiting) はこの関数に置き換え、`agentGuard` も同じ関数で判定する。

### T-番号

`seq` を 4 桁にゼロ埋めして `T-` を付ける。`seq` が 10000 以上なら桁をそのまま出す (**agent 推定・利用者未確認**)。`seq` が NULL なら「旧」と作成日。採番は利用者ごとに `max(seq)+1` で、`(user_id, seq)` の一意索引に衝突したら 1 回だけ採番し直す (**agent 推定・利用者未確認**、qa-ai-database-web-003)。

### 版の説明 (qa-ai-decision-007)

補足指示を前後の空白を除いて改行で分けた最初の空でない行。無ければ v1 は「初回レポート」、v2 以降は「最新のデータで再分析」。レポート JSON の schema と skill は変えない。

### タブの振り分け (qa-ai-decision-008)

| タブ | 本文 (契約 v3 の項目) |
| --- | --- |
| 要約 | `summary` (総評)、主な発見 3 点、次に取るべきアクション 3 件 |
| 根拠データ | `charts` (図表)、`sections` の 5 節 (spend / change / reduction / split / subscriptions)、`dataGaps` (データ不足) |
| 改善提案 | `keyFindings` の 3 分類 (improvements / wasted / quickWins)、`followUp` (前回の指摘) |
| 関連リンク | `needs` (必要な情報と各画面へのリンク) |

主な発見と次に取るべきアクションの選び方は、`keyFindings` の 3 分類を 1 列に並べ、`priority` が high → mid → low → null の順、同順位は配列の順で上位 3 件を取り、主な発見にその `label` と `fact`、次に取るべきアクションにその `action` を出す (**agent 推定・利用者未確認**)。

### JSON 取り込みエラーの行と位置

core の純関数が入力文字列を走査し、最初の構文エラーの 1 始まりの行と列を返す。実行環境の `JSON.parse` のメッセージ文字列には依存しない (**agent 推定・利用者未確認**)。構文が通ったら API へ送り、契約検査は既存の `reportInputSchema` と `normalizeReport` に任せる。

### 使用するデータの数え方

期間内の freee 取引の件数、期間内で集計対象の MF 明細の件数 (振替と除外を除く)、期間内に出現した科目の種類数、期間内に出現した取引先の種類数 (**agent 推定・利用者未確認**、qa-ai-backend-web-003)。

### 下書き

localStorage のキーは利用者 ID を含める。1000 字を超える値は保存しない。読み書きの例外は握って画面を止めない (**agent 推定・利用者未確認**、qa-ai-security-web-003)。

## API契約

共通: 利用者経路はすべて `/api/*` のセッション認証のフェンスの内側に載る。他の利用者の依頼・レポートの id には 404 を返す。エラーの形は既存どおり `{ "error": { "code": string, "message": string } }`。

### POST /ai/tasks/:id/cancel

#### 識別と目的

待機中・実行中の依頼を取り消す。トークンを無効にし、行はキャンセルとして残す (qa-ai-decision-003)。

#### 認証・認可

セッション cookie。`userId` の一致する依頼だけ。

#### Request

path `id`。body なし、または空の JSON `{}`。

#### Response

200 `{ "ok": true, "task": 依頼ビュー }`。依頼ビューは下の `GET /ai/tasks` と同じ形。

#### Validation・ビジネスルール

`canceled_at` を現在時刻にする更新は `used_at IS NULL AND canceled_at IS NULL` を条件にした 1 文 (CAS) で行う。すでにキャンセル済みなら更新せず 200 で現在の依頼ビューを返す (冪等、**agent 推定・利用者未確認**)。

#### Error contract

| HTTP | Code | Condition | Retryable | Client action |
| --- | --- | --- | --- | --- |
| 404 | not_found | 依頼が無い、または他の利用者の依頼 | no | 一覧を取り直す |
| 409 | already_done | 結果を受信済み (完了) | no | 詳細を開く |
| 409 | already_expired | 期限切れ (失敗) | no | 再実行か削除を選ぶ |
| 413 | payload_too_large | body が上限超過 | no | body を送らない |

`already_expired` を 409 にすることは **agent 推定・利用者未確認** である。

#### 実行セマンティクス

1 文の条件付き更新。受信との競合で `used_at` が先に入った場合は 409 already_done。

#### キャッシュ・ページング

N/A: 単一行の更新で一覧を返さない。

#### 可観測性と監査

失敗は既存の API エラーログの流儀で code を残す。トークンやその平文は記録しない。

#### セキュリティ確認

取消後のトークンは `agentGuard` で 401 になる (下記)。

#### Contract tests

待機中・実行中 50%・実行中 75% の取消が 200、完了が 409 already_done、失敗が 409 already_expired、2 回目の取消が 200 で `canceledAt` 不変、他の利用者の id が 404、取消後のトークンでのデータ取得とレポート送信が 401。

### POST /ai/tasks/:id/retry

#### 識別と目的

失敗・キャンセルの依頼と同じ期間と補足指示で新しい依頼を発行する。元の行は残す (qa-ai-decision-003)。

#### 認証・認可

セッション cookie。`userId` の一致する依頼だけ。

#### Request

path `id`。body なし、または空の JSON `{}`。

#### Response

201。`POST /ai/tasks` の成功応答と同じ形 (指示文と新しい依頼ビュー)。新しい依頼は新しい `seq` とトークンを持つ。`parentReportId` は元の依頼の値を引き継ぐ。

#### Validation・ビジネスルール

元の依頼の段階が失敗かキャンセルのときだけ受ける (**agent 推定・利用者未確認**。画像の再実行は失敗の行だけ)。期間は元の `period_from` / `period_to` を使う。

#### Error contract

| HTTP | Code | Condition | Retryable | Client action |
| --- | --- | --- | --- | --- |
| 404 | not_found | 依頼が無い、または他の利用者の依頼 | no | 一覧を取り直す |
| 409 | not_retryable | 段階が待機中・実行中・完了 | no | その行の操作を使う |
| 413 | payload_too_large | body が上限超過 | no | body を送らない |

#### 実行セマンティクス

新しい行の挿入だけ。元の行は書き換えない。

#### キャッシュ・ページング

N/A: 単一行の作成で一覧を返さない。

#### 可観測性と監査

失敗の code を残す。トークン平文は応答の指示文にだけ入り、ログに出さない。

#### セキュリティ確認

新しいトークンは既存と同じく 32 バイトの乱数を base64url にし、SHA-256 のハッシュだけを保存する。

#### Contract tests

失敗とキャンセルから 201 で新しい `seq` が 1 増える、元の行が残る、待機中・実行中・完了が 409、他の利用者の id が 404。

### GET /ai/inventory

#### 識別と目的

1.依頼の「使用するデータ」カードの件数を返す (qa-ai-decision-004)。

#### 認証・認可

セッション cookie。自分のデータだけを数える。

#### Request

query `from` / `to` (`YYYY-MM`)。既存の `periodSchema` と同じ検証 (開始が終了以前、最長期間の上限)。

#### Response

200 `{ "period": { "from", "to", "label" }, "freeeDeals": number, "mfTransactions": number, "categories": number, "counterparties": number }`。キー名は本仕様で新設する。

#### Validation・ビジネスルール

数え方は「ビジネスルールと検証」の使用するデータの数え方のとおり。

#### Error contract

| HTTP | Code | Condition | Retryable | Client action |
| --- | --- | --- | --- | --- |
| 400 | invalid_request | `from` / `to` の書式や範囲が不正 | no | 期間を選び直す |
| 401 | unauthorized | セッションが無い | no | ログインし直す |

#### 実行セマンティクス

読み取りだけ。期間で絞った件数読み取りを 1 回の batch で行う。

#### キャッシュ・ページング

画面側は期間をキーにしてキャッシュする。サーバー側のキャッシュとページングは N/A: 件数 4 つの小さな応答。

#### 可観測性と監査

通常の API ログだけ。

#### セキュリティ確認

件数だけを返し、明細・摘要・金額を返さない。

#### Contract tests

フィクスチャの期間で 4 つの件数が同じ期間の D1 行数と一致する、他の利用者の行を数えない、不正な期間が 400。

### 既存経路の変更

| 経路 | 変更 |
| --- | --- |
| `POST /ai/tasks` | 採番した `seq` を保存し、依頼ビューに段階・進捗・T-番号を加える。期間は `usePeriod` の範囲を受ける。 |
| `GET /ai/tasks` | 依頼ビューに `stage` / `progress` / `displayId` / `canceledAt` / `rejectCount` を加える。既存の `status` は core の段階から導く。既存の上限 20 件と新しい順は変えない。 |
| `DELETE /ai/tasks/:id` | 規則は変えない (結果の無い依頼だけを消し、受信済みは 409 already_done)。キャンセル済みも結果が無いので消せる。 |
| `GET /ai/tasks/:id/data` (エージェント) | 成功時に `data_fetched_at` が NULL なら現在時刻を書く。 |
| `POST /ai/tasks/:id/report` (エージェント) | 契約違反 (400) で差し戻すとき `rejected_at` を現在時刻にし `reject_count` を 1 増やす。body 上限を読み込み前に掛ける。 |
| `POST /ai/tasks/:id/paste` | body 上限を読み込み前に掛ける。キャンセル済みの依頼には 409 を返す。 |
| `agentGuard` | 期限切れ・受信済みに加え、キャンセル済みも 401 unauthorized で拒否する (文言「この依頼は取り消されました。アプリで指示文を作り直してください」)。 |
| `runtimeSchemaGuard` | 必須列に 0046 の列を加える。 |

body 上限: レポート送信・貼り付けの request budget は固定 4 MiB (4,194,304 bytes)。境界値までは bodyLimit を通し、1 byte 超過は JSON 読み込み前に 413 `payload_too_large` を日本語の文で返す。個別 field・配列は `reportInputSchema` と `normalizeReport` が別に検証する。キャンセル・再実行の body 上限は 4KB。これらは **agent 推定・利用者未確認** である。

## データモデル

migration `migrations/0046_ai_task_stages.sql` (追加のみ)。既存の最新は `0045_owner_labels.sql`。

- 既存行は書き換えない (更新 0 件)。段階名・進捗 %・版の説明は導出できるので保存しない。
- `ai_reports` には列を足さない。
- `packages/api/src/db/schema.ts` の `aiTasks` に同じ列と索引を足す。

migration `migrations/0047_ai_report_invariants.sql`。版の一意性を DB 側の不変条件にする。列は足さず、既存行の `version` だけを書き換える。

| 対象 | 内容 |
| --- | --- |
| 一意索引 `uq_ai_reports_series_version` | `(user_id, report_type, period_from, period_to, version)`。同じ系列に同じ版番号を 2 行置けなくする。 |

- **既存行の `version` を書き換える** (このハーネスで唯一の行更新 migration)。旧実装が版を件数から決めていたため、同時受信や古い fixture に重複版があり得る。索引を張る前に、系列ごと `created_at, id` 順の `ROW_NUMBER()` で連番へ正規化する。
- 書き換えるのは `version` 列だけで、本文・`created_at`・`task_id`・id は変えない。行の削除・追加もしない。作成順は保存則として保たれる (並べ替えの基準が `created_at, id` 自身なので、正規化後も順序が入れ替わらない)。
- 既に連番が正しい行は `WHERE version <> next_version` で除外するので更新 0 件。
- **既存の `task_id` 重複は消さない。** trigger は BEFORE INSERT なので、今後の追加だけを止める。過去の重複行と、それを指す参照はそのまま残る。
- `packages/api/src/db/schema.ts` の `aiReports` に同じ一意索引を足す (trigger は SQL 側だけが持つ)。

## 認証・認可

- 利用者経路 (`/ai/tasks`・`/ai/reports`・`/ai/inventory` 配下) は既存のセッション cookie 認証のフェンスの内側に置き、route の中で個別の認可判定を書かない。各クエリは `c.get('userId')` で絞る。
- エージェント経路 (`/ai/tasks/:id/data`・`/ai/tasks/:id/report`) は依頼ごとの Bearer トークンだけを受け、`agentGuard` 1 か所で拒否する。期限切れ・受信済み・キャンセル済みはすべて 401 unauthorized。
- 新しいログイン手段や長期トークンは設けない。トークンの有効期限 24 時間と接頭辞 `kjo_` は変えない。

## エラー・例外・回復

- 取り込みの構文エラー: 保存せず、行の文を出し、入力を保持する。修正して再度押せる。
- 取り込みの契約違反 (400 invalid_report / missing_sections): issues の先頭 20 件をそのまま一覧で出し、入力を保持する。
- 取り込み先の依頼が完了済み (409 already_done): 「この依頼は結果を受信済みです」を出し、入力を保持する。
- キャンセル・再実行・削除の 409: 文を出して依頼一覧を取り直す。
- 413: 「送信できる大きさを超えています」の文を出し、入力を保持する。
- クリップボードへの書き込み失敗: 指示文を選択可能な欄に出して手でコピーできるようにする。依頼は発行済みのまま残る。
- localStorage の例外: 下書きの自動保存表示を出さず、入力は続けられる。
- ネットワーク失敗: 各段の失敗状態と再読込。

## イベント・非同期処理

- アプリ内にキュー・定期処理・Webhook は無い。段階の変化はエージェントが既存の API を呼んだ結果として D1 に記録される。
- 画面は依頼一覧を取り直して段階の変化を拾う。結果待ち (待機中・実行中) の依頼があるあいだだけ一定間隔で取り直す (間隔 10 秒、**agent 推定・利用者未確認**)。結果待ちが無ければ取り直さない。
- 操作 (コピー・キャンセル・再実行・削除・取り込み・アーカイブ) の成功後は、依頼一覧とレポート一覧のうち該当するキーだけを無効化する (TanStack Query の invalidateQueries)。

## 可観測性

- 段階の記録列そのものが観測点になる: データを取りに来たか (`data_fetched_at`)、何回差し戻したか (`reject_count`)、利用者が取り消したか (`canceled_at`)。
- API のエラーは既存の流儀で code を残す。トークンの平文、補足指示の本文、レポート本文はログに出さない。
- 新しい計測基盤やダッシュボードは足さない。

## 互換性・移行・リリース

- 反映の順序は既存の Migrate → Deploy。0046 は列追加だけなので、適用後に旧 Worker が動いていても新しい列を読まないだけで壊れない。巻き戻しは Worker を戻すだけでよい。
- 0047 は行を書き換えるので巻き戻しが対称でない。**索引と trigger は DROP で戻せるが、正規化した `version` は元へ戻らない。** 重複版はもともと表示上の同点でしかなく、戻す値が一意に定まらないため。適用前の DB を戻したい場合は Migrate 前のバックアップを使う。
- 0047 適用後に旧 Worker が動いても、旧実装の採番 (件数+1) は正規化後の連番と一致するので INSERT は索引に衝突しない。衝突するのは 1 依頼に 2 通目を入れようとしたときだけで、それは旧実装でも不正な状態だった。
- 既存の依頼は `seq` が NULL のまま「旧」と作成日で表示する。既存のレポートは本文が変わらない。版番号は重複していた系列だけが連番へ直り、番号の大小関係 (どれが新しいか) は保たれる。
- レポート JSON 契約 v3 と skill `run-kanjo-accounting-report` は変えないので、`skills:test` と契約テストは緑のまま。
- 既存の DOM テストが import する部品名は、移設先から再エクスポートするか、テストを新しい構成に合わせて書き直す。
- 新しい secret・binding・外部サービスの登録は発生しない。

## テストと受入条件

core 単体テスト (vitest):

- 段階の 6 条件それぞれと、境界 4 件を `toBe` で固定する: 期限切れと受信が同時に成り立つ行は完了、キャンセル後に期限が切れた行はキャンセル、差し戻し後にデータを再取得した行は 75% のまま、期限ちょうどの時刻は待機中 (**agent 推定・利用者未確認**、qa-ai-maintenance-ops-web-003)。
- T-番号: 1 → `T-0001`、9999 → `T-9999`、10000 → `T-10000`、NULL → 「旧」と作成日。
- 版の説明: 補足指示あり (1 行目)、先頭が空行、補足指示なしの v1 と v2。
- タブの振り分け: 契約 v3 のフィクスチャを振り分けた結果を `toEqual` で固定する。
- JSON エラーの行と位置: 10 行目に不正な文字を置いた入力で 10 を返す。

- cancel / retry / inventory の Contract tests (各節に列挙したもの)。
